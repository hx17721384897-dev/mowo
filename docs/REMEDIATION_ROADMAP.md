# REMEDIATION_ROADMAP.md - 按功能区整改路线

> 基准日期：2026-08-12。最后更新：2026-08-18。
>
> 这份路线把代码整改拆成用户能理解和验收的功能区。每一批开始前复述项目目标、当前范围和暂不处理的事项；修改时同步检查安全、性能、数据一致性和文档，不把历史规划自动当成已上线功能。

## 最优实施顺序

项目不需要为了“企业级”推倒重写。当前的 Fastify、PostgreSQL、Prisma 和阿里云 OSS 可以继续使用；更重要的是先把配置、账号、文件、订单和运维规则做成可验证的闭环，再按真实访问量扩容。

|---|---|---|---|
| 0 | 工程地基 | 让项目换一台电脑也能装好、启动、检查，错误配置不能带病运行 | R0.1 已完成，数据库基线待处理 |
| 1 | 账号与文件安全 | 保护手机号、登录状态、用户视频/原图、简历和合同，防止越权读取或误删 | 本地与内部邀请测试核心规则已验收；恶意文件扫描、正式 OSS 和定制素材入口在对应阶段继续 |
| 2 | Web 定制主流程 | 用户看价格、上传素材、看初筛结果、提交人工审核并确认最终款式和价格 | 首批提交与后台接收已完成；审核协作与订单待下一批 |
| 3 | 微信小程序交易 | 网页订单通过一次性码关联到微信用户，在小程序确认购物车和付款 | 待整改；真实支付需主体和商户条件 |
| 4 | 生产、库存与售后 | 管理订单编号、批次、生产状态、现货/现做、发货和售后 | 暂缓定案，开发前由负责人讲解完整流程 |
| 5 | 创作者合作与内部台账 | 初期人工认定创作者、记录合作和优惠，线上分红/牛量/提现保持关闭 | 待整改 |
| 6 | 稳定上线与扩容 | 自动测试、备份恢复、监控告警、压测和多实例运行 | 随前述模块渐进建设 |

## 功能区 1：账号与文件安全

### 第一批：登录与设备安全（已完成）

- 首发登录弹窗只展示短信验证码，密码登录能力保留但默认关闭。
- 旧注册和旧登录入口永久停用；Web 账号资料读取和修改迁到新版接口。
- 每台设备拥有独立会话；退出当前设备不影响其他设备，另提供“退出全部设备”。
- 设置或修改密码时保留当前设备，撤销其他设备；换手机号、封禁和注销撤销全部设备。
- 所有需登录接口统一检查设备会话和账号状态；员工角色调整后按数据库当前值立即生效。

简单说：电脑和手机各有一把独立钥匙，普通退出只收回当前钥匙，安全事件才会收回全部钥匙。

补充修复：设置页现有“退出当前设备”和“退出全部设备”两个按钮，头像菜单普通退出只退出当前浏览器。`router.js` 已改为普通脚本可用的 `window.Router`，设置页安全按钮优先绑定；退出时停止自动续期，避免退出后被并发刷新重新登录。

### 第二批：员工权限与安全记录（已完成）

- 增加负责人、运营客服、生产人员、合作运营四个固定岗位；保留旧数字角色用于兼容。
- 后台请求统一按岗位权限拦截，页面菜单按岗位显示，服务器仍是最终权限判断者。
- 售后列表和处理接口补齐登录与员工权限保护。
- 员工不能修改或封禁自己；运营客服不能停用员工；负责人不能被普通封禁；至少保留一位负责人。
- 岗位变化后撤销该员工所有设备会话。
- 用户列表默认返回脱敏手机号。
- 通用安全记录增加成功/失败/拒绝、HTTP 状态、设备会话和浏览器，并统一隐藏密码、验证码、凭证、手机号、地址、快递单号和文件内容。
- 安全记录页面仅负责人可见，并对内容做网页转义，防止日志内容执行恶意代码。
- 增加 `npm run check:staff-security` 权限反向测试。详细事实见 `modules/staff-permissions-audit.md`。

### 第三批：私有文件核心安全（核心层已完成，业务入口按模块迁移）

- 新增 `private_files` 登记用途、所有者、大小、声明/识别类型、校验状态和业务绑定。
- 本地开发不再依赖已暂停的阿里云 OSS，使用不公开的 `storage/private`；生产仍强制使用私有 OSS。
- 头像、售后凭证、创作者帧图、联络作品集和简历已接入；匿名联络附件使用临时上传身份绑定同一留言。
- 普通用户不能查看或绑定他人文件；员工只能查看已绑定业务且属于本岗位范围的文件；未绑定文件对负责人也不可见。
- 已执行大小、扩展名、MIME 和文件头检查，并增加 `npm run check:private-files` 反向测试。
- 头像替换、废弃头像自动清理和删除失败重试已完成；尚未完成恶意文件扫描、定制原视频主流程、旧 ZIP 帧包迁移和全部业务文件的保留期限配置。详见 `modules/private-file-security.md`。

### 首要工作

- 已完成：统一登录设备会话和账号注销规则；注销采用 10 分钟防误操作保护期、跨业务阻断、限制新增、期满匿名化、失败重试和后台异常任务管理；修改密码后保留当前设备并撤销其他设备。
- 已完成：修复当前确认的后台遗漏鉴权，建立固定岗位并限制用户资料范围。
- 已完成：安全记录不再保存密码、验证码、地址、手机号等完整请求内容。
- 已完成核心层：为视频、原图、简历、作品集和合同分别建立上传用途、所有者、大小、类型和读取权限；定制主流程、合同和旧帧包入口仍需接入。
- 已完成：登录/验证码、联络和上传的数据库分级限流，接口基础安全响应头及过期计数清理；正式网关、可信代理、指标和人机验证待部署阶段补齐。
- 已完成：用服务端功能开关关闭首发不开放的社区、模拟认证、创作者自助联名、分红、牛量和提现接口；前端同步隐藏，联名展示保留。
- 已完成：新增邀请测试版用户协议/隐私政策页面，注册分别保存版本、时间、场景和必要设备证据；正式主体信息和法律审查仍是 B1 阻断项。

### 完成标准

达到 R1 后，才可邀请真实用户提交手机号和素材。普通用户不能读取他人私有文件；员工越权请求会被拒绝并留下脱敏审计记录；注销和资料删除可以实际执行。

### 2026-08-18 阶段验收

- 人工页面回测已完成；真实订单存在时的注销拦截，因订单流程尚未跑通，保留为功能区 2 完成后的人工联调项。

## 功能区 2：Web 定制主流程

### 2026-08-20 首批已完成

- 保留原有设计风格，在上传页增加“我自己筛选”和“请工作人员帮我筛选”两个并列入口，窄屏改为单列。
- 正式提交生成独立 `DZ-YYYYMMDD-XXXXXX` 定制编号；草稿、定制申请、订单和生产编号严格分开。
- 新增“我的定制”列表/时间线和后台“定制处理”页；普通用户、客服、生产、合作运营和负责人权限已做反向测试。
- 原素材、选中帧和编辑配方分开保存；中断上传 24 小时清理，未提交草稿 7 天清理并保留过期说明。
- 正式处理中定制阻止账号注销；未到 `CONFIRMED` 的定制不能通过旧购物车接口绕过审核。
- 当前后台只接收和查看，尚未实现处理动作。详细事实见 `modules/web-customization.md`，人工验收见 `WEB_CUSTOMIZATION_ACCEPTANCE.md`。

### 下一批

- 工作人员开始处理、请求补素材、判定不可制作、推荐其他动画/标准款式，并分开保存内部说明和用户说明。
- 用户补充素材、查看多个方案并确认其中一个；确认后锁定最终价格和版本。
- 只由已确认方案生成待支付订单；随后再进入 Web 与微信小程序的订单关联阶段。

### 已确认的首发路径

1. 未登录用户可以浏览产品和参考价格。
2. 提交定制需求前登录，并确认是否为拥有版权的创作者。
3. 用户上传视频或原图，系统只提供简单筛选结果，不代替最终工艺判断。
4. 工作人员判断素材能否制作；不能制作时可推荐其他动画，款式不适合时推荐几个标准款式。
5. 用户确认款式后生成不可随意修改的最终固定价格和待支付订单。
6. 创作者可以不加企业微信；需要合作或优惠时再由企业微信人工核验和沟通。

### 完成标准

用户不会进入社区、线上分红或复杂设计器；从产品介绍到提交、审核、推荐、确认订单的每个状态都有明确页面、通知和后台操作，并能处理拒绝、超时和重复提交。

## 功能区 3：微信小程序交易

### 推荐方案

- Web 只创建待支付订单和一次性关联码，不直接完成付款。
- 微信扫码打开小程序后，以一次性短码领取对应订单，不能把可伪造的订单号直接当凭证。
- 小程序使用微信身份；付款前绑定并验证手机号，与 Web 账号建立可撤销关联。
- 第一版小程序以联名标准款展示、购物车、订单和微信支付为主；复杂帧编辑仍留在 Web。
- 若微信支付主体条件尚未完成，B 阶段只演练订单确认；企业微信负责沟通，可向已识别用户发送受控订单入口。

### 完成标准

同一个订单不能被多人领取或重复付款；服务端核验金额、商户、签名和支付结果；重复通知不会重复扣库存；用户能看到订单、退款、物流和售后状态。

## 功能区 4：生产、库存与售后

当前代码已经有订单编号、批次和生产状态，但文档与多套实现交叉。项目负责人已明确：库存、批次、扫码、现货/现做和生产状态的完整逻辑，需要在实际修改前专门讲解。

因此本区当前只记录风险，不擅自改业务含义。以后进入本区时，应先画出真实流程和异常分支，再统一状态机、库存流水、扫码绑定、发货、售后和幂等规则。联名商品对用户无需区分预制或现做，后台可优先消耗库存，无库存再进入现做流程。

## 功能区 5：创作者合作与内部台账

- 合同对象不强制注册账号，初期合同和签约在线下完成。
- 管理员可为部分账号标注创作者资格，并记录版权核验、合作状态和标准化优惠资格。
- 在现有管理后台增加简化合作台账；合同与财务记录不能彻底删除，应保留必要的归档和审计信息。
- 首发不启用线上分红率、牛量、余额、提现和收益仪表盘；未来大量创作者进入时，再把收益展示、结算和打款拆成可对账的线上体系。

## 功能区 6：稳定上线与扩容

- 每个功能区同时补自动测试，避免最后一次性返工。
- C 阶段真实交易前完成数据库和 OSS 备份、恢复演练、支付对账和核心告警。
- D 阶段公开上线前建立预发、发布审批、回滚、事故手册和容量目标。
- 先压测再决定云服务器规格；把图片、ZIP、DOCX 和定时任务逐步移出 API 进程，避免大量访问时互相拖慢。

## 每批固定执行方式

1. 复述业务目标、已确认决策和本批不处理的边界。
2. 对照代码、数据库、Web、小程序和 Markdown，列出本批事实与风险。
3. 说明最优方案、用户影响、改造复杂度和需要负责人确认的少量问题。
4. 修改代码和文档，不删除历史信息，不覆盖无关的现有改动。
5. 运行自动检查和关键反向测试，记录通过项与尚未验证项。
6. 汇报当前完成度，并说明下一功能区开始前需要讨论的业务细节。
