# mowo 订单页面流程、接口和实施验收

> 2026-10-14。按“先核对真实数据和代码，再改业务与页面，再验收”推进。这里是开发清单，不把现有基础当成已经达到目标。

## 1. 私人定制完整流程

1. **选商品**：客户选择自己有权使用的定制作品、锁定动画版本、层级规格、SKU、数量；购物车提示无效商品、价格或库存变动。
2. **结算**：服务端重算价格和可售量，生成 PreOrder 与不可变快照，记录库存预留凭据和截止时间；重复提交同一幂等键返回同一结果。
3. **付款**：开发测试用模拟支付；真实环境以后接微信。可信支付成功后原子生成 SO、全部明细、数量相等的 PU，并冻结付款时的暂缓履约分钟数；断网可查最终结果。
4. **客户查单**：付款前后都可在“我的订单”找到交易；付款后未入批显示“已付款”和最早排产时间。
5. **生产**：后台候选显示尚需等待/其他阻止原因；创建 PB 的最终事务复核。成功入批后顾客显示“制作中”，现有生产流程继续运行。
6. **发货与收货**：生产完成才待发货；真实运单绑定后显示运输中；顾客满足条件时确认收货。
7. **取消与售后**：未入批且符合政策时整单取消；入批后通过整单售后申请。取消、申请、审核、退款都留各自记录。

## 2. 页面、接口、数据对照

| 页面 | 需要的服务端结果 | 当前基础/改动重点 |
|---|---|---|
| 购物车/结算 | 商品与 SKU 有效性、重算金额、库存变化、预留结果 | 已有 cart/checkout；核对层级规格、并发与快照 |
| 付款结果 | PreOrder 截止时间、渠道结果、SO 关联 | 已有 payment/status 和模拟支付；补未知/失败恢复和可信支付适配 |
| 我的订单 | PreOrder 与 SO 的统一列表、搜索筛选分页、主状态和可操作项 | 当前 /orders/mine 只读 SO 且先全量后内存分页；须改服务端分页与待付款体验 |
| 订单详情 | 明细快照、金额/支付、最早排产、PU/PB 摘要、运单、售后历史 | 当前 /orders/:id 有部分基础；补独立资金/事件数据 |
| 取消/收货 | 服务端实时资格、原因和最终执行结果 | 当前 cancel/confirm-receipt 有路由；补并发、待付款和退款边界 |
| 售后 | 整张 SO 的申请、审核、凭证、资金进度 | 当前 AftersaleRequest 关联 PU；需改 SO 关联并迁移旧记录 |
| 商家订单 | 查询筛选、待办、支付/生产/物流/售后、操作审计 | 沿用现有后台；订单管理与生产管理相互跳转 |
| 批次/设置 | 候选阻止原因、最终入批校验、分钟数与修改记录 | 现有 PB 候选/创建基础；加冻结时间及所有入口检查 |

每个接口契约应写清：登录或管理员岗位、请求字段、幂等键、可见数据、成功状态、失败码、可重试性、中文页面文案。前端不能从零散字段自行猜主状态或按钮资格。新增字段和数据库迁移须保留历史订单，先核对实际 mowo_db 的迁移记录并备份。

## 3. 首轮数据要补的关系

- PreOrder → 一张正式 SO，支付流水、预留流水各自有唯一识别；支付回调重复时不能新建第二张 SO。
- SO → 多条 SalesOrderItem → 每条按数量生成多个 PU；每件 PU 有自己的 SKU 和成交配置；PB 仍由原生产逻辑建立。
- SO 保存付款时适用的暂缓分钟数和最早入批时间；后台配置更改不更新旧 SO。
- 售后从“挂在任意首个 PU”改为“挂在整张 SO”，旧记录需可追溯；审核结果、退款结果不覆盖生产状态。
- 增加可审计的订单事件和资金事件，记录执行人、时间、原因和关联流水。地址、私有作品、售后图片按本人/岗位读取。

## 4. Git 和数据库操作顺序

1. Git 存档当前代码、核对工作树；记录页面/API/模型/生产消费者清单。
2. 备份现有 mowo_db，核对真实表结构与迁移账本，再决定迁移文件；隔离测试库只用于验证脚本，不替代旧业务数据。
3. 先实现服务端事实与事务，再接客户端和管理页；改 PB 时复跑原生产流程，不改变已设计的工艺规则。
4. 每个阶段提交 Git，并记录修改文件、迁移、接口、验证结果和剩余问题。
5. 真实收款前完成微信支付验签、主动查单、退款、对账与环境隔离。生产环境不得暴露模拟付款。

## 5. 必须验收的场景

| 场景 | 通过标准 |
|---|---|
| 同一结算重复点击、付款回调重复 | 仅一张 SO、正确明细和 PU，库存只预留/扣减一次 |
| 两件 SKU-1 加一件 SKU-2 | 两条明细、三个 PU、每件规格/动画版本准确，客户与后台一致 |
| 并发抢最后一件库存 | 至多一笔成功，不超卖；失败预留释放一次 |
| 支付结果未知/断网/迟到 | 顾客刷新可恢复同一交易，未确认前不显示已付款 |
| 管理员改 60→30 分钟 | 旧已付款订单时间不变，新付款订单按新值；到时不自动入批 |
| 同时取消和创建 PB | 只能成功一边，库存、SO、PU、PB 一致 |
| 付款后取消、退款失败 | 页面显示取消与退款失败两个事实，后台可定位重试/人工处理 |
| 售后申请、审核、退款 | 整张 SO 仅一份处理中申请；审核通过不等于退款成功 |
| 商品改价、下架、作品更新 | 老订单仍显示成交时标题、版本、规格和价格 |
| 换账号访问订单 ID | 读不到地址、作品、付款/售后凭证，也不能执行操作 |
| 历史数据与迁移 | 旧订单可查，生产原流程可跑，数据库可恢复 |
| 手机端、空状态、失败状态 | 页面文字、金额、按钮可读可点，失败可恢复 |

第一轮仅实现整单售后与清晰的整单发货边界。若将来要部分发货、逐件退款或多包裹，要先设计商品数量与包裹/退款的精确对应关系，再补接口和页面。
