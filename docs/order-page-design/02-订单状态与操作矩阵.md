# mowo 订单状态与操作矩阵

> 2026-10-14。状态名称为页面目标文案；开发时须建立服务端事实与展示映射，不能仅改 Vue 文本。

## 1. 五种并行事实

| 维度 | 首轮事实 | 用途 |
|---|---|---|
| 支付 | 未付、确认中、成功、失败、退款待处理/中/成功/失败 | 决定是否可建正式订单和展示资金 |
| 交易 | 待付款凭据、正式 SO、取消中/已取消 | 记录顾客购买的整笔交易 |
| 生产 | 未入批、已入 PB、制作完成 | 由现有 PU/PB 决定，不能由付款时间推测 |
| 物流 | 未发、已绑定运单、运输中、收货确认 | 和真实发货操作对应 |
| 售后 | 无、已申请、审核通过/拒绝、结案 | 不覆盖支付、生产和物流原记录 |

生产任务和批次只用于服务端计算“制作中”等对外状态；顾客接口不返回 PU/PB 编号、任务数组、工序或内部备注。

页面主状态的优先级：支付结果未知或顾客必须行动的事项 → 有处理中售后/异常 → 正常生产物流阶段 → 完成/取消。即使主状态为“售后处理中”，详情仍要保留“运输中”等并行事实。售后审核通过与退款渠道成功是两个事件。

## 2. 顾客状态与按钮

| 页面主状态 | 触发条件 | 主按钮/辅助操作 | 不能误写成 |
|---|---|---|---|
| 待付款 | PreOrder 有效且无可信支付成功 | 继续支付、取消 | 正式 SO 已生成 |
| 支付确认中 | 已发起，渠道最终结果未知 | 查询状态、联系客服 | 已付款或失败 |
| 付款失败 | 渠道确认失败 | 重新支付或重新结算，取决于凭据有效性 | 已取消 |
| 已过期 | 凭据过期且无成功支付 | 重新结算 | 旧单可继续支付 |
| 已付款 | 付款成功，SO/明细/PU 完整，未入 PB | 查看详情；允许时整单取消 | 制作中 |
| 制作中 | 订单任务实际入 PB，未全部完成 | 查看进度、整单售后/客服 | 可直接取消 |
| 待发货 | 所需生产完成，尚无有效发货 | 查看详情、客服 | 运输中 |
| 运输中 | 实际发货/有效运单已绑定 | 物流、合格时确认收货 | 已送达 |
| 已完成 | 顾客已确认收货或以后经正式规则完成 | 查看历史、有效期内售后 | 无法申请问题 |
| 已取消 | 取消事务成功 | 查看取消和退款进度 | 已退款 |
| 售后处理中 | 有未结案整单售后 | 查看申请 | 原支付/物流事实消失 |

列表筛选使用上述服务端状态汇总。一个订单只有一张卡；售后中可作为筛选标签，同时详情保留原生产/物流信息。待付款与正式订单由 PreOrder→SalesOrder 关联，支付成功后只保留对应 SO 卡。

## 3. 关键操作资格

| 操作 | 可做时 | 拒绝时页面说明 | 服务端最后一道检查 |
|---|---|---|---|
| 继续支付 | 凭据有效、金额和预留有效、尚未成功支付 | 已过期/结果确认中/已付款 | 幂等键和渠道查单，防二次付款 |
| 取消待付款 | 凭据有效、无可信成功支付 | 支付确认中请先查状态 | 关闭凭据和释放预留同一可靠流程 |
| 取消已付款 | SO 未入 PB，整单政策允许 | 已进入制作请走售后；支付/退款异常联系客服 | 与入 PB 互斥事务，库存只释放一次，退款独立跟踪 |
| 创建 PB | 已付款、尚未取消、已过最早排产时间、全部任务合格 | 后台显示每一项阻止原因 | 候选查询和最终写入都校验，旁路入口同样校验 |
| 确认收货 | 全部应发商品已真实发货，用户本人且未确认 | 尚未全部发货/已确认 | 归属、全件数、状态、重复请求 |
| 整单售后 | SO 本人、政策期内、无重复处理中申请 | 不符合条件时说明原因并给客服 | 归属、期限、申请次数、凭证权限 |
| 售后审核/退款 | 授权岗位，申请状态允许 | 需先处理前一步/资金未确认 | 审计记录、退款流水与重复防护 |

按钮是否显示由服务端资格返回；提交时再次计算。后台手工修改订单也要经过同一规则。不同用户拿到别人的 ID 应统一返回不可访问，不泄露订单是否存在。

## 4. 60 分钟规则的时间例子

订单甲在 14:20 付款，后台当时设置 60 分钟，因此最早 15:20 入批。14:40 管理员改为 30 分钟：甲仍是 15:20；14:41 才付款的订单乙最早 15:11。15:20 到来只解除“时间阻止”，不自动创建 PB。甲真正入 PB 时才从“已付款”变成“制作中”。如果甲在 15:25 申请取消，且同时生产员创建批次，数据库只能允许其中一个完成。

## 5. 异常优先处理

| 场景 | 页面 | 后台与数据 |
|---|---|---|
| 支付回调晚到/重复 | “确认中”直到最终可信结果；不让顾客盲目再付 | 查单、幂等建 SO；晚到成功须人工/自动补偿 |
| 收款成功但 SO 未建好 | 显示“付款已确认，订单处理中”，可查询与求助 | 告警与可重试任务，不可再扣款 |
| 库存不足或价格改变 | 显示具体哪条商品变化，回结算确认 | 释放失败预留，旧快照不被污染 |
| 部分 PU 生产异常 | 详情显示“制作处理中/遇到问题”，不宣称整单已完成 | 后台标异常责任和处理记录 |
| 已取消但退款未完成 | “已取消，退款待处理/中” | 独立资金流水，失败可定位 |
| 运单缺失或不可信 | “待发货/物流信息待更新” | 不伪造承运商和预计日期 |
| 售后被拒或退款失败 | 说明理由、时间及客服入口 | 保留申请与资金历史，不覆盖成成功 |

## 6. 暂不开放的状态

部分发货、部分退货/退款、多个包裹、换货、补款、促销调整、游客查单只有未来扩展位置。本轮若真实业务需要分件处理，应先补数据模型、金额/库存分摊、页面明细和测试，再启用按钮。成熟系统把付款、履约、退货分开管理的思路可参考 [支付](https://docs.medusajs.com/user-guide/orders/payments)、[履约](https://docs.medusajs.com/user-guide/orders/fulfillments)、[退货](https://docs.medusajs.com/resources/commerce-modules/order/return)。
