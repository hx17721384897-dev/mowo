# PROJECT_ENGINEERING_REVIEW_PLAN.md - 项目工程复盘计划

> 建立日期：2026-10-16
> 当前状态：RP1-A、RQ-001～RQ-004 与 RP1-B 已完成；下一步继续 RP1 全域入口和依赖图
> 性质：Vue 正式页面迁移与大部分旧页退役后的全栈工程复盘；最终人工验收、长期门禁和唯一旧编辑器的最终处置仍未完成。本计划本身不授权修改业务代码。

## 一、复盘目标

这次复盘不以“页面能打开”或“外观看起来一致”为完成标准，而是验证项目内部是否真正清晰、可靠、可维护：

1. 每项首发能力只有一套正式实现；退役能力在页面、路由、接口、任务和数据层都不可达。
2. Vue 页面、共享组件、状态、DTO 和 API 边界明确，不用复制页面或全局补丁维持功能。
3. 后端权限、校验、事务、幂等、状态变化、文件权限和审计日志能够共同证明业务正确。
4. 定制、资产、订单、库存和生产的状态机只有一个事实来源，失败后能够安全重试和恢复。
5. 数据库结构、迁移、历史数据、测试库与当前代码一致，重要约束不能只靠前端提示。
6. 验收覆盖从“空数据”到“创建、处理中、完成、失败、取消、删除和恢复”的完整生命周期。
7. 日志能回答谁在何时对什么对象做了什么、结果如何，同时不泄露密码、令牌和隐私内容。
8. 最终给正式程序员留下可追踪的架构图、问题清单、决策记录、测试证据和整改顺序。

## 二、当前边界与保护规则

- 用户正在单独调整订单界面及相关功能。订单代码只做依赖定位，不修改，也不在其稳定前给出最终正确性结论。
- 订单域由项目负责人明确宣布稳定，并记录稳定 commit 与日期后重新纳入：若 RP1 尚未结束，从 RP1 进入；若已完成 RP1，则补做 RP1 订单依赖图后进入 RP2、RP4、RP7。稳定前所有依赖订单语义的结论标记为“受订单改动阻塞”，其他领域可以形成局部结论。
- 每次开始工作先读取 Git 状态；任何已有在途改动均视为受保护内容，不覆盖、不格式化、不纳入复盘提交。
- RP0～RP7 默认是只读审计。允许新增复盘文档和与业务隔离的检查脚本；业务代码整改必须进入 RP8 后按已确认问题单独执行。
- 自动检查只证明它覆盖到的条件，不替代视觉、角色权限和真实流程验收；人工观察也不能替代 API、数据库和日志证据。
- 日常库 `mowo_db` 只允许只读核查和备份。迁移、造数、破坏性测试仅允许使用明确识别的测试库。
- 不以文件行数直接决定拆分，不为“架构漂亮”引入微服务；先按业务责任和事务边界判断。
- 新实现接管后删除被替代实现，不长期保留新旧两套入口、临时兼容分支或隐藏按钮。
- 发现 P0/P1 安全、越权、金额、库存或不可逆数据风险时立即汇报，不等待阶段结束。
- 每阶段完成后记录范围、证据、结论、未决问题和下一步，防止网络中断后重复工作。

## 三、问题分级与证据格式

### 严重级别

| 级别 | 定义 | 处置 |
|---|---|---|
| P0 | 可造成越权、敏感数据泄露、金额/库存严重错误、生产事故或不可恢复数据损坏 | 立即停止相关上线或测试路径 |
| P1 | 核心流程错误、状态无法恢复、幂等失效、审计缺失或高概率数据不一致 | 首发前必须整改 |
| P2 | 架构重复、维护风险、边界模糊、重要测试或可观测性不足 | 纳入明确里程碑 |
| P3 | 命名、局部结构、体验和低风险技术债 | 统一整理或延期 |

所有发现统一进入 `ENGINEERING_REVIEW_FINDINGS.md`。每条必须包含：编号、状态、级别、负责人、发现阶段、代码位置、客观事实、复现条件、业务影响、是否需要产品确认、关联决策/整改、建议改/删内容、验证方式、数据库影响、阻塞关系、风险接受人和到期日、修复 commit、验证证据与关闭日期。不能只写“建议优化”。

每个领域从七个维度评级为“未知、缺失、部分满足、满足”：正确性、数据一致性、安全、可维护性、可测试性、可观测性、可部署性。没有证据时只能标记未知。

## 四、阶段规划

### RP0：基线、范围和所有权冻结

核对 Git 状态、commit、在途改动、当前正式入口、服务启动方式、数据库用途、功能开关、首发范围、退役范围、文档时效、V6 未完成验收、订单重新纳入门槛和运行环境。旧文档只能作为线索，必须由当前代码和较新决策交叉确认。

同时建立邀请测试阶段的非功能目标基线：预期并发、日订单/上传量、单文件与单批上限、页面与 API 性能、错误率、RPO/RTO、浏览器范围、可访问性、日志期限、数据库/对象存储预警线。业务尚不能给出正式数值时标记“待确认”，不能伪造成生产 SLO。

RP0 优先标记并修正活动入口文档中的过期事实；历史验收快照只标注替代关系，不重写历史。数量快照必须带审计日期、Git commit、Schema 哈希、自动统计方式和最后迁移，避免把易变化数字继续写成永久事实。

交付：`ENGINEERING_REVIEW_BASELINE.md`，包括受保护文件、审计范围、测试环境、文档可信度和不可操作项。

通过门槛：不会把用户改动当旧代码删除；不会把历史规划当当前实现；正式、暂缓、退役能力都有唯一归类；所有未知非功能目标、文档冲突和受订单阻塞项均已显式登记。

### RP1：真实架构与依赖图

逐域追踪全部入口、调用者与完整链路：

`入口/调用者 -> Vue / 微信小程序 / 旧编辑器 / 回调 / Scheduler / CLI 与管理脚本 -> API 或领域服务 -> 事务/Prisma -> 数据库 -> OSS/短信/支付/文件系统 -> 领域流水/审计/指标/告警`

覆盖认证与账号、定制、动画与帧素材、联名商品、购物车与订单、库存、生产、私有文件、后台岗位权限。同步核查 Nginx 旧 URL 跳转、静态文件入口、数据修复/backfill、测试工具和规划中的外部回调，并区分“当前存在”和“未来边界”。识别循环依赖、跨域直接读写、双重事实来源和无法单测的耦合。

#### RP1-A：定制与动画专项事实调查

RP0 后先只读核实 RQ-001～RQ-003 涉及的页面、接口、表关系、删除行为、文件绑定、订单/生产引用和清理任务。将“当前行为、风险、推荐方案与备选代价”交给负责人确认后，再把决定纳入完整 RP1/RP2；不能把初步线索当审计结论。

#### RP1-B：运行拓扑与后台任务

专项核查 API 进程内 Scheduler 在单实例和多实例下是否重复执行，是否有数据库租约/唯一约束/leader，重启期间是否漏执行，单条失败是否拖垮整批，是否有重试、死信/人工关注、最近成功时间、积压、定时器关闭、优雅停机，以及数据库和外部依赖不可用时 liveness/readiness/降级是否符合实际依赖关系。

初步需要重点验证的线索包括：超大后端路由和 Vue 页面、重复弹窗/定时器/页面锁定逻辑、直接访问浏览器存储、全局 legacy 样式、后台人工筛帧仍交接旧编辑器、预览生成占位逻辑。它们只是审计触发器，不自动等于必须重写。

交付：`ARCHITECTURE_CURRENT_STATE.md`、页面/API/数据表/日志矩阵、依赖热点清单。

### RP2：产品语义与状态机复盘

为每个核心对象明确：谁创建、初态、允许的变化、操作角色、前置条件、副作用、失败补偿、终态、删除与保留规则。优先顺序：

1. 定制请求、动画草稿、正式动画资产、版本与文件处理任务；
2. 购物车、预订单、销售订单、支付事件与回调；
3. 商品、SKU、BOM、价格、可售状态、授权来源、下架与进行中订单；
4. 库存锁定、领用、退回检查、报废和补发；
5. 生产批次、帧图任务、物流、发货、签收、退款与售后；
6. 外部平台订单占位入口、异常订单与人工处置；
7. 联络留言、附件、通知与短信；
8. 账号注销与历史保留。

所有对象进入状态机总目录，但按“首发、受限占位、退役、未来规划”分层；非首发能力不为复盘而过度设计。

只把真正需要业务负责人决定的语义交给用户确认；代码事实先由审计确定。决策写入独立台账，不散落在聊天中。

交付：`DOMAIN_STATE_MACHINES.md` 和更新后的决策台账。

### RP3：Vue 架构复盘

检查页面是否只负责组合和交互，业务能力是否归入 feature/composable；共享组件是否保持统一但允许明确变体；DTO、金额、日期和错误是否集中转换；Pinia、URL、页面状态、会话存储和服务器状态是否各自有清晰所有权；刷新后是否以服务器事实恢复。

专项检查：重复导航/认证 UI、toast/modal、body 滚动锁、上传下载、轮询和定时器清理、Object URL 释放、旧全局 CSS 污染、响应式与无障碍、异常与空状态。

目标边界：

- `views`：路由级编排；
- `features`：单一业务能力；
- `components`：可复用展示与交互；
- `composables/stores`：生命周期与共享状态；
- `services/api`：通信、DTO 和统一错误；
- 不在多个页面复制同一业务规则。

### RP4：后端、领域、API 与事务复盘

检查超大路由是否混合协议、权限、业务和持久化；输入验证是否统一；客户端字段能否覆盖服务器事实；跨表写入是否同一事务；金额、库存、订单和文件操作是否持久化幂等；相同幂等键但不同请求内容是否拒绝；返回 DTO 是否存在隐私或内部字段泄露；关键变化是否和事务结果关联记录；并发更新是否由版本、约束或锁保护。

单列“事务外副作用与补偿”：覆盖 OSS 上传/复制/删除、本地文件与 DOCX/ZIP/打印文件生成、短信、支付调用和回调、通知与响应丢失。验证 DB 成功但外部失败、外部成功但 DB 失败、重试、孤立对象、删除失败、支付成功但落单失败等情况是否有可恢复状态、outbox/补偿任务或明确人工责任。

目标是边界清晰的模块化单体，不提前拆微服务。

### RP5：数据库、文件与生命周期复盘

核对 Prisma schema、迁移和查询是否一致；唯一约束、外键、索引和状态约束是否承担应有责任；软删除是否真的不可见且可审计；文件记录、对象存储、业务绑定和权限是否一致；草稿、上传、签名 URL、版本、订单引用和清理任务是否形成完整生命周期；孤立对象、失败删除和延迟回收是否可发现、可重试、可人工处理。

单独核查历史 `mowo_db` 到当前结构的恢复/复制边界，以及退役功能的数据表是否仍有消费者。迁移数量以 RP0 自动快照为准；禁止未经演练把当前迁移链直接重放到日常库。

### RP6：安全与隐私复盘

先建立威胁模型：资产、攻击者、信任边界、全部入口和滥用场景。再覆盖访问/刷新令牌、Cookie、CSRF、XSS、CORS、CSP、服务器端角色授权、对象级权限、私有文件、上传验证、恶意文件/压缩炸弹/图片解码、SSRF 与不可信 URL、接口限流、撞库、短信轰炸、批量导出、管理员高风险操作二次确认、注销、错误回显和日志脱敏。

供应链检查包括锁文件、依赖漏洞、Secret、SAST、许可证、依赖来源和第三方前端资源；备份检查加密与访问权限。记录已检查、未检查及工具限制，不为了形式引入不必要的安全平台。

访问令牌当前使用浏览器持久存储是重点威胁建模项，但不会在未分析小程序、跨页登录和 CSRF 取舍前盲目改写认证架构。

交付：`SECURITY_REVIEW.md`。P0/P1 问题发现即单独报告。

### RP7A：测试与质量门禁

每条核心流程按以下固定步骤验收：准备隔离环境 -> 记录空态基线 -> 创建数据 -> 执行中间状态 -> 完成或失败 -> 同时核对 UI/API/数据库/日志 -> 清理 -> 再确认无残留。

测试至少覆盖：空态、新建、编辑、刷新恢复、重复提交、并发、权限失败、网络失败、取消、删除、完成、历史查询、文件失效和清理。增加 API 契约、Vue/小程序消费者兼容、故障注入、数据库约束负向测试、空库迁移重放、历史副本演练、夹具泄漏、flaky 识别、前后端锁文件与 Node/PostgreSQL 版本矩阵。覆盖率只作为线索，不作为通过标准。

核查 CI 触发范围、分支保护与失败阻断；前端、后端、Prisma 迁移、跨端契约和恢复演练必须分别说明已有门禁与缺口。

### RP7B：日志、指标、告警与审计

检查请求 ID 是否贯穿 API、领域流水和外部调用；日志是否包含操作者、对象、前后状态、结果、失败原因、保留期限和访问权限，且不记录令牌、验证码和不必要隐私。同步检查存活/就绪、请求量/错误率/延迟、数据库连接和慢查询、Scheduler 最近成功时间与积压、文件失败、库存差异、支付/订单异常，以及告警接收人和升级路径。

### RP7C：性能、容量、部署、备份与灾难恢复

按 RP0 的邀请测试阈值检查图片/视频处理、懒加载、包体、长列表、主线程任务、Object URL、API 性能与容量预警；检查构建、Windows 启动脚本、部署回滚、备份加密、恢复演练、RPO/RTO 和依赖故障下的降级。

交付：`ENGINEERING_TEST_COVERAGE_MATRIX.md`，内含每一步假设数据和预期证据。

### RP8：整改路线图

审计完成后按风险而非页面顺序安排：

1. P0/P1 安全、金额、库存和数据一致性；
2. 状态机、事务、幂等、历史版本和失败恢复；
3. DTO、领域边界与权限；
4. 有特征测试保护的超大文件拆分；
5. 重复状态、组件和浏览器副作用；
6. legacy、死代码和过渡入口物理删除；
7. 日志、性能和运维完善。

交付：`REFACTOR_BACKLOG.md`。每项写明收益、风险、依赖、验收和删除项，不创建含糊的“以后优化”。

### RP9：分批整改与关闭

每个整改切片遵循：冻结现有业务语义 -> 补特征测试 -> 只改一个责任边界 -> 删除替代实现 -> 自动测试 -> 人工全流程 -> 数据库和日志核查 -> 清理测试数据 -> 更新记录。

关闭条件：P0/P1 清零，P2 有明确整改排期或由具名责任人接受风险；首发核心生命周期通过；正式入口没有未批准的旧版、临时版和重复实现；文档与代码事实一致。

P2 风险接受必须记录接受人、原因、有效期、重新评估的发布阶段、监控或临时缓解措施和到期复核日，不允许以“接受风险”永久搁置。

## 五、需要用户确认与无需用户确认的边界

需要确认：业务责任人、金额/退款规则、删除与保留、状态含义、角色权限、线上与线下边界、用户可见数据、失败后由谁处置。

不需要用户替代码作判断：调用关系、死代码事实、事务是否存在、接口是否越权、日志是否泄密、测试文件命名、内部文件拆分方式。

每轮只讨论一个业务主题，并提供：当前代码行为、架构影响、建议方案、备选方案和代价、需要确认的一句话。确认结果写入 `PROJECT_ENGINEERING_REVIEW_DECISIONS.md`。
