# 项目工程化与架构整理计划

> 版本：v1.0（2026-09-08）
>
> 本计划的近期目标是让哞屋达到**可安全进行邀请测试**的程度，而不是立即面向公众发布或接入真实线上支付。它是架构、质量、安全、文档和交接的共同执行计划；每一批次都必须可独立验证、提交和回退。

## 1. 已确认的产品目标

哞屋是一个将动画内容制作成实体动画机的商品与履约平台：

1. 用户可以浏览并购买联名动画商品，也可以提交素材制作私人动画。
2. 两类商品共享统一的购物车、交易准备、订单、库存与生产履约边界。
3. Web 是浏览、定制和生成付款前订单的主要入口；未来由微信小程序完成身份确认、支付、订单查询和通知。
4. 已付款订单进入统一的生产批次、打印、领料、扫码、装箱和发货流程。
5. 社区互动、线上创作者分红/提现、牛量和 CRMEB 不属于当前首发范围，必须保持关闭或明确标注为未开放。

## 2. 近期发布目标：邀请测试

邀请测试分两层，不能混为一谈。

| 阶段 | 用户和数据 | 允许的事 | 不允许的事 | 最低工程等级 |
|---|---|---|---|---|
| B0 内部演练 | 仅团队成员、合成数据 | 验证页面、订单、生产与后台操作 | 真实用户资料、真实收款、对外交付承诺 | R0 可重复开发 |
| B1 邀请测试 | 少量受邀真实用户；可能含手机号、素材、地址 | 验证定制、人工处理、订单确认与内部履约 | 真实线上支付、公开注册、社区/线上财务功能 | R1 可安全邀请 |

本计划以 **B1 可安全邀请测试** 为完成条件。若某次测试只用合成数据，可先在 B0 执行；一旦接收真实手机号、视频/图片、地址、简历或作品集，就必须按 B1 的安全要求处理。

## 3. 不把“换 Vue”当成架构整理的全部

Vue 3 + TypeScript 适合逐步承接购物车、结算、订单、定制编辑器和管理后台等复杂交互页面，但不是邀请测试的前置条件，也不应一次性重写整个网站。

当前阶段的优先级是：先固定接口契约、权限、数据与测试基线；再抽取公共 Web 能力；最后按页面价值和变更频率逐页迁移。静态介绍、协议、帮助页面可以继续保持静态 HTML，只要链接、样式、安全策略和部署方式受控。

企业级可维护性由以下能力共同决定：

- 清楚的产品范围与业务状态机。
- 可复现的数据库迁移、环境配置和依赖安装。
- 明确的后端领域边界、API 契约、权限和错误处理。
- 身份、私有文件、输入、日志和密钥的安全基线。
- 自动测试、持续集成、发布门禁与可回滚的 Git 历史。
- 备份、恢复、监控、告警和操作手册。
- 能让新程序员理解“现在真实如何运行”的文档，而非只保留历史规划。

## 4. 执行原则

### 4.1 先事实、后改动

- 当前代码、Prisma Schema、迁移、运行检查和实际前端消费者优先于旧规划文档。
- 业务规则未确认时，记录问题，不擅自把候选方案写进生产逻辑。
- 不为追求整洁而删除仍有消费者、数据迁移责任或追溯价值的旧代码。

### 4.2 小批次、可验证、可回退

每个批次必须：

1. 写明目标、范围、排除项与验收条件。
2. 在开始前保存 Git 基线；只在本批专用分支或清晰提交上工作。
3. 同步修改代码、测试和对应事实文档。
4. 运行自动检查与关键人工回归。
5. 用单一主题提交保存；通过后创建带日期和批次号的 Git tag。

禁止将无关的界面微调、格式化、临时目录、生成文件或另一批业务改动混进同一个提交。`.codex-tmp/` 与 `content-service/.codex-tmp/` 始终不作为产品代码提交。

### 4.3 先收口，再重写

先建立唯一的入口、唯一的服务端事实源和兼容期边界，再删除旧实现。对 Web 前端采用渐进迁移；对交易、库存、生产等高风险模块先统一状态与数据，再考虑代码形态。

## 5. 邀请测试完成标准

达到 B1 前，以下项目必须满足：

| 责任域 | B1 完成标准 |
|---|---|
| 范围 | 首页、定制、联名展示、人工处理、订单确认和内部生产入口的开放/关闭状态可由服务端与前端共同验证；未开放功能无可用入口。 |
| 环境 | 新电脑按文档可安装依赖、配置环境、从空库建立数据库并启动服务。开发、测试与未来生产的配置不混用。 |
| 数据库 | 当前 Schema 有可重放的迁移基线；空库迁移、种子（如需要）和核心冒烟检查有记录。 |
| 身份与权限 | 新旧认证入口有明确边界；普通用户、客服、生产、运营、负责人只能访问职责所需数据与动作。 |
| 文件与隐私 | 私有素材、头像、简历、作品集、订单文件按所有者、用途和岗位授权；上传有限制、临时读取可追踪；真实附件进入前具备扫描或隔离方案。 |
| Web 主流程 | 受邀用户可完成登录、浏览、定制或提交人工筛帧、查看自己的处理结果和订单状态；后台可完成对应人工操作。 |
| 测试 | 基础检查、关键 API 权限/契约测试，以及 Web 核心浏览器回归可重复运行。 |
| 运行 | 有健康检查、脱敏日志、最小错误告警方案、数据库与文件备份方案；故障时知道谁处理、如何暂停邀请测试。 |
| 告知 | 邀请测试文案、用户协议、隐私政策、定制可制作范围和人工处理时效不含未经确认的支付、退换、配送承诺。 |

真实支付、退款、正式微信支付、公开注册、容量扩展、线上分账和公开上线不属于本轮验收。

## 6. B1 前的实施批次

### P0：基线冻结与全量审计

**目的：** 建立可信起点，不在不清楚当前状态的情况下重构。

**工作：**

- 确认主仓库、小程序仓库、根目录依赖和临时文件的归属；补齐 `.gitignore`。
- 为当前可工作的版本创建清楚的 Git 提交与 tag；未提交工作按“界面、文档、业务”分开保存。
- 建立代码清单：页面、路由、端点、Prisma 模型、迁移、脚本、环境变量、第三方资源和小程序消费者。
- 分模块审查全部代码：基础设施与认证、交易与库存、生产、联名与创作者、内容与联络、Web、小程序、运维质量。
- 将“可删除”“需迁移”“保留但关闭”“当前唯一入口”列入差异台账，不直接删除。

**验收：** 有一份可追溯的审计报告和 P0/P1/P2 整改清单；任何后续批次都能说明影响的消费者、数据与接口。

### P1：工程地基与可重复开发

**目的：** 让项目不依赖某台开发电脑、根目录偶然存在的依赖或本地数据库历史状态。

**工作：**

- 收口各项目的 `package.json`、锁文件和启动说明；删除未声明的运行时依赖。
- 建立可从空 PostgreSQL 重放的 Prisma 迁移基线，验证迁移顺序、种子策略和数据升级路径。
- 统一 `.env.example`、配置校验和开发/测试/生产环境命名；扫描并轮换任何真实或疑似泄露的凭据。
- 建立 liveness/readiness、优雅停止和最小部署说明。
- 增加格式化、静态检查、依赖漏洞检查、Secret 扫描和最小 CI 基础。

**验收：** 独立目录可安装、空库可启动、基础检查可在 CI 中通过；配置错误会明确失败，不会悄悄采用弱默认值。

### P2：账户、权限、私有文件与安全基线

**目的：** 在邀请真实用户前保护账号、手机号、地址和素材。

**工作：**

- 收口旧版和新版认证入口，明确 Web 与小程序的会话策略、刷新、退出和设备撤销规则。
- 建立全路由权限矩阵；高风险动作统一记录操作者、目标、结果、请求 ID 和必要原因。
- 审查 Token 存储、XSS 输出点、CSP、CSRF、CORS、安全响应头、限流、输入校验与响应脱敏。
- 统一上传类型、大小、文件头、用途、归属、业务绑定、扫描状态、下载签名和生命周期。
- 完成账号注销、私有文件删除和失败人工处理的回归测试。

**验收：** 未授权访问、越权下载、过期会话、恶意输入和频率滥用均有自动反向测试；日志不保存密码、Token、验证码、完整地址或私有文件内容。

### P3：邀请测试主流程收口

**目的：** 让受邀用户与内部人员在不开启真实支付的前提下完成端到端业务演练。

**工作：**

- 明确并实施邀请测试允许的 Web 路径：联名浏览、私人定制、人工筛帧、确认结果、订单确认和订单查询。
- 确认联名商品、私人定制、动画资产、价格快照、购物车和订单之间的唯一服务端事实源。
- 清理断链、重复入口、旧页面的误导性按钮和未开放能力；对保留旧页设置明确归档或受控跳转。
- 为状态变化、异常提示、用户通知和后台人工操作定义最小验收场景。
- 不启用真实支付；模拟付款只允许开发/内部演练，并由环境开关强制限制。

**验收：** 一名受邀用户和一名内部处理人员能按人工测试清单完成核心流程；每一步有明确的失败提示、权限检查和可追踪记录。

### P4：交易、库存与生产的邀请测试安全线

**目的：** 虽不收真实款，也不能让测试订单破坏库存、生产或历史数据。

**工作：**

- 统一订单状态、库存预留/释放、生产单件任务和批次的写入入口；修复不稳定幂等键与跨入口副作用不一致。
- 将关键写操作放入明确的事务、唯一约束和补偿机制；建立重复提交、失败重试和并发测试。
- 收口生产批次、帧包、扫码、领料、配对、装箱和发货的状态机；禁止客户端信任式直接改状态。
- 将真实支付回调保持关闭；为后续微信支付预留验签、金额、商户、交易号和重放防护的契约。

**验收：** 同一测试操作重试不会重复扣库存、重复建单、重复发货或重复生成生产资料；测试数据可被明确识别和清理。

### P5：Web 前端渐进治理

**目的：** 降低页面间复制粘贴造成的接口、鉴权和样式漂移，同时不阻塞 B1。

**工作：**

- 抽取统一 API Client、会话恢复、错误展示、URL/HTML 安全输出、运行时 API Origin 和页面守卫。
- 建立唯一的页面清单、链接检查和共享设计 token；先修复现行入口，不承诺 `_legacy` 页面可运行。
- 选择购物车、结算、订单、定制与管理后台作为 Vue 迁移候选，先完成组件边界和契约，不做全站一次性重写。
- 为关键 Web 流程增加 Playwright 回归。

**验收：** 现行 API 页面不再各自维护 Token 和 API 地址；核心页面的链接、登录跳转和窄屏布局有自动检查。

### P6：邀请测试运行准备与试运行

**目的：** 让 B1 有可控的开启、暂停、观察和恢复能力。

**工作：**

- 建立测试环境、受邀名单、测试账号与测试数据隔离策略。
- 建立数据库备份、文件存储备份/生命周期、恢复演练和最小运行手册。
- 部署错误收集、关键操作告警和访问日志；明确负责人、暂停条件和问题响应流程。
- 按 B1 验收矩阵进行内部演练，修复阻断项后再邀请第一批用户。

**验收：** 有经过演练的备份恢复记录、已知问题清单、邀请话术、问题反馈入口与暂停方案；负责人明确批准 B1 开启。

## 7. 本轮明确不做

- 不进行全站一次性 Vue 重写。
- 不接入真实微信支付、退款、提现或第三方商城。
- 不开放社区、评论、点赞、关注、公开注册或线上创作者结算。
- 不在没有容量数据前过早拆微服务、引入复杂中间件或购买固定规格服务器。
- 不删除旧代码或历史文档，除非已确认没有消费者、数据兼容和追溯价值，并有独立提交记录。

## 8. Git 与回退约定

| 时点 | 必须动作 |
|---|---|
| 开始一个批次前 | 工作区清洁或未提交工作已分类；记录基线提交；创建批次分支。 |
| 每个独立改动完成后 | 运行对应检查；以单一主题提交，不夹带格式化和无关文件。 |
| 一个批次验收通过后 | 更新事实文档、差异台账和验收记录；合并或保留清晰提交；创建带批次号的 tag。 |
| 出现回归或需求变更时 | 优先回退到最近可验证 tag 或提交；不要用覆盖式修改掩盖问题。 |

建议 tag 形式：`b1-p0-baseline-YYYYMMDD`、`b1-p1-foundation-YYYYMMDD`。每个 tag 应能独立说明已知风险与测试结果。

## 10. 下一步

从 P0 开始，不直接进入代码重构。P0 首先确认当前所有未提交改动的归属，建立基线 tag，并输出按模块划分的代码审计清单；完成后再依优先级进入 P1。
