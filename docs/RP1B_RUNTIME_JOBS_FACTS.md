## 1. 当前运行拓扑

当前后端是一个 Fastify API 进程：连接 PostgreSQL，按环境选择本地私有文件或阿里云 OSS，并在 HTTP 监听成功后直接调用 `startScheduler(fastify)`。仓库没有独立 Worker、持久任务队列、数据库任务租约、Leader 选举或生产部署清单。

这意味着：

- 每个 API 实例都会启动完整 Scheduler；两个实例会同时扫描同一批数据。
- 所有 API 实例停止时，定时任务也全部停止。
- 重启后只有明确“启动即执行”的任务会补扫；固定时刻任务不一定补齐停机窗口。
- Scheduler 的 timeout/interval 句柄没有保存，也没有注册 Fastify `onClose` 停止钩子。
- 代码没有 SIGTERM/SIGINT 处理；Prisma 只在 Fastify 被正常关闭时断开。
- 根路径只返回静态成功消息，不检查数据库、存储和后台任务，不是 readiness。

## 2. 后台任务逐项矩阵

| 任务 | 频率与启动行为 | 并发/幂等保护 | 重启与失败事实 | 结论 |
|---|---|---|---|---|
| 库存日快照 | 每天 00:00；启动不补跑 | `(skuId, snapshotDate)` 唯一且 upsert | 单个 SKU 出错会中断余下 SKU；错过零点需等下一次，没有运行记录 | 数据重复风险较低，完整性与补跑不可证明 |
| SKU 授权到期 | 启动立即执行，之后每天 08:00 | 按当前状态条件批量更新 | 失败只写进程日志，下次启动/次日再试 | 重复执行基本安全，但不可观测 |
| 预订单过期释放 | 启动立即执行，每 2 分钟 | 事务内按 `pending_payment` 抢占；库存流水有唯一幂等键 | 全量顺序扫描，无分页；一条损坏快照抛错会终止整批 | 抢占可靠，但单条坏数据可阻塞后续释放，P1 |
| 商品草稿过期 | 每天 03:00；启动不补跑 | 无任务租约；最终批量写 `removed` | 与定制请求清理使用不同对象和时钟 | 已归入 ERF-005 |
| 14 天自动收货 | 启动立即执行，每小时 | 查询 `shipped` 后按 ID 更新，无条件抢占；单条错误被隔离 | 多实例可重复写同一状态；没有业务事件、运行记录或积压指标 | 当前副作用有限，但不满足多实例任务标准 |
| 废弃头像清理 | 启动立即执行，默认每小时 | 文件状态、更新时间和绑定关系组成乐观抢占 | `DELETING/DELETE_FAILED` 可在 15 分钟后重试 | 单文件并发保护较完整 |
| 定制上传/草稿清理 | 启动立即执行，默认每小时 | 未绑定文件与请求都有状态抢占；删除失败可重试 | 商品草稿另有一套每日任务 | 文件级保护较完整，领域生命周期仍分裂 |
| 账号注销 | 启动立即执行，默认每分钟 | `status + updatedAt` 抢占；普通失败转 `FAILED` 重试 | 进程在抢占后崩溃会遗留 `PROCESSING`；扫描和后台操作均不恢复该状态 | 不可恢复卡死，P1 |
| 限流记录清理 | 启动立即执行，之后每天 | 条件 `deleteMany` | 失败只写进程日志，下次启动/次日再试 | 重复执行基本安全 |

## 3. 已确认的关键风险

### 3.1 账号注销可能永久停在 PROCESSING

任务先将 `REQUESTED/FAILED` 抢占为 `PROCESSING`，再删除文件并匿名化资料。自动扫描只选择 `REQUESTED` 和 `FAILED`；后台人工重试只允许 `FAILED` 和 `MANUAL_REVIEW`，暂停也不允许 `PROCESSING`。如果进程在抢占后退出、主机重启或被强制终止，该任务没有租约到期或 stale recovery，用户数据删除不会继续，也没有可用的后台恢复按钮。

### 3.2 一条异常预订单可中断整批过期释放

扫描先取出所有过期 `pending_payment` 预订单，再在一个外层 `try` 中逐条调用关闭事务。关闭函数读取并验证冻结快照；历史缺失或损坏快照会抛错，外层立即结束本轮，后续记录不再处理。查询没有稳定排序、分页、单条隔离或异常任务表，可能反复遇到同一坏记录，使后续库存继续被锁定。

订单域仍在负责人单独修改，因此这里只确认当前 Scheduler 的通用失败传播事实；最终订单修复设计和正确性结论要等订单稳定 commit 后重新核对。

### 3.3 Scheduler 没有可证明的运行所有权与健康状态

当前依靠各任务内部条件更新降低重复副作用，但没有统一保证“同一任务同一时间只有一个执行者”。也没有任务名称、run ID、计划时间、开始/结束时间、处理数量、失败对象、最近成功时间、下次重试、积压和告警责任人。进程日志无法证明某日库存快照是否完整，也不能让 readiness 拒绝一个数据库已断开或后台任务长期失效的实例。

## 4. 已存在的正向基础

- 预订单状态抢占与库存释放在同一事务，库存流水有唯一幂等键。
- 私有文件清理使用状态、更新时间与绑定关系抢占，失败状态可以重新处理。
- 定制请求过期清理使用 `EXPIRING` 中间态，进程重启后可重新拾取。
- 账号注销对正常异常有失败次数、重试时间和人工关注状态，缺口集中在进程崩溃留下的 `PROCESSING`。
- 库存日快照有日期唯一约束，授权和限流清理使用可重复的条件写入。

## 5. RP8 前的建议方向

1. 邀请测试阶段若仍用进程内任务，部署必须显式限制为单 Scheduler 实例；API 扩容不能自动复制任务执行者。
2. 为每类关键任务建立数据库租约或独立 Worker；执行使用稳定 run key，过期租约可被安全接管。
3. 账号注销增加 `PROCESSING` 租约截止时间与恢复策略，后台允许对明确过期的处理任务执行受审计恢复。
4. 预订单扫描使用有界分页和逐条错误隔离；异常记录进入人工关注队列，但不得阻塞其他库存释放。
5. 增加任务运行表或等价指标，至少记录最近成功、最近失败、处理数、积压和失败对象；对注销、预订单、库存快照建立告警。
6. 增加独立 liveness/readiness、SIGTERM/SIGINT 优雅停止和 Scheduler 停止/等待在途任务机制。
7. 库存快照按业务日期补跑并验证 SKU 覆盖率，不把 upsert 成功等同于整日快照完整。

这些是后续整改方向，不授权在 RP1 阶段直接修改业务代码或部署结构。
