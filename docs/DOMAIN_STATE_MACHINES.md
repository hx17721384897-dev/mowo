## 1. 对象责任

| 对象 | 唯一责任 | 不是它的责任 |
|---|---|---|
| `CustomizationRequest` | 一次定制过程、当前处理阶段和追加式时间线 | 不是购物车、订单或可复用动画本体 |
| `CustomProduct` | 本次购买所需的定制商品工作记录，连接动画版本与购买选项 | 不是正式动画资产，也不应独立决定请求生命周期 |
| `AnimationAsset` | 用户可管理、修改和复用的动画主资产 | 不代表某次购买、SKU 或生产结果 |
| `AnimationAssetVersion` | 已确认且不可覆盖的帧版本 | 不承担草稿状态；修改必须新增版本 |
| `CustomizationFrameSelection` | 员工每次正式提交给用户的筛帧结果版本 | 不覆盖旧结果，不直接代表用户已接受 |
| `PrivateFile` | 文件所有权、用途、校验、业务绑定与物理删除状态 | `linkedResource` 不是登录状态，也不能代替长期业务引用关系 |

跨对象不变量：

1. 请求是定制过程的生命周期主对象；商品草稿不能单独结束或复活该过程。
2. 正式动画资产只能由用户确认动作产生；自助路线在选择 SKU 确认时产生，人工路线在接受筛帧结果时产生。
3. 动画版本不可覆盖；订单和生产只引用确定版本，不读取资产“当前版本”代替历史快照。
4. 删除资产库卡片不能删除订单、生产、历史请求或它们固定的版本。
5. 文件物理删除必须在数据库状态提交后异步、幂等、可重试，并在删除前重新检查引用。

## 2. 定制请求状态机

### 2.1 自助定制当前可达流程

```text
DRAFT
  ├─ 用户确认 SKU ──────────────> CONFIRMED
  ├─ 到期任务抢占 ──────────────> EXPIRING ──清理成功──> CLOSED
  └─ 用户删除（已确认目标，当前未实现）──────────────> CLOSED
```

| 状态 | 业务含义 | 用户可见位置 | 允许动作 | 禁止/约束 |
|---|---|---|---|---|
| `DRAFT` | 尚未提交的自助定制过程 | 我的定制；对应动画草稿可在我的动画显示 | 继续编辑、选择 SKU、删除 | 7 天后过期；不能被订单/生产引用 |
| `EXPIRING` | 清理任务已抢占，正在回收临时文件 | 我的定制 | 等待任务恢复/完成 | 用户不能继续提交；失败后应由任务重试 |
| `CONFIRMED` | 定制内容与购买选项已固定，可进入购物车/结算 | 我的定制“已结束” | 加购由商品记录承接 | 不表示已付款、已下单或已生产 |
| `CLOSED` | 草稿已删除或过期，过程不可继续 | 我的定制“已结束” | 只读历史 | 必须记录关闭原因；不得用同一记录恢复购买 |

`CONFIRMED` 的名称容易与“订单已确认”混淆。本状态只结束定制过程并开放购买资格，不证明交易发生；后续 DTO 和文案必须明确这一层边界。

### 2.2 人工筛帧当前可达流程

```text
SUBMITTED ──员工领取──> REVIEWING ──提交筛帧──> OPTIONS_READY
    ^                      │                         ├─用户要求调整──> SUBMITTED
    └────员工退回任务池────┘                         └─用户接受──────> FRAME_ACCEPTED
                                                                       └─选择 SKU──> CONFIRMED
```

| 状态 | 当前含义 | 当前进入方式 | 当前退出方式 |
|---|---|---|---|
| `SUBMITTED` | 等待工作人员领取或重新处理 | 用户首次提交、员工退回、用户要求调整 | 员工领取 |
| `REVIEWING` | 某位员工持有编辑锁并筛帧 | 领取或领取下一条 | 提交结果、退回任务池；锁过期可被重新领取 |
| `OPTIONS_READY` | 最新筛帧结果等待用户决定 | 员工提交结果 | 用户接受或要求调整 |
| `FRAME_ACCEPTED` | 用户已接受筛帧，资产 V1 已创建，等待选 SKU | 用户接受最新 selection | 用户选择 SKU |
| `CONFIRMED` | 定制内容与 SKU 已固定，可进入购买 | 选择 SKU | 定制过程只读结束 |

### 2.3 已声明但当前不可达的状态

| 状态 | 出现位置 | 当前事实 | RP2 结论 |
|---|---|---|---|
| `NEEDS_SUPPLEMENT` | 后端标签、后台状态列表、Vue 类型与筛选 | 没有写入接口、用户补充入口或恢复转换 | 若 RQ-005 确认保留，必须实现完整双向流程；否则删除全部声明 |
| `STYLE_SELECTED` | 后端标签、Vue 类型和若干兼容 guard | 选择 SKU 接口直接从 `FRAME_ACCEPTED` 写入 `CONFIRMED` | 当前流程没有独立“选款后再最终确认”步骤，建议从首发状态词表删除 |
| `UNAVAILABLE` | 后端标签、后台状态列表、Vue 类型与筛选 | 没有写入接口、原因字段或责任动作 | 若 RQ-005 确认保留，作为带公开原因的终态实现；否则删除声明 |

状态字段目前是自由字符串，各层分别维护列表。RP3～RP5 必须决定共享契约与数据库约束，防止继续产生“代码能写、客户端不认识”或“客户端展示、服务端永远到不了”的状态。

## 3. 商品工作记录状态机

### 3.1 当前可达状态

```text
自助：draft ──加入购物车──> in_cart ──付款成功──> ordered
           └─手动/定时删除──> removed

人工：reviewing ──用户接受后仍保持 reviewing──> 加入购物车时 in_cart ──付款成功──> ordered
```

| 状态 | 当前写入来源 | 语义评价 |
|---|---|---|
| `draft` | 自助编辑器、动画复用 | 可编辑且尚未购买 |
| `reviewing` | 员工提交筛帧结果 | 实际表示“人工结果等待用户接受”，但 Schema 注释和 Vue 草稿契约没有该状态 |
| `in_cart` | 加入购物车 | 购买工作记录已被购物车引用；移出购物车后的回退规则待交易域补审 |
| `ordered` | 支付成功路径 | 已被订单固定，不可按草稿删除 |
| `removed` | 手动删除或商品草稿任务 | 不应再提交、加购或复活 |

已确认目标：

- `reviewing` 记录不属于“我的动画”草稿，接受前只在“我的定制”展示。
- 用户接受筛帧结果后，应把商品工作记录归入统一的可购买状态，同时由正式 `AnimationAsset` 在“我的动画”展示；不能长期保留含义已经过期的 `reviewing`。
- 删除未提交草稿必须在同一事务关闭关联 `DRAFT` 请求；当前只写 `removed` 的行为仍属于 `ERF-005`。
- `in_cart -> draft`、购物车失效和预订单取消后的回退要等订单稳定后与交易状态机一起确定。

## 4. 动画资产与版本状态机

### 4.1 动画主资产

```text
ACTIVE ──用户从资产库删除──> USER_DELETED
   └────后台归档──────────> ARCHIVED（当前只存在字段，归档操作待后续消费者核查）
```

| 状态 | 规则 |
|---|---|
| `ACTIVE` | 私人资产可重命名、追加版本和复用；联名资产按运营与授权规则使用 |
| `USER_DELETED` | 仅从私人资产库隐藏并禁止未来修改/复用；历史引用和版本保留 |
| `ARCHIVED` | 设计为后台归档，但本切片未发现正式转换入口；在确认消费者前不能当作已实现能力 |

普通用户不能删除联名资产。`assetType`、`collabStatus`、`authorizationStatus` 是不同维度，不能混入资产生命周期状态；联名上/下架将在后续 RP2 切片单独建模。

### 4.2 动画版本

`AnimationAssetVersion` 没有可变业务状态，创建即成为不可变历史：

- `(assetId, versionNo)` 唯一；
- `sourceKey` 唯一，防止同一确认动作重复创建版本；
- 修改动画只能追加 V2/V3；
- 复购固定现有版本，不复制文件、不生成伪版本；
- 订单、生产渲染和生产文件均应引用明确 `versionId`。

## 5. 筛帧结果状态机

```text
SUBMITTED
  ├─用户接受────────> ACCEPTED
  ├─用户要求调整────> REVISION_REQUESTED
  └─员工提交更新版本> REPLACED
```

- 每次正式提交追加 `version`，不覆盖旧结果。
- 同一请求同时最多一个待用户处理的 `SUBMITTED` 结果。
- 只有 `ACCEPTED` 结果可以成为人工动画资产 V1 的来源。
- `internalNote` 永远只属于员工 DTO；用户只能看到公开说明。

## 6. 私有文件状态与业务绑定

```text
PENDING ──上传校验成功──> READY ──清理抢占──> DELETING ──成功──> DELETED
   └─────校验失败────────> REJECTED ──到期清理──> DELETING
                                      └─物理删除失败──> DELETE_FAILED ──重试──> DELETING
```

文件还具有独立的业务绑定维度：

- 未绑定上传：登录用户已经上传，但没有关联请求、商品草稿或筛帧结果；24 小时后回收。
- 已绑定草稿：关联 `CUSTOMIZATION_REQUEST`、`CUSTOM_PRODUCT` 或筛帧结果；当前按请求生命周期保留 7 天。
- 已进入正式版本：对象键被动画版本、订单或生产引用；不能仅因原绑定对象删除而物理回收。

RP5 必须补证：动画版本长期引用是否有正式文件所有权/引用记录、账号注销如何保留订单所需版本、失败删除和孤立对象如何被发现。

## 7. 页面职责与状态投影

| 页面 | 应显示 | 不应承担 |
|---|---|---|
| 我的定制 | 所有定制请求、公开时间线、用户当前可执行动作 | 不复制动画版本或订单状态 |
| 我的动画 | 未提交且由用户可继续编辑的动画草稿；ACTIVE 正式资产 | 不显示员工处理中的 `reviewing` 候选，不展示已删除资产 |
| 购物车/订单 | 固定商品、SKU、动画版本、价格和数量 | 不从当前草稿或资产“最新版本”恢复历史事实 |
| 后台人工筛帧 | 领取、锁、草稿保存、正式追加 selection、公开说明/内部备注 | 不直接修改用户订单或覆盖旧 selection |

## 10. 联名作品、商品与销售规格的责任

| 对象/字段 | 当前责任 | RP2 边界 |
|---|---|---|
| `CollabWork.status` | `approved` 表示已经完成线下合作与权利确认；`pending/rejected` 是旧在线审核词汇 | 首发不恢复线上审核；后续应改成符合线下确认事实的命名或受控导入状态 |
| `CollabWork.shelfStatus` | `on_sale / suspended / off_shelf` | 应成为唯一货架状态事实 |
| `CollabWork.isOnShelf` | 公开查询的第二个开关 | 当前形成双重事实来源；目标应由状态派生或受数据库约束 |
| `CollabSaleSku` | 一项联名商品可销售的真实 SKU、最终价格、履约方式与交期 | 只控制未来销售，不覆盖历史成交快照 |
| `MachineModelSku.isActive` / Model `isActive` | 基础硬件规格是否可售 | 任一停用都会使对应联名规格停止新销售 |
| `AnimationAssetVersion` | 联名商品当前用于销售和生产的确定动画版本 | 已成交订单必须固定版本；换版不能回写历史订单 |
| 购物车/预订单/销售订单 | 从当前报价到成交快照的不同阶段 | 货架操作只能直接控制未来销售；资金/生产处置必须有独立动作 |

线上只管理商品、销售、库存和履约。创作者合作确认、合同、合作暂停和结算继续在线下完成；后台“暂停销售”不能被解释为线上暂停创作者合作关系。

## 11. 当前公开销售条件

一项联名商品只有同时满足以下条件才会出现在公开列表、详情、加购和新结算中：

1. `CollabWork.status = approved`；
2. `isOnShelf = true`；
3. `shelfStatus = on_sale`；
4. 已关联正式动画资产与版本；
5. 有正式商品封面；
6. 至少一项 `CollabSaleSku.isEnabled = true`；
7. 对应基础 SKU 与机型均启用；
8. 动画基础帧数与 SKU 目标帧数兼容；
9. 价格、履约方式和交期满足服务端校验。

公开接口使用字段白名单，历史买家不能通过商品详情读取已下架联名的原始帧。成交后需要的标题、价格、SKU、动画版本、交期和履约方式由订单快照承担。

## 12. 联名货架当前状态机

当前代码意图可以表示为：

```text
OFF_SHELF ──上架检查通过──> ON_SALE ──普通运营暂停──> SUSPENDED
    ^                           │                         │
    └──────强制下架─────────────┘                         └─恢复检查通过──> ON_SALE
```

规范组合应当只有三种：

| 业务状态 | `shelfStatus` | `isOnShelf` | 新销售 | 允许下一步 |
|---|---|---:|---|---|
| 销售中 | `on_sale` | `true` | 允许 | 暂停、强制下架 |
| 暂停销售 | `suspended` | `false` | 拒绝 | 恢复、强制下架 |
| 已下架 | `off_shelf` | `false` | 拒绝 | 重新上架 |

当前实现没有强制这三组组合：Schema 默认会产生 `on_sale + false`；暂停接口还可从 `off_shelf` 进入；首次“上架”前端实际调用只接受 `off_shelf` 的重新上架接口。因此货架有两个事实来源并可能卡在“后台显示销售中、公开不可见、也无法首次上架”的状态，已登记 `ERF-016`。

目标状态机要求：

- 使用单一货架状态，公开可见性由其派生；若过渡期保留布尔字段，数据库约束必须保证组合一致。
- 所有转换使用当前状态条件更新，重复请求幂等，非法来源明确拒绝。
- 初次上架与重新上架可以共享内部服务，但外部命令和审计要区分。
- 恢复/重新上架每次重新执行销售准备检查；暂停/下架不能自动清空商品资料、销售 SKU、库存或历史订单。

## 13. 下架对交易阶段的当前影响

| 交易阶段 | 当前代码行为 | 业务规则状态 |
|---|---|---|
| 尚未加入购物车 | 公开列表/详情立即不可见，不能加购 | 已明确 |
| 已在购物车 | 再次读取时当前报价解析失败，条目标记 `invalid`，不能新结算 | 已明确 |
| 已创建 `pending_payment` 预订单 | 保留 10 分钟快照和库存预留；下架不主动取消，当前仍可付款 | RQ-006 已确认：普通暂停保留原付款窗口，强制下架必须取消并释放预留 |
| 已付款 | 销售订单和商品快照不回读货架，继续进入履约 | 建议保持；停止履约必须另走订单动作 |
| 生产中/已发货 | 不受货架字段直接影响 | 建议保持；紧急召回属于独立流程 |
| 售后/历史订单 | 订单记录继续存在 | 已确认；只能看成交和售后快照，不公开原帧 |

货架操作当前不会查询、记录或通知受影响预订单/正式订单；这使运营人员无法从操作结果判断影响范围。该业务缺口登记为 `ERF-017`，产品规则已由 RQ-006 确认，等待订单代码稳定后实施审计。

## 14. 货架审计与商品编辑边界

- 商品工作区保存会记录 `COLLAB_PRODUCT` 的前后内容和销售 SKU，产品历史页可以查询。
- 暂停、恢复、强制下架和重新上架只依赖全局通用操作日志；没有设置目标、前后状态和受影响交易数量，因此不会出现在商品历史中，登记为 `ERF-018`。
- 强制下架保存内部原因和给创作者的通知内容，但页面仍写“创作者修改后重新提交”，与首发线下合作边界不一致；后续应改成“线下确认后由运营重新上架”。
- 当前销售中的商品可以直接修改价格、SKU、交期和素材。是否要求“销售关键字段先暂停再编辑、显式发布”将在 RQ-006 后作为独立主题确认，不能与紧急下架混为一个按钮。

## 15. RP2-B 已确认规则

负责人已于 2026-10-20 确认 `RQ-006`：

1. `SUSPENDED` 用于普通运营暂停：关闭新销售，但暂停前已创建的 10 分钟预订单可在原有效期完成付款。
2. `OFF_SHELF` 用于权利、合规或明确停售：关闭新销售，并取消所有未付款预订单、释放预留库存。
3. 已付款、生产中、已发货、售后和历史订单继续按成交快照履行；货架操作本身不自动退款、停产或召回。
4. 若确需停止已付款订单，另走有权限、原因、顾客通知、退款/库存副作用和审计的订单处置流程。
5. 下架不删除商品、动画版本、销售配置、库存或历史；重新上架必须重新通过准备检查。

这些规则已经成为后续设计和验收依据，但尚未授权本阶段修改业务代码；订单代码稳定后还要补审具体事务、幂等和并发。

## 16. RP2-C 在售商品编辑的当前事实

当前 `PUT /api/admin/collab/:id/product-workspace` 同时承担“保存编辑”和“写入正式商品”两种责任：

- 不存在独立草稿、发布版本或生效时间；保存成功后公开接口立即读取新值。
- 在 `on_sale`、`suspended` 和 `off_shelf` 状态均可保存，服务端只要求作品已完成线下合作确认。
- 一次保存会在事务内同时修改展示内容和 `CollabSaleSku`，但事务提交后没有独立发布事件或不可变版本号。
- 已删除的销售 SKU 会被直接删除；价格、履约方式、交期和启用状态原地更新。
- 商品历史记录保存操作摘要，通用日志可保存前后数据，但商品历史 API 只返回动作、操作者和时间，不能用于恢复某一已发布版本。
- 请求不携带 `version`/`updatedAt` 条件，两个管理员基于旧页面保存时采用最后写入覆盖。

## 17. 编辑后对顾客对象的实际影响

| 对象 | 当前影响 |
|---|---|
| 公开列表与详情 | 下一次请求立即看到保存后的标题、封面、媒体、价格、SKU、交期和履约方式 |
| 已加购物车 | 下次读取时重新解析当前商品；价格变化进入 `price_changed`，SKU 不再可售则进入 `invalid` |
| 购物车中的交期/履约变化 | 没有专门状态或确认步骤；结算时会使用最新值生成快照 |
| 已创建待付款订单 | 使用创建时冻结的商品、价格、动画版本、SKU、交期和履约快照，不随编辑变化 |
| 已付款及生产订单 | 继续使用成交快照，不回读当前商品工作区 |

因此，当前系统已经具备“交易快照不被后改”的一部分正确边界，但没有“商品草稿与正式发布”边界，也没有统一表达价格以外的购物车关键变化。

## 18. RP2-C 已确认目标状态机

建议的商品发布状态不替代货架状态：

```text
已发布版本 N ──创建/继续编辑──> 草稿
草稿 ──保存──> 草稿
草稿 ──校验与显式发布──> 已发布版本 N+1
草稿 ──放弃──> 回到已发布版本 N
```

- `on_sale/suspended/off_shelf` 回答“当前是否允许成交”；草稿/已发布版本回答“顾客看到哪一组完整商品资料”，两者不得混成一个字段。
- 保存草稿不改变线上；发布时对内容、SKU、价格、履约和交期做一次完整校验并原子切换。
- 每次发布形成可审计、可比较的不可变版本，并以版本号/条件更新阻止过期页面覆盖新修改。
- 价格、SKU、履约方式或交期发生变化时，现有购物车统一进入“商品信息已变化”并要求重新确认；纯展示字段变化不阻断结算。
- 待付款、已付款及生产对象继续遵守创建时快照，停售按 RQ-006 处理。

以上规则已经由负责人通过 `RQ-007` 确认，作为后续 RP4/RP5 设计和 RP8 实施验收依据；本阶段仍不修改业务代码或数据库。

## 19. RP2-D 库存事实来源与数量守恒

当前标准材料包库存并非只有一张表：

| 事实 | 当前记录 | 责任 |
|---|---|---|
| SKU 汇总实物数 | `SkuInventory.currentStock` | 购物车可售判断和库存总览 |
| 订单锁定数 | `SkuInventory.reservedStock` | 待付款及已付款待生产订单占用 |
| 组装批次余量/预留 | `KitAssemblyBatch.availableQty/reservedQty` | 现场 FIFO 来源和生产领料 |
| 箱内数量/预留 | `KitContainer.currentQty/reservedQty` | 实体箱码来源 |
| 批次领料 | `ProductionMaterialPick` | 领取、剩余、消耗和退回 |
| 库存流水 | `InventoryLog` 及材料/批次流水 | 追溯数量变化 |

目标守恒关系应为：

```text
可售 = 汇总实物数 - 订单锁定数
批次可领 = Σ(组装批次余量 - 组装批次预留)
箱码可领 = 箱内数量 - 箱内预留
```

同一套材料包进入逐件配对时，必须在一个事务里同时减少汇总实物数和该订单的锁定数，并减少具体组装批次/箱码余量与预留；否则各层事实会分叉。

## 20. 结算锁定到生产消耗的当前状态机

```text
可售
  └─ 创建待付款订单 ─> 订单锁定
       ├─ 超时/取消/付款失败 ─> 可售
       └─ 付款成功 ─> 已付款锁定
            ├─ 未入批取消 ─> 可售
            └─ 批次领料 ─> 具体 KB/BX 预留
                 ├─ 未配对退料 ─> 释放 KB/BX 预留
                 └─ 逐件配对 ─> 正式消耗
```

当前正确部分：待付款创建使用条件 SQL 防超卖；取消/过期与订单状态在事务中释放；具体组装批次和箱码领用、退回、配对均使用条件更新；帧包重复配对不会重复扣减。

当前断链：付款后 `reservedStock` 正确保留为已付款待生产锁定，但逐件配对只减少 `currentStock`，没有减少 `reservedStock`。因此每完成一件生产，汇总可售数会额外减少一件，已完成订单仍永久显示为锁定。登记为 `ERF-021`。

此外，通用释放函数和若干旧四态库存转换使用 `GREATEST(0, ...)` 把不足直接截为零，而不是拒绝数量不一致；手工调减只校验总数不会小于零，没有保证总数仍覆盖锁定/在制量。它们可能把账实异常伪装成成功，登记为 `ERF-022`。

## 21. 生产领料与重复请求

- 领料会校验批次仍活动、待领生产件数量和具体 `KB/BX` 可用量，并在事务中增加批次/箱码预留。
- 退料只允许尚未配对的剩余数量，并同步恢复生产件状态及减少具体预留。
- 配对以帧包对应生产件为唯一事实，重复扫描返回已有结果，不重复消耗。
- 领料与退料接口没有持久化客户端请求编号；相同网络请求被重复送达时，只要批次仍有其他待领件/可退件，就可能形成第二次真实领料或退料，而不是恢复第一次结果。登记为 `ERF-025`。

## 22. 退回检查当前状态机

```text
售后批准
  └─ 仓库收货 ─> QUARANTINED
       └─ 原子认领 ─> INSPECTING
            ├─ 未拆封完整 ─> INSPECTED + 新 KR 批次 + NEW 汇总库存
            └─ 已拆封 ─> INSPECTED
                 ├─ SERVICE_ONLY（维修备用）
                 ├─ SCRAP（报废记录）
                 ├─ MISSING（缺失记录）
                 └─ PRIVATE_DESTROY（私人帧素材销毁记录）
```

收货、检查和补发均已使用请求编号与请求指纹防止重复写入；`QUARANTINED -> INSPECTING` 使用条件更新，检查事务失败会整体回滚。

但检查只验证数量为正数：未拆封回库数量没有上限，也不与批准退回的具体商品/SKU核对；已拆封明细的数量合计、材料身份和原 BOM 也未被约束，具备岗位权限的误操作可凭空增加新品或维修备用库存。登记为 `ERF-024`。`PRIVATE_DESTROY` 目前只保存处置名称，没有销毁任务、完成时间、操作证据或私有文件生命周期联动，登记为 `ERF-026`。

## 23. 补发当前事实

- 一个退回收货记录最多创建一个关联原生产件和售后申请的 `PU-R`，数据库唯一约束和请求账本阻止重复创建。
- 当前只要求已有退回收货记录；隔离检查完成与否都可创建补发。
- 补发没有独立数量输入，也不锁定材料包库存。
- 补发状态直接写为 `processing`，继续关联原 `SalesOrderItem` 并增加 `unitIndex`。
- 正式生产批次只接受 `SalesOrder.status=paid`、所有单件任务为 `paid`，并要求任务总数等于订单商品购买数量；售后中的原订单与新增补发都不满足这些条件。

因此现有自动测试证明“只创建一条补发记录”，没有证明它能获得库存、进入批次、完成配对和发货。该流程登记为 `ERF-023`，并受订单域正在修改的边界影响，具体数据结构需在订单稳定后补审。

## 24. RP2-D 推荐规则与待确认

`RQ-008` 推荐：

1. 未拆封、封签完整、SKU/数量与批准退回明细一致并经复核，才允许生成新 `KR` 批次进入新品库存。
2. 已拆封零件不能进入新品；可复用件只进维修备用，耗材报废，私人帧素材进入有执行证据的销毁流程。
3. 补发是零金额、关联原订单具体商品/单件和售后申请的独立履约任务，创建时明确数量并锁定库存。
4. 默认检查完成后补发；经客服负责人明确选择“无需退回”或“先行补发”并记录原因时可以提前。
5. 退款、仅退货、补发及退款加退货分别具有明确状态和副作用，不能只靠售后 `completed` 字符串表达。

确认前不实现退回/补发结构；`ERF-021/022/024/025` 属于数量守恒和幂等缺陷，不依赖产品偏好，但仍留到 RP8 按完整事务设计整改。
