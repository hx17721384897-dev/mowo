### 0.2 当前阶段的修改授权与质量目标

本项目尚未上线、没有真实用户和真实业务数据，当前有充足时间修正架构。实施时以长期可维护、安全、清晰和可验证为优先，不以维持旧原型或压缩修改量为目标。

- 已完成消费者、数据责任、权限和回退核对的冗余实现，应删除或替换；不因“旧代码已经存在”而默认永久兼容。
- 新旧实现不得无限期并存。兼容只允许服务于明确的迁移窗口，并必须有负责人、截止条件和删除验收。
- 允许对当前代码做结构性修改，包括删除无消费者页面/路由、调整目录、收口 API 客户端和拆分大文件；但不得跳过依赖图、测试、文档和可回退提交。
- 对纯技术实现，可依据当前代码、测试和安全原则作出最小且可逆的判断；涉及业务范围、金额、权限归属、订单/库存副作用、数据保留或对外承诺时，必须先向项目负责人确认。
- “企业级”在本阶段表示边界明确、默认安全、错误可见、变更可测、记录可交接；不表示提前引入微服务、复杂中间件或生产级云资源。

### 0.3 中断恢复与持续复查规则

每个执行批次必须维护可恢复的工作记录。发生网络、工具或进程中断后，不得凭记忆继续覆盖修改；恢复时按固定顺序执行：

1. 读取本计划、当前批次记录和最近一次进度说明。
2. 检查 `git status`、`git diff`、当前分支和最近提交，区分用户原有修改、已完成修改和未完成修改。
3. 核对已运行测试、失败输出、临时服务/端口和测试数据库状态；不假设中断前命令已经成功结束。
4. 从“最后一个有证据通过的检查点”继续；先复验可能只完成一半的文件和数据变更，再实施下一步。
5. 每完成一个可验证子步骤，记录修改文件、决策、测试命令与结果、剩余风险和下一动作。

任何较大修改至少进行两轮检查：实现后的局部复查，以及批次结束前的跨模块回归。删除类修改还要再次扫描 import、路由注册、页面链接、API 消费者、Schema 关系、Scheduler、环境变量、测试和文档引用。

### 0.4 安全与漏洞处理规则

- 前端隐藏、路由守卫和按钮禁用都不是安全边界；对象归属、岗位权限、功能状态、价格、库存、文件读取和状态变化必须由服务端验证。
- 不提交或输出密钥、验证码、Token、真实手机号、地址、私有素材、签名 URL、数据库备份和包含敏感数据的日志。本阶段测试只使用隔离库和合成数据。
- 新增依赖前检查用途、维护状态、许可证和已知安全风险；依赖版本进入锁文件，不使用来源不明的脚本或运行时 CDN 代码。
- 发现越权、隐私泄露、任意文件读取/上传、认证绕过、支付伪造、重复扣库存/建单/发货、命令注入或其他 P0 风险时，立即停止相关功能修改，保存脱敏证据并向项目负责人报告；不得把异常吞掉或只在前端规避。
- 发现非立即可利用但会扩大攻击面的 P1 风险时，在当前批次记录影响、临时边界和修复条件；若本批改动触达该路径，应一并修复或在继续前确认延期理由。
- 安全修复必须包含允许路径与拒绝路径测试，并复查日志、错误响应和页面是否泄露对象存在性或内部字段。

### 0.5 文档与程序员交接要求

每个批次结束时，交接记录至少包含：目标与非目标、代码事实、产品决定、修改文件、正式入口、API/DTO、权限、状态变化、测试命令与结果、人工验收、已知风险、回退点、删除项及下一步。文档描述必须与当前代码一致；历史方案如有追溯价值，应明确标为历史，不能继续与当前事实并列生效。

### 0.5.1 视觉迁移与共享组件决策门

2026-09-15 的公共页面返工确认：技术架构迁移不得被执行成视觉重设计。后续所有页面迁移和组件抽取必须遵守以下规则：

- 旧站中名称相同的导航、页脚、弹窗、表单和状态组件，先逐页面比较结构、样式、断点、交互与业务语义，再判断是否共用；不能仅因名称相同就强制统一。
- 确认属于无意义重复的实现，应收口为一个共享组件；确认属于页面业务差异的内容，应通过清晰的属性、插槽或页面组合表达，不复制整套组件。
- 无法判断差异是历史偶然还是有意设计时，必须在编码前把差异、统一方案和影响页面交给负责人确认。不得先覆盖后补解释。
- 迁移页面以固定旧提交、固定数据和桌面/手机视口做逐页对照。自动测试通过只证明工程门禁通过；涉及视觉取舍时，负责人确认仍是阶段完成条件。
- 共享组件修改必须回归所有消费者，并检查切页过程中的几何稳定、活动态、滚动复位、滚动条、字体加载、焦点恢复和移动菜单，而不只比较页面加载完成后的截图。
- 不再接受以新壳、新组件库或“更统一”为理由遗漏旧页面细节。允许差异仅限已确认退役能力、安全修复、虚假承诺清理和经负责人确认的设计统一。

公共页面视觉返工已于 2026-09-15 获负责人统一确认，详细事实源、提交和验证命令见 `VUE_VISUAL_FIDELITY_REMEDIATION_PLAN.md`。后续 V1c 至 V6 继续执行上述门禁。

## 1. 目标、前提与不做事项

### 1.1 目标

将目前由大量独立 HTML、页面内 CSS 和页面内 JavaScript 组成的 Web 前端，逐步整理为一套 Vue 3 + TypeScript 前端。最终做到：

- 页面按**官网展示层、用户交易层、后台运营/生产层**分区，但共享同一套可靠的请求、登录、权限、组件和测试基础。
- 每个业务只有一个正式入口；旧页面在替代页验收后才退役。
- 前端只负责展示、输入校验和交互，不把价格、权限、库存、订单状态或文件读取权限当作前端可信事实。
- 每个迁移批次都能在独立测试库中复查正常路径、异常路径和权限边界，并能回退。
- 新成员能从目录、类型、接口和测试中理解业务，而不是在几十个 HTML 页面里寻找重复逻辑。

### 1.2 本计划的前提

本项目不急于上线，优先追求干净、可维护和可验证，而不是用最短时间把旧页面逐字翻写成 Vue。

Vue 迁移开始前，以下基础必须先可用：

1. 空库迁移链、独立测试数据库和种子/测试数据边界可重复运行。
2. 当前批次对应的后端 API、权限、数据状态和功能开关已有明确结论。
3. 旧页面、旧接口和正式入口已有消费者地图；不因“看起来旧”而直接删除。
4. 真实支付在未启用期间继续由服务端隔离；社区、创作者自助、线上财务和牛量/推广先由 R1-A 服务端拒绝，再由 R1-B 删除运行能力，不能只依赖前端隐藏。

### 1.3 本计划不做什么

- 不替换 Fastify + Prisma 技术栈，也不借前端迁移重写无关后端业务；允许并要求为契约收口、安全修复和已决定退役能力删除相应后端代码。
- 不一次性重写全站，不让 Vue 与旧 HTML 长期承担同一个正式流程。
- 不在前端保存密钥、支付凭据或私有文件永久地址。
- 不因引入 Vue 而提前开放真实支付、公开注册、社区或线上结算。
- 不拆微前端、微服务或多个前端仓库；目前规模采用一个模块化 Vue 应用更容易维护。

## 2. 技术选型与关键原则

| 领域          | 选择                                   | 原因与边界                                                               |
| ------------- | -------------------------------------- | ------------------------------------------------------------------------ |
| 框架          | Vue 3 + TypeScript + `<script setup>`  | 组件边界、类型提示和可复用逻辑；所有新业务页面使用 TypeScript。          |
| 构建          | Vite                                   | 本地开发快、构建清晰、环境变量和产物标准化。                             |
| 路由          | Vue Router                             | 用路由元数据标识页面分区、登录要求和岗位要求；后端仍是权限唯一事实源。   |
| 共享状态      | Pinia                                  | 只存会话摘要、购物车摘要、短期 UI 状态；不把所有接口数据塞进全局 Store。 |
| 接口层        | 原生 `fetch` 的统一封装                | 集中处理 API Origin、凭证、刷新会话、错误码、超时与请求编号。            |
| 单元/组件测试 | Vitest                                 | 与 Vite 共用构建配置，测试 TypeScript、工具函数、组件和 Store。          |
| 浏览器回归    | Playwright                             | 用真实浏览器覆盖登录、浏览、定制、购物车、订单和后台关键流程。           |
| 样式          | CSS 变量 + 分层样式文件 + 组件局部样式 | 先建立项目自己的设计 Token，不在第一期引入大型 UI 框架。                 |

使用 Vite 时，任何以 `VITE_` 开头的环境变量都会被打包到浏览器；因此它只能保存公开 API 地址、构建标识等非敏感配置，绝不保存密钥。[Vite 环境变量说明](https://vite.dev/guide/env-and-mode)

Vue Router 是 Vue 的官方客户端路由方案；它负责 URL 和页面组件的映射，不承担服务端鉴权。[Vue Router 文档](https://router.vuejs.org/guide/index.html)

Pinia 用于不绑定单一组件树的共享状态；本项目将限制其职责，避免形成新的“大型全局状态文件”。[Pinia 文档](https://pinia.vuejs.org/getting-started)
Vitest 可以复用 Vite 的配置和转换链，适合本项目的单元及组件测试。[Vitest 文档](https://vitest.dev/guide/why)

## 3. 目标架构：一个代码库、三类布局、按业务模块拆分

### 3.1 为什么不是三个独立前端项目

官网、用户交易、后台生产的受众不同，但它们共用登录、API、设计语言、商品信息和类型定义。当前团队规模不适合为三套应用重复维护构建、依赖、接口客户端和权限逻辑。

因此采用**一个 Vue 代码库 + 三类布局 + 路由按需加载**：构建时仍是一份前端产物，访问后台或生产页时才下载对应模块代码。未来若访问量、团队或部署边界真正需要，再以清晰模块为基础拆分，而不是现在预先制造复杂度。

### 3.2 新旧站并存、部署与最终目录

`frontend-vue/` 是迁移期间的新工程目录；它不是第二个永久前端。项目最终只保留一个正式前端根目录 `frontend/`。V6 在所有正式流程完成切换、旧消费者清理和回退窗口结束后，以独立提交将 Vue 工程提升为 `frontend/`，或等价地将当前 `frontend/` 完整替换为 Vue 构建源码；两者不可长期并存。

迁移期间必须使用以下可执行机制：

1. **初期地址固定。** Vue 仅在本地、独立测试域名，或明确的 `/app/*` 前缀下运行；V0 写明每个环境的 Base Path，不能用页面 JavaScript 猜测当前环境。
2. **切换由静态站点/反向代理完成。** 验收后的正式路径由部署配置映射到 Vue 构建产物；Vue Router 的 history fallback 只匹配前端路由，必须先排除 `/api/*`、私有文件、健康检查和真实静态资源，避免 API 被错误返回 `index.html`。
3. **旧 URL 有显式映射。** 每条被替代的旧地址记录“旧地址 → 新地址 → 负责人 → 切换日期 → 回退地址”。验证窗口优先使用可撤回的 302；确认稳定且不再需要回退后，才使用永久 301/308 或受控说明页。
4. **不使用静默前端跳转。** 不允许旧 HTML 依靠 `window.location` 猜测、自动跳到不确定的新页，或用前端逻辑承担兼容责任。
5. **深链接必须验收。** 在新标签、刷新、浏览器返回、复制链接和旧收藏链接场景下均应到达正确页面或明确说明页。

### 3.3 路由命名边界

当前对外联名货架的正式语义为“展示/选购”，因此 Vue 对外商品路由统一采用 `/showcase`、`/showcase/:id`。`/products` 仅可保留为已确认的品牌介绍页；它不得与历史 `/api/products` 创作者自助商品体系混为一谈。Vue API 客户端不会为历史 `/api/products` 生成正式模块。

### 3.4 模块内部固定结构

每个模块按同一结构组织，减少“文件到底该放哪里”的争论：

```text
modules/commerce/
├─ api/             # 本模块 API 函数与 DTO 转换
├─ components/      # 仅本模块使用的组件
├─ composables/     # 业务交互逻辑，如 useCart
├─ routes.ts        # 本模块路由声明
├─ stores/          # 仅真正跨页面共享的状态
├─ views/           # 路由页面
├─ types.ts         # 本模块类型
└─ *.test.ts        # 与代码相邻的单元测试
```

禁止：

- 在 Vue 组件中直接散落 `fetch('http://localhost:3001/...')`。
- 在每个页面重复读取 Token、拼接请求头、判断岗位。
- 用 Pinia 替代后端数据库或存放订单、地址、私有文件的长期可信副本。
- 用页面是否隐藏作为权限控制。
- 让公共 `shared/` 反向 import 某个业务模块。

## 4. 三层页面边界与目标路由

| 层级       | 典型页面/模块                               | 路由边界                                               | 访问控制                     |
| ---------- | ------------------------------------------- | ------------------------------------------------------ | ---------------------------- |
| 官网展示层 | 首页、品牌、FAQ、联名列表、详情、联络、协议 | `/`、`/showcase`、`/products`、`/contact`              | 默认公开；仅购物动作需登录   |
| 用户交易层 | 设置、地址、动画、定制、购物车、结算、订单  | `/account/*`、`/customization/*`、`/cart`、`/orders/*` | 必须登录；服务端核验对象归属 |
| 后台运营层 | 用户、联名商品、帧图、订单、库存            | `/admin/*`                                             | 必须登录 + 指定 `staffRole`  |
| 生产层     | 批次、打印、扫码、配对、装箱、发货          | `/production/*`                                        | 必须登录 + 生产相关岗位      |

路由守卫只负责改善体验：未登录跳转登录页、无岗位显示无权页面。它绝不能代替 Fastify 中的服务端权限检查。

## 5. 迁移前的强制门槛

以下任一未满足时，不能迁移其对应业务域；可以做 Vue 基础骨架和纯 UI 组件，但不能宣布该业务页可用。

| 门槛         | 必须证据                                       | 对应风险                       |
| ------------ | ---------------------------------------------- | ------------------------------ |
| 数据库可重建 | 独立空库完整执行迁移、种子和冒烟脚本           | 新环境无法启动、测试结果不可信 |
| API 契约明确 | 路径、入参、返回 DTO、错误码、权限写入模块文档 | Vue 反复跟随后端猜字段         |
| 正式入口明确 | 旧页、新页、跳转和删除条件列入差异台账         | 双入口、用户走错流程           |
| 业务状态明确 | 订单/库存/定制/生产状态变化可列成表            | UI 允许非法操作                |
| 权限验证存在 | 至少有用户 A/用户 B、不同员工岗位的 API 测试   | 前端隐藏但接口越权             |
| 独立测试数据 | 自动脚本仅写入 `mowo_b1_test` 或等价隔离库     | 测试污染开发数据               |

## 6. 迁移总策略：竖向切片，不逐字翻译页面

一个“竖向切片”是用户可以完整完成的一条流程，例如：

```text
联名列表 → 商品详情 → 登录后加入购物车 → 购物车
```

迁移一个切片时，必须同时完成页面、API 客户端、类型、错误状态、权限、测试、旧入口切换和文档，而不是只完成视觉页面。

### 6.1 旧页面与新页面的切换规则

1. 新 Vue 页面先只在本地/测试环境可访问，不替代旧正式入口。
2. 使用同一份后端 API 和同一份测试数据，完成正常、失败、越权和移动端验证。
3. 在差异台账标明新旧地址、切换日期、回退方法和删除条件。
4. 切换共享导航、按钮和深链接到新 Vue 页面；旧页保留一个短暂兼容期。
5. 检查全仓库链接、浏览器历史、收藏链接和文档引用。
6. 确认没有消费者后，单独提交删除旧页面及其专用脚本、样式和残留路由。

旧页面不能“静悄悄消失”。如用户可能保存旧 URL，应提供明确跳转或说明页；不再存在的关闭功能可返回受控的 404/功能未开放页面。

## 7. 推荐执行批次

固定顺序如下；任何例外必须记录依赖、风险和负责人：

```text
H0 接管、文档同步与 L0 基线封存
  → R0 后端/数据库既有证据确认
  → R1-A 已退役能力的服务端隔离（可与 R0 并行启动）
  → V0 Vue 脚手架、认证决策、契约与功能矩阵
```

### V0：基础契约与 Vue 脚手架

**目的：** 建造可重复使用的空壳，不迁移业务，不改变旧页面正式入口。

**工作：**

- 消费 R0 已验证的独立测试数据库、迁移基线和 API 契约；不对 `mowo_db` 或业务 Schema 直接试错。
- 建立 `frontend-vue/`，使用 Vue 3、TypeScript、Vite、Vue Router、Pinia、Vitest 和 Playwright。
- 配置绝对路径别名、严格 TypeScript、ESLint/格式化、生产构建、类型检查和测试命令；明确受支持的 Node LTS 版本、唯一包管理器、锁文件提交规则和依赖升级流程。
- 明确构建输出目录、静态资源指纹/缓存策略、生产 sourcemap 是否生成及其访问控制、前端错误上报字段和脱敏规则。
- 建立公开运行时 API 配置；开发、测试、未来生产的 API 地址明确分开；同时写出 `/app/*` 测试前缀或独立测试域名、Vue history fallback、`/api/*` 排除和旧 URL 映射方案。
- 建立 `PublicLayout`、`AccountLayout`、`AdminLayout`、`ProductionLayout` 空布局，以及统一 404、无权、加载、空数据、错误页。
- 完成**认证迁移架构决策**：记录当前 Access Token 在 `localStorage`、Refresh Token 在 HttpOnly Cookie 的边界；明确 `credentials: 'include'` 的适用请求、401 刷新并发去重、最多重试一次、登录回跳、登出/注销后的内存与本地状态清理。评估未来同域部署时是否迁移到更安全的 Cookie/BFF 方案；该评估完成前，任何模块不得自行实现刷新逻辑。
- 建立 `apiClient`：超时、JSON 解析失败、网络错误、统一错误对象、请求 ID、凭证策略和认证刷新均集中处理。
- 建立**首发功能矩阵**：每项功能必须列出前端路由、后端路由前缀、**服务端边界**、当前状态（正式/内部保留/退役中/已退役）、唯一负责人、**验收证据**（测试名称、路由扫描或部署产物检查）和**恢复规则**。服务端边界仅可为“正式开放”“内部岗位权限”“Feature Flag”或“无路由（已退役）”；已退役能力不得为了填表重新增加 Feature Flag。社区、线上财务、牛量/推广和创作者自助的恢复规则统一为“不得重新开启旧实现；未来只能按新业务设计重新开发”。至少覆盖社区、线上财务、牛量/推广、创作者自助、外部平台订单导入、CRMEB 历史遗留、真实支付和人工联名合作。
- 建立最小 UI Token：颜色、间距、圆角、字号、断点、层级、禁用/危险状态；不急于复制全部旧样式。
- 建立 CI 的最小门禁：安装、类型检查、单元测试、生产构建、E2E 冒烟。

**部署交付物：** 可版本化的静态托管/Nginx（或等价平台）配置、Vue/旧 URL 路由映射表、`/api/*` 排除规则、history fallback 规则和部署冒烟脚本。实际采用的托管产品可以后定，但这些规则必须以可执行配置保存，而非只写在 Markdown。

**验收：** 新项目可在新电脑按固定 Node/包管理器/锁文件安装、启动和构建；空页面通过 `/app/*` 或独立测试地址访问；部署冒烟验证刷新 Vue 深链接时不拦截 `/api/*`；任何页面都不包含硬编码密钥或 `localhost` 生产分支；认证刷新只有一个并发请求；首发功能矩阵经产品负责人确认；CI 可以运行。

### R1-A：已决定退役能力的服务端隔离（立即开始）

**目的：** 在 R1-B 删除源码完成前，阻止已决定退役的旧能力被直接调用、被旧页面继续使用或被 Vue 误接入。

## 8. API、身份与数据规则

### 8.1 统一请求客户端

所有 API 调用经由 `platform/api/apiClient.ts`，它负责：

- 从公开运行时配置读取 API Base，而不是页面自定 `localhost`。
- 设置 `Accept`、请求编号和必要的认证凭证。
- 统一处理 401、刷新会话、退出登录和返回原页面。
- 区分网络失败、超时、非 JSON、验证错误、无权、功能关闭和服务端业务错误。
- 只记录脱敏的请求元数据；不记录密码、验证码、Token、地址、手机号或签名 URL。

每个模块只定义类似 `getCart()`、`addCartItem()` 的业务函数，不允许 View 自己拼 URL 或解释后端不同响应结构。

### 8.2 类型与 DTO

- **唯一契约事实源**是：后端路由 Schema、后端契约测试，以及按版本冻结的 DTO fixture。三者不一致时，以修复后端 Schema/契约测试和 fixture 的明确结论为准。
- `docs/API.md` 是面向人阅读的同步说明，不是前端猜测字段或绕开契约测试的来源；它与代码漂移时必须登记并修正。
- 每个 Vue 模块为关键成功/失败响应维护 fixture 契约测试；高风险或外部输入响应在 API 转换层做运行时结构校验，校验失败显示受控错误并记录脱敏诊断，不把异常对象交给组件渲染。
- 把后端原始 DTO 与页面 ViewModel 分开；格式化价格、日期、标签的工作在转换层完成。
- 后端字段变动时，同步更新 DTO、转换函数、测试和模块文档。
- TypeScript 只提高开发期发现问题的能力，不替代服务端输入校验。

### 8.3 身份与权限

- 不将 Access Token 作为普通业务状态在多个 Store/组件传递。
- 前端路由只做“是否登录/岗位是否可能访问”的体验判断；对象归属、下载权限、价格、库存和危险动作永远由服务端再次核验。
- 无权页面不泄露目标对象是否存在、手机号、地址、合同或内部备注。
- 认证、登出、会话失效、功能关闭和账号注销均有统一错误体验。

### 8.4 会话迁移的单一实现规则

当前 Web 的会话组合是“短期 Access Token + `localStorage`”与“轮换 Refresh Token + HttpOnly Cookie”。Vue 初期不得因迁移而暗中改变该协议；它必须由 V0 的认证决策明确记录并由一个 `sessionManager` 实现：

1. 哪些请求发送 Cookie，哪些请求发送 Access Token；跨域时的 CORS/凭证要求。
2. 多个请求同时收到 401 时，只允许一个刷新请求进行，其余请求等待结果；刷新成功后每个原请求最多重试一次。
3. 刷新失败、登出、全部设备退出、账号注销或账号状态失效时，一次清理内存状态、Pinia、`localStorage` 和页面缓存，并保留安全的登录回跳地址。
4. 为开发、测试、预发和正式环境分别记录 Cookie 的 `SameSite`、`Secure`、`Domain`、Path、有效期、允许的 CORS Origin 与 `credentials` 策略。除本地开发外 Cookie 必须使用 `Secure`；默认采用 host-only Cookie，只有经审计的子域共享需求才扩大 Domain。若 Vue/API 属于真正跨站域名，必须明确采用 `SameSite=None; Secure`、精确 Origin 白名单与 CSRF 防护，不能依赖通配 CORS。
5. 同域部署或 BFF/Cookie 方案是未来可评估的安全升级，不得在一个业务迁移批次中半途切换。

## 9. 设计系统与可访问性

先提取真实重复模式，再抽组件；不要把每一段旧 HTML 强行做成组件。

第一批共享组件建议为：

- `AppButton`、`AppInput`、`AppSelect`、`AppTextarea`、`AppFileInput`
- `AppDialog`、`ConfirmDialog`、`Toast`、`InlineError`
- `AppTable`、`Pagination`、`StatusBadge`、`EmptyState`、`LoadingState`
- `PageHeader`、`FilterBar`、`DetailDrawer`、`PermissionDenied`

最低质量规则：

- 关键操作可以键盘完成，有清楚的焦点状态。
- 表单元素有真实 label 和错误说明，不只依赖颜色。
- 图像有合适替代文本；纯装饰图标标为装饰。
- 弹窗打开后焦点进入弹窗，关闭后回到触发按钮。
- 手机端以真实常用宽度验证，不只检查桌面浏览器缩放。
- 危险操作使用文字说明，不只使用红色按钮或图标。

### 10.1 测试金字塔

| 层级           | 工具/方式               | 必测内容                                                    |
| -------------- | ----------------------- | ----------------------------------------------------------- |
| 类型与静态检查 | `vue-tsc`、ESLint、构建 | 类型、未使用代码、构建失败、环境变量误用                    |
| 单元测试       | Vitest                  | 金额/日期格式、DTO 转换、错误转换、路由权限判断、幂等键生成 |
| 组件测试       | Vitest                  | 表单校验、禁用状态、加载/失败态、弹窗确认、分页、权限提示   |
| API 契约测试   | 后端脚本 + 独立测试库   | DTO、权限、隔离、状态机、幂等和事务                         |
| 浏览器 E2E     | Playwright              | 三层正式主流程、双账号隔离、关键异常路径                    |
| 人工验收       | 固定清单                | 移动端、扫码设备、文件上传、打印与生产操作                  |

每个迁移切片至少覆盖：正常路径、未登录、无权、接口失败、重复提交、刷新/返回和移动端。

### 10.2 每批固定验收模板

每次迁移新模块前，在提交说明或对应文档中写清：

```text
目标：迁移哪条完整业务流程
影响：页面、路由、API、数据模型、权限、旧入口
不做：明确不迁移的页面/功能
测试库：名称和隔离方式
自动验证：执行命令与结果
人工验证：操作步骤、账号角色、预期结果
回退：切回哪个旧入口、如何处理已打开的深链接
删除条件：旧页面何时可删
```

### 10.3 回退原则

- Vue 新页未验收前不替换旧正式入口。
- 切换入口的提交与删除旧页的提交分开。
- 发现回归时优先恢复旧入口或上一个已验证提交，不通过覆盖式修补掩盖问题。
- 不以回退前端页面的方式回退已经写入的订单、库存或生产数据；此类动作由服务端状态机和补偿流程处理。

| 环境      | 用途                    | API/数据要求                         |
| --------- | ----------------------- | ------------------------------------ |
| 开发      | 本地编码和手工调试      | 可使用本地 API，但不使用真实用户数据 |

## 12. 已决定退役的功能：删除运行能力，谨慎清理数据结构

### 12.1 产品决定

社区、线上创作者财务、牛量/推广和创作者自助能力不属于“未来改个开关即可上线”的功能。本计划将它们定义为 **RETIRED（退役）**：未来若重新开展，必须从业务规则、权限模型、账本、审核和测试重新设计，不能重新开启旧实现。

这比“隐藏按钮 + 永久 Feature Flag”更符合当前项目的复杂度控制目标。源码和 Git 历史用于追溯，不将可误用的旧运行能力长期留在产品仓库。

### 12.2 退役范围与保留边界

| 范围       | 目标动作                                                                     | 明确保留                                                                  |
| ---------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 社区       | 退役文章、Feed、评论、点赞、收藏、关注的路由、页面、旧页面、链接、测试和配置 | 与私人定制、联名货架无关的用户基础资料                                    |
| 线上财务   | 退役收益、余额、提现、结算、储备金、分红计算、财务定时任务、配置、页面和接口 | 已成交订单的必要金额快照；线下合同与付款资料不录入首发平台                |
| 牛量/推广  | 退役积分、等级、引流链接、外链声量、任务、页面、接口和配置                   | 订单/合同中必要的作品权利人和授权追溯字段                                 |
| 创作者自助 | 退役历史 `/api/products` 的自助上架、改价、下架及其页面/客户端               | 受工作人员管理的联名商品、SKU、权利与授权来源、内部线下合作和历史订单关联 |
| CRMEB      | 不生成 Vue 页面、API 客户端或新依赖                                          | 历史 Schema/文档中为迁移追溯所需的记录                                    |

外部平台订单导入的业务概念和历史数据不归入永久退役范围。负责人在 V4-E3 进一步确认当前只保留内部入口，不假设淘宝 CSV 或其他平台模板；旧写实现已删除并由服务端门禁关闭，取得真实样表并确认正式订单契约后重新开发。

| 已确认决定   | 执行批次与边界                                                                                        |
| ------------ | ----------------------------------------------------------------------------------------------------- |
| 内部首发保留 | 纳入 V4 后台运营层，迁移 `admin-import`、SKU 映射、异常补全和相关库存来源展示；仅内部岗位权限可访问。 |

CRMEB 已确定不再接入：Vue 只承担“不生成页面、API 客户端和依赖”的边界。所有 CRMEB 代码、配置和历史字段的最终清理必须在后续专项依赖审计后进行，不在 Vue 迁移提交中顺手删除。

### 12.3 R1 路由—HTTP 方法验收矩阵

R1-A 与 R1-B 都必须维护可执行的负向 API 测试，而不是只抽查少量 GET。除已确认保留的外部订单导入外，以下最低覆盖项均应验证每种方法返回受控 404（或已统一批准的 410）、不返回业务数据且不产生副作用：

| 退役功能                            | 最低必测 HTTP 方法                                |
| ----------------------------------- | ------------------------------------------------- |
| 社区文章                            | GET、POST、PUT、DELETE                            |
| 评论、点赞、收藏、关注              | GET、POST（并覆盖项目实际存在的 DELETE/PUT 变体） |
| 历史 `/api/products` 创作者自助商品 | GET、POST、PUT、DELETE                            |
| 创作者自助联名                      | GET、POST、PUT（并覆盖实际存在的删除变体）        |
| 收益、提现、结算                    | GET、POST、PUT                                    |
| 牛量、推广                          | GET、POST、PUT                                    |

R1-B 完成不能只看 HTTP 响应，还必须有下列证据：

1. 后端入口文件不再注册相应路由，路由模块不再被 import。
2. 对应 Scheduler、队列消费者、环境变量、Feature Flag 和后台任务不再启动。
3. 前端源码、API 客户端、导航、文档和测试中没有消费者；生产构建产物中没有相关页面或静态入口。
4. 所有旧 URL 的直接访问均不能进入旧业务：公开路径自然 404；后台路径先执行统一认证/岗位授权，未登录为 401、无权限为 403、获授权调用到路由层后为 404；不能仍可打开历史页面。
5. 保留的权利人、授权来源和订单快照通过独立测试库重放及追溯测试；线下合同不进入平台。

### 12.4 旧静态文件、已知链接与文档事实

`frontend/pages/_legacy/` 不得作为公开部署入口。R1-B 已删除其中属于退役功能的页面；需要追溯时依赖 Git 历史。部署冒烟测试必须直接请求已知旧 URL，确认不能返回历史 HTML。

R1 的依赖审计从现有旧前端开始，至少将下列已知项列为逐项关闭、修复或保留理由清单，不能只扫描新 Vue 源码：

- `settings.html` 指向不存在的 `creator-certify.html`、`creator-dashboard.html` 的链接。
- `router.js` 对 `community.html`、`favorites.html` 的遗留路由/导航引用，以及其他扫描到的已退役页面引用。
- `_legacy` 页面之间的相互链接和可直接访问的静态入口。
- `feature-flags.js` 中当前为空的 `disabledPages`：不得误以为空对象已经形成页面隔离。
- 私人定制编辑器的“返回/取消”目标：它属于保留的私人定制能力，必须逐项验证目标存在且属于保留流程，不得因创作者中心退役而误删。当前扫描未复现 `creator-animations.html` 这一具体目标，实施时以实际代码和浏览器回归结果为准。

R1-B 还必须同步更新 `DEFERRED_CREATOR_PLATFORM.md`、`RELEASE_SCOPE.md`、相关模块事实文档、`DOC_CODE_DIFFERENCES.md`、`API.md` 与 `DOCUMENTATION_STATUS.md`。同一能力在全仓库只能使用一个准确状态：`暂时关闭但保留`、`退役中`、`已退役` 不得混用；对本章已决定 RETIRED 的范围，R1-B 后只能标为“已退役，不得重新启用旧实现”。

### 12.5 退役执行顺序

1. 建立依赖图：路由、前端入口、Scheduler、环境变量、模型、迁移、订单快照、合同、测试和文档。
2. 先移除所有公开和内部运行入口，再删除专用服务、定时任务、Feature Flag 和 API 注册；源码不存在时接口自然返回 404，不再依赖 `FEATURE_NOT_AVAILABLE`。
3. 对仍被人工联名、合同或历史订单使用的字段做最小保留，不以“创作者”名称就整体删除模型。
4. 删除应用依赖后，在独立空库基线重建阶段统一清理无消费者的旧表；绝不在既有历史迁移 SQL 中随手删除表或改写历史。
5. 用空库迁移、核心订单/合同追溯测试、第 12.3 节的路由—HTTP 方法验证、部署产物检查和全仓库链接扫描作为验收。
6. 文档标明“已退役，不得重新启用旧实现”，并记录未来如需恢复必须新立设计与审批。

此项应单列为“退役批次”，由一名负责人处理，不与交易、库存、生产或 Vue 页面视觉迁移混在同一提交中。

## 14. 项目治理规则

1. 新功能先归属三层之一和一个业务模块，再开始设计页面。
2. 新页面默认写 Vue；只有纯静态、低变化的协议/帮助页可暂留静态 HTML，并写明原因。
3. 不允许再新增数百行页面内 JavaScript；临时修复也应进入公共脚本或 Vue 迁移待办。
4. 一个 Git 提交只处理一个可验收主题，且不提交 `.env`、私有文件、测试产物或 `.codex-tmp/`。
5. 任何删除先查消费者、链接、数据责任和回退路径；删除与替代上线分开提交。
6. 每完成一个模块，同步更新模块事实文档、差异台账、测试记录和本计划状态。
7. 每月或每完成一个大模块复核依赖版本、安全公告、失效链接和前端包体大小。

## 15. 计划完成后的可验证结果

完成 H0、R0 证据确认、R1 和 V0～V6 后，哞屋 Web 前端应具备以下可观察结果：

- 官网、用户端、后台和生产端有清晰边界，但不复制三套基础代码。
- 页面、接口、角色和状态的关系可以从模块目录和测试中查到。
- 用户无法靠改 URL 或前端状态访问他人的订单、素材或后台功能。
- 同一个业务流程不再同时由旧 HTML 与 Vue 两套正式入口承担。
- 新页面可以复用组件、类型、错误处理和测试，而不是复制整页代码。
- 新电脑可安装、构建、运行测试；独立测试库可重建。
- 任何一次迁移都能说明改了什么、怎么验证、如何回退和旧代码何时删除。

这份计划的成功标准不是“项目里出现了 Vue”，而是前端成为一套能长期修改、可验证、可交接的业务界面系统。
