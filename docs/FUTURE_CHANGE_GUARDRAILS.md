# 新功能工程约束

> 适用范围：此后所有新增页面、接口、数据库字段、后台动作、定时任务和第三方接入。
> 目标：避免再次出现“代码已写、运行库有字段、迁移/测试/文档却缺失”的漂移。

## 1. 每项功能开始前

先写清一页简短方案，至少包含：用户目标、正式入口、前后端消费者、数据模型、权限、状态变化、关闭方式、失败提示与验收方法。没有这些信息时，不直接开始堆页面或接口。

## 2. 数据库：Schema、迁移与测试库必须同步

1. 修改 `schema.prisma` 时，必须在同一功能提交中新增对应迁移、写明迁移目的并通过空库重放。
2. 日常功能开发不使用 `prisma db push` 修改共享开发库；它只可用于可随时丢弃的个人实验库。
3. 已提交并被他人/环境使用的历史迁移不可改写；新需求只能新增迁移。当前早期项目的历史链修复是一次性例外，不能作为常规做法。
4. 所有会写数据的验证只连接命名明确的测试库（当前为 `mowo_b1_test`），绝不连接 `mowo_db`、邀请测试库或未来生产库。
5. 每次涉及数据结构的改动至少运行：Prisma 校验、空库 `migrate deploy`、`migrate status`；重要领域再运行 Schema diff 和对应业务冒烟。
6. 删除字段、删表、删外键、改字段类型/非空/默认值前，必须先列出现有数据、消费者、备份和回退方案，并由负责人确认。

## 3. 后端：一项能力只有一个正式事实源

- 新接口必须有明确路径、输入校验、认证/岗位授权、错误响应和审计要求。
- 交易、库存、生产、支付和账号状态必须先定义状态机与唯一写入入口；禁止新增“临时第二条写入路径”。
- 新旧接口需要兼容时，写清消费者、截止时间、返回 `410` 的条件和最终删除计划。
- 功能暂不开放时，优先由服务端拒绝，再由前端隐藏入口；关闭能力仍要记录恢复条件。

## 4. 前端：复用基础能力，不复制业务判断

- 复用统一运行时 API Origin、会话请求封装、导航和错误展示；页面不得自行拼部署环境的 API 地址。
- 新页面必须说明正式入口、返回路径、未登录/无权限/接口失败/空数据状态。
- 不把后端权限判断复制为前端信任逻辑；前端隐藏只改善体验，不是安全控制。
- 页面、接口、文案与功能开关必须同一提交更新，避免展示“未上线能力”或指向已删除页面。

## 5. 测试与验收

- 最小要求：`npm run check`、改动模块的自动检查，以及对应主路径的本地人工冒烟。
- 涉及登录、数据写入、订单、文件或权限时，必须补“允许”和“拒绝”两类验证。
- 新发现的缺口先写入审计台账；不能为了让测试通过而关闭约束、删除外键或把异常吞掉。

## 6. 文档、Git 与回退

- 同步更新模块事实、计划/台账、环境变量模板与 API 说明；文档记录的是代码事实，不写“预计已完成”。
- 一个可独立回退的主题一个提交；提交前运行检查，提交信息说明目的而非笼统写“update”。
- `.codex-tmp/`、日志、密钥、测试输出和生成物不得提交。
- 出现回归时先回退到最近已验证提交或 tag，再定位问题；禁止在未知状态上持续覆盖修改。

## 7. 合并前清单

- [ ] 入口、消费者、权限和状态变化已说明。
- [ ] Schema、迁移、测试库验证同步完成（若涉及数据）。
- [ ] 无新增重复接口、重复页面或未受控旧入口。
- [ ] 配置项已写入 `.env.example`，且默认安全关闭。
- [ ] 自动检查、主路径和失败路径已验证。
- [ ] 文档、风险台账与 Git 提交已更新。
