# 聚合订单验收清单

> 实施日期：2026-08-22。范围是一次支付一个用户订单、订单商品快照和按数量展开单件生产任务；真实微信支付、退款资金流和完整生产物料流程不在本次范围。

## 简单关系

```text
一次支付
  -> 一个 SO 用户订单
      -> 一条或多条订单商品
          -> 按商品数量生成一个或多个 PU 单件生产任务
```

例如同时购买 A 款 1 件和 B 款 2 件：订单页只能显示 1 张 `SO` 卡片，详情有 2 条商品，生产后台有 3 条 `PU` 任务。

## 人工验收

1. 在购物车放入至少两种定制款式，或把其中一种数量改为 2。
2. 进入结算并使用本地模拟支付。
3. 打开 `orders.html`，本次付款只能显示一张以 `SO-` 开头的订单卡片。
4. 卡片内应同时显示各商品名称、规格、数量、行金额和订单合计。
5. 打开详情，应按购物车条目显示多条商品；数量为 2 的商品应提示已生成 2 个生产任务。
6. 后台生产列表应按每件实物显示以 `PU-` 开头的独立任务，仍可分别进入批次、物流和状态流程。
7. 重复发送同一个模拟支付，不得增加 `SO`、订单商品或 `PU` 数量。
8. 订单商品必须锁定成交时的动画版本；用户后来把动画修改成 V2，旧订单仍保持原版本。

2026-08-29 回归修复：确认页重复选择同一 SKU 时，购物车会合并为一条数量 2 的记录。前端、结算接口和支付回调都会去重同一个购物车条目 ID，数量仍从购物车记录读取并展开两个 `PU`。模拟支付只有在正式 `SO` 确实创建后才显示成功；内部回滚或预订单状态异常必须把失败原因返回页面。

## 自动检查

在 `content-service` 运行：

```powershell
npm run check:sales-order-structure
```

该检查会创建临时账号和一笔“两种商品、三件实物”的订单，额外提交一个重复购物车条目 ID，验证接口去重、商品数量、数据库关系、失败支付提示和重复支付幂等，并用真实 Edge 检查订单列表与详情页，结束后自动清理测试数据。
