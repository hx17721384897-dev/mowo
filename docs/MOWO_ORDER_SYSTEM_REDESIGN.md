# mowo 独立站订单系统重设计稿

> 决策版草案 · 2026-10-14。先讨论并定稿，再修改业务代码。本文以当前 mowo 商品、交易与生产流程为起点。

## 1. 这次要解决什么

让顾客从私人定制入口完成选择、结算、付款、查看订单、取消与整单售后；让商家在现有后台看到同一笔订单并按已设计的生产流程处理。联名入口沿用相同订单模型，但本轮先验收私人定制。每增加一项后台能力，客户端页面必须能看到对应的准确结果。

现有 mowo 已有 `MachineModelSku`、`SkuInventory`、购物车、`PreOrder`、`SalesOrder`、`SalesOrderItem` 和逐件生产任务（PU），以及 Vue 的购物车、结算、我的订单、订单详情和生产后台。需要补全的是状态、页面内容、资金与库存边界、异常处理和上线验收；不能把“页面做完整”当作后端规则已经安全。

## 2. 系统边界：只保留一个业务事实来源

| 业务 | 唯一写入方 | 页面职责 |
|---|---|---|
| 账号与订单归属 | mowo 用户与服务端鉴权 | Vue 只展示本人数据；后台按岗位授权 |
| 商品规格、定制作品、动画版本 | mowo 商品与定制模块 | 结算、订单详情展示成交时的不可变快照 |
| 价格与未来促销 | mowo 结算规则 | 明示原价、调整、应付、实付；不开放没有规则支撑的优惠按钮 |
| 可售量、预留、在制量 | mowo `SkuInventory` | 库存不足明确提示；一次下单仅预留一次 |
| 待支付凭据与正式订单 | mowo `PreOrder`、`SalesOrder`、明细 | 同一订单号贯穿成功页、我的订单、后台 |
| 模拟付款／未来微信支付 | mowo 支付适配层 | 只根据可信支付事实显示已付款；真实支付接入前模拟入口限测试环境 |
| 生产、包裹、发货 | mowo SO／PU／PB 生产流程 | 我的订单读取进度；后台只有一个发货写入口 |
| 售后与未来退款 | mowo 售后申请及独立资金记录 | “申请”“审核”“退款处理中”“退款成功”分开显示 |

订单列表、详情活动记录、付款状态、生产履约状态和售后处理都在现有 mowo 页面与服务端流程中实现。每项操作只设一个业务写入入口，并保存可核对的操作记录。

## 3. 订单身份与不可变快照

- `PreOrder` 是付款前凭据：记录顾客、明细、收货信息、金额、失效时间、幂等键和预留关系。到期、取消、付款失败释放预留；重复请求不得重复释放。
- `SalesOrder` 是付款确认后的客户订单：一笔付款对应一张 SO，一条购物车商品对应一条明细，数量 N 对应 N 个 PU。顾客展示 SO 订单号，生产岗位可追踪 PU。
- 成交快照保留商品来源 `CUSTOM/MARKET`、定制作品 ID、动画版本、每层 SKU、配置、标题、预览、数量、单价、调整金额、收件资料和当时适用的履约规则。后续改商品价、下架或改作品，不覆盖旧订单。
- 必须把金额事实分开：应付、实付、已退款、退款中。初期无优惠时显示实际费用即可，不填虚假的折扣、税费或预计到账时间。
- 支付、生产、物流、售后是并行事实；客户看到的主状态由服务端汇总，不能让前端自行猜测。

## 4. 付款后的 60 分钟暂缓履约

这是已确认的产品规则，本分支先写设计，待设计定稿后重新实现。

1. 默认暂缓 **60 分钟**。负责人可在现有管理后台设置后续订单的分钟数；修改时要留下操作者和时间。
2. 一笔订单实际确认付款时，冻结当时使用的分钟数和“最早可进入生产批次时间”。设置变更只影响**后来付款**的订单，已付款订单保持原时间。
3. 付款后、未进入 PB 时，客户主状态显示“已付款”；进入 PB 后显示“制作中”。60 分钟到期**不自动**进入 PB，仍由生产后台选择。
4. 生产后台的候选列表、创建 PB 的最终事务、任何可绕过的单件入口，都要检查等待时间和取消状态。客户端按钮是否可见不能代替服务端检查。
5. 等待期内以及到期后但尚未入批，按已确认的整单取消政策处理；取消与入批并发时只能有一方成功，库存释放与状态更新必须一致。进入 PB 后不提供直接取消，转客服／售后流程。
6. 客户详情显示付款时间、最早可排产时间和当前处理说明。该时间表示**最早可排产**，不是承诺发货时间。

## 5. 客户页面：每种结果在哪里看到

| 页面 | 第一轮必须出现 | 数据来源／交互 |
|---|---|---|
| 定制确认、购物车、结算 | 作品与动画版本、完整规格、数量、当前价格、库存异常、收货信息、付款倒计时 | 服务端重算价格和可售量；提交前核验归属与版本 |
| 下单结果页 | 付款确认中／成功／失败的真实结果、订单号、进入订单详情 | 服务端查询最终支付和建单结果；网络中断可刷新恢复 |
| 我的订单列表 | 全部／待付款／进行中／已完成／取消／售后筛选；订单号或商品搜索；来源、首件图、规格、件数、实付、主状态与下一步 | 服务端分页、排序和状态汇总；历史订单可查 |
| 订单详情 | 时间线、每条商品的成交快照、付款与费用、收件信息、生产进度、物流、取消／售后记录 | 未发生的节点不伪造；按实时资格返回可操作项 |
| 整单售后 | 原因、说明、必要凭证、提交结果、审核进度 | 申请成功不等于退款成功；初期仅整单申请 |
| 后台订单列表／详情 | 搜索、筛选、付款和生产状态、异常标记、订单与 PU／PB 关联、操作历史 | 订单操作与生产操作分清，保留现有生产台 |

无订单、筛选无结果、加载失败和无权限要分别呈现。移动端首屏先显示状态、商品和当前主要操作；每一条错误要告诉顾客下一步。订单地址、私有动画和凭证只能经本人或授权岗位读取。

## 6. 状态与操作矩阵（第一轮）

| 主状态 | 触发事实 | 客户可见操作 | 后台规则 |
|---|---|---|---|
| 待付款 | 有效 `PreOrder`，无可信支付成功结果 | 继续付款、取消 | 到期后只释放一次库存；不可生产 |
| 支付确认中 | 已发起支付，最终结果未知 | 刷新状态、求助 | 不重复建 SO，不凭前端跳转标记已付款 |
| 已过期／付款失败 | 支付窗口失效或渠道失败 | 重新结算 | 旧预留释放，旧凭据不可复活 |
| 已付款 | 支付成功且 SO／明细／PU 已正确创建，尚未入 PB | 查看最早排产时间；符合规则可取消 | 冻结 60 分钟设置；禁止提前入 PB |
| 制作中 | 至少有生产任务进入 PB | 查看生产摘要、申请售后 | 不开放直接取消；生产状态由现有流程产生 |
| 待发货／运输中 | 实际生产完成／已绑定有效物流单 | 查看物流 | 以真实发货操作和运单为准 |
| 已完成 | 确认收货或按后续正式规则完成 | 查看历史、申请售后（有效期内） | 保留全部成交和操作记录 |
| 已取消 | 取消事务已成功完成 | 查看取消结果 | 不可继续生产；库存只释放一次 |
| 售后处理中 | 有未结案的整单售后申请 | 查看申请 | 不覆盖原付款和物流事实 |

第一轮只承诺整单取消／整单售后申请。部分发货、逐件退换、多个包裹、部分退款、促销、发票、游客查询都是**扩展设计**：数据结构和页面布局可留位置，但接口、权限、资金和生产规则未实现之前不展示可点击功能。付款、履约与售后分别记录，页面状态由这些事实汇总。

## 7. 必须解决的风险及验收

| 风险 | 服务端要求 | 可观察的验收 |
|---|---|---|
| 重复点击／重复支付通知 | 结算键、支付交易号、SO 唯一约束及事务幂等 | 重放两次仍仅一张 SO、正确数量的明细与 PU |
| 超卖／重复释放 | 同一库存账本原子预留，释放有唯一凭据 | 并发购买不超售；失败、超时、取消各释放一次 |
| 金额或定制内容变化 | 结算重算并冻结，支付通知核对金额和快照 | 改价／改动画版本后旧订单保持原记录 |
| 越权查看或操作 | 查询含 `userId`，服务端重算按钮资格 | 换另一个用户的订单 ID 无法读取地址或修改订单 |
| 支付事实不可信 | 模拟支付只用于测试；微信通知须验签、主动查单、对账 | 未确认资金时不出现“已付款”与可生产订单 |
| 生产竞态 | 取消和入 PB 的最终写入做互斥校验 | 同时发起时只能成功一方；状态与库存一致 |
| 失败后找不到订单 | 保存失败原因、可重试记录和后台提醒 | 顾客能看到真实状态；后台能定位并修复 |
| 旧库迁移记录不一致 | 先备份、核对现有 schema 与迁移账本，再应用新迁移 | 原有历史订单保留，可查询，可恢复 |

## 8. 从设计到开发的顺序

1. **设计定稿**：确认第一轮状态、页面、取消与整单售后政策、60 分钟规则；列出扩展能力的触发条件。用户先审阅本稿。
2. **代码与数据核对**：以当前 `main` 为基线，记录所有订单入口、字段、旧数据、生产消费者和测试库差异。先验证原数据库备份与迁移账本；不通过新建业务库绕开旧数据。
3. **订单与支付基础**：完善快照、库存预留／释放、幂等、真实支付适配边界；测试环境继续虚拟支付，生产环境关闭模拟入口。
4. **60 分钟与生产衔接**：后台设置、付款冻结、候选与最终入批双重检查、取消竞态、生产回归。
5. **前后台页面**：按第 5 节逐页接入，API 结果、类型和中文文案同时验收；历史订单保持可见。
6. **发布准备**：微信支付验签、查单、退款与对账单独实施；权限、并发、恢复、移动端、生产全链路及真实场景验收后才开放收款。

每一阶段先 Git 存档，再改代码，记录修改文件、迁移、接口、测试和遗留风险。实际工作以本稿定稿后的版本为准。
