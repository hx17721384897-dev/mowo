# mowo 订单系统与页面设计

> 2026-10-14 设计稿。本稿说明要实现的功能，并不代表代码已完成。先打通私人定制，联名入口以后复用同一订单骨架。桌面“页面设计”文件夹的 00—03 是本稿的页面、状态和实施细化。

## 1. 产品目标与系统分工

顾客应能从定制商品、层级规格、数量确认，一路完成结算、付款、查单、取消和整单售后。商家在现有订单后台处理交易，在现有生产后台处理生产。两处通过同一 SO（客户总订单）、订单明细、PU（逐件生产任务）和 PB（生产批次）关联；订单后台不能另造生产状态。

成熟订单后台值得借鉴的是可搜索筛选的列表、订单详情中的付款/履约/售后独立记录和操作历史。[订单概览](https://docs.medusajs.com/user-guide/orders)、[订单详情](https://docs.medusajs.com/user-guide/orders/manage)、[订单模块](https://docs.medusajs.com/resources/commerce-modules/order)。mowo 继续用 Vue 3 + TypeScript、Fastify、Prisma 和 PostgreSQL 实现；商品、库存、客户、价格、促销均只有 mowo 一处业务写入，不增加第二个商家后台。

| 业务事实 | 唯一写入方 | 页面如何用 |
|---|---|---|
| 商品、定制作品、动画版本、层级 SKU | mowo 商品和定制模块 | 结算时校验，订单按成交快照展示 |
| 身份和收件信息 | mowo 账户模块 | 本人查询；收件地址留订单快照 |
| 价格、将来的优惠、运费 | mowo 服务端结算 | 只展示真实可核算金额 |
| 可售量、预留、释放 | mowo 库存账本 | 防超卖，释放只做一次 |
| 待付款凭据与正式订单 | PreOrder、SalesOrder、SalesOrderItem | 客户和商家看到同一交易 |
| 支付、退款 | mowo 支付适配层与资金记录 | 模拟付款仅开发测试；以后接微信支付 |
| 生产、批次、发货 | 现有 PU／PB 和发货流程 | 订单后台读取并跳转生产后台 |
| 整单售后 | mowo 售后流程 | 申请、审核、退款结果分别展示 |

## 2. 一笔定制订单如何流动

例：作品 A、动画 V2、5×5 cm 白色 SKU-1 买 2 件；作品 B、8×8 cm 黑色 SKU-2 买 1 件。结算时服务端重新检查作品归属、动画版本、规格组合、SKU、库存和价格，生成不可变的结算快照。提交后先得到待付款凭据；可信支付成功后生成 **一张 SO、两条订单明细、三个 PU**。每个 PU 关联正确的明细和 SKU。顾客只看到一张订单卡；商家可沿 SO → 明细 → PU → PB 找到每件货。

- PreOrder 保存付款前快照、金额、地址、过期时间、库存预留和幂等键。SalesOrder 与 PreOrder 一对一；付款前后在客户界面是一笔交易，不出现两个互不相干的订单。
- 明细冻结来源 CUSTOM/MARKET、作品和动画版本标识、SKU 编码、各层规格、标题/预览、数量、单价、调整与行金额、履约方式。商品以后改价、换图、下架不改旧单。
- 应付、实付、退款中、已退款分别记录；付款或退款有交易流水、时间、金额和结果。不用更改原订单总价表示退款。
- 联名商品以后使用 MARKET 来源和自己的上架、版权及 SKU 校验；本轮只验收私人定制，不能把定制商品 ID 当成联名商品 ID。

## 3. 首轮页面与能力

### 页面文案规则

“我的订单”“订单详情”等功能页直接以功能名称为标题；标题下不放品牌标语、抒情副标题或重复的英文装饰标题。订单卡、详情和帮助区只保留顾客完成任务需要的事实：状态、时间、金额、规则、可用操作和下一步。例：“已付款，最早 15:20 可排产”可以显示；“从下单到制作，每一步都有迹可循”“一份创意，正在等待启程”不使用。空状态也说明实际情况和可执行操作，不写泛泛的宣传句。

| 页面 | 第一轮必须让人看到/做什么 |
|---|---|
| 定制确认、购物车 | 作品、动画版本、完整规格、数量、价格变动、库存异常 |
| 结算 | 最终商品快照、费用、收件资料、支付入口；提交时服务端重算 |
| 待付款/支付结果 | 截止时间、继续支付、结果查询、失败/过期、成功跳正式订单；断网后可恢复 |
| 我的订单列表 | 全部、待付款、进行中、完成、取消、售后；订单号/商品搜索、分页、状态、金额、下一步 |
| 订单详情 | 完整成交快照、费用/付款、最早可开始制作时间、对外制作状态、醒目的物流、收件地址、售后记录 |
| 整单售后 | 原因、说明、凭证、提交结果、审核进度；退款另列 |
| 商家订单列表/详情 | 搜索筛选、客户与金额、付款/生产/物流/售后、异常、关联 PU/PB、操作历史 |
| 生产候选/设置 | 入批阻止原因、最终校验；暂缓履约时长可改并留审计 |

无订单、筛选无结果、失败、无权限、支付结果未知必须分别给中文说明。移动端首屏先有状态、商品和主要操作。没有可信依据时不显示预计发货或送达日期。“最早可排产”不是预计发货。详见《01-我的订单-列表与详情页.md》。

## 4. 状态与操作

| 事实阶段 | 顾客主状态 | 可见操作 | 必须守住的规则 |
|---|---|---|---|
| PreOrder 有效且未付款 | 待付款 | 继续支付、取消 | 过期后旧预留释放一次 |
| 渠道结果未确认 | 支付确认中 | 查询、求助 | 不能凭前端跳转认定付款成功 |
| 付款失败/过期 | 付款失败/已过期 | 重新结算 | 旧凭据不可复活 |
| 付款成功、未进入 PB | 已付款 | 看最早排产时间、符合政策时取消 | SO/明细/PU 完整，取消与入批互斥 |
| 成功进入 PB | 制作中 | 看进度、申请整单售后 | 不提供直接取消 |
| 制作完成未发 | 待发货 | 查看、求助 | 来自真实生产事实 |
| 有有效发货记录 | 运输中 | 查物流、合格时确认收货 | 运单绑定订单/件数 |
| 确认收货 | 已完成 | 查看历史、合格时售后 | 记录确认人和时间 |
| 整单取消成立 | 已取消 | 查退款进度 | 不可继续生产；库存只释放一次 |
| 售后未结案 | 售后处理中 | 查申请 | 不覆盖原付款/生产/物流事实 |

主状态是摘要；付款、生产、发货、售后和退款分开保存。按钮资格由服务端实时返回，点击时再次校验。“制作中”的分界是 **PB 创建成功**，不是 60 分钟过去，也不是已有 PU。细则见《02-订单状态与操作矩阵.md》。

### 客户能看到什么

| 顾客页面可见 | 仅商家/生产后台可见 |
|---|---|
| 客户订单号、成交商品/规格/数量/金额、付款与退款结果、收件信息、可操作项 | PU/PB 编号、生产任务数量、批次候选与阻止原因、工序、产物文件、扫码记录、员工处理备注 |
| “已付款”“制作中”“待发货”“运输中”等对外状态，以及真实发生的时间 | 用于推导对外状态的内部任务状态和关联关系 |
| 发货后的承运商、运单号、可信物流节点和最后更新时间（若已接入轨迹服务） | 生产批次、内部排程、库存账本和物流接口凭据 |

PB 创建成功可以作为“制作中”的内部判定条件，但客户页面和客户订单接口**不得返回批次号、生产任务号或任务列表**。客户页面也不写“已进入生产批次”。顶部保留一处主状态与简明阶段指示；历史事件只有在提供不同信息时才单独展示，不能再做第二块相同的“订单进度”。

物流一旦产生，应在订单详情顶部主状态附近突出显示；没有真实运单时不占用独立的物流大卡片。已决定接入自动轨迹查询/订阅，并保留运单复制及承运商官方查询入口作为备用。具体服务商在接入批次确定；未接通前只展示已绑定的承运商和运单号，不能宣称本站正在监控物流。轨迹节点要记录来源和最后更新时间；接口异常时显示“物流信息暂时无法更新”，不猜测运输位置。

### 60 分钟暂缓履约

默认 60 分钟。管理后台可修改未来订单的分钟数，变更留下操作者、时间和旧/新值。付款确认时冻结该订单适用分钟数与最早可入批时间；设置变化**只影响后付款成功的订单**，已付款订单保持原时间。候选列表显示阻止原因；创建 PB 的最终事务和所有旁路入口均检查时间、未取消和未入批。到时间不会自动生产。

等待期内以及到期但尚未入批时，符合政策的整单取消可执行；入批后转售后。取消与入批同时发生时只能成功一个。已付款取消后可写“退款待处理/处理中”；资金渠道确认前绝不写“已退款”。退款具体期限在微信支付规则定稿时确定。

### 整单售后边界

第一轮只允许整张 SO 申请售后，类型先保留退款诉求和质量问题，填写原因、说明及必要凭证。申请、审核、退款各有结果与时间线。当前 AftersaleRequest 关联单个 PU，现有操作还会改写多项订单/任务状态；开发时须改成明确关联 SO 的整单申请，迁移旧记录并保留原生产事实。逐件退换、部分退款、多包裹、订单编辑、优惠、发票、游客查询和再次购买保留扩展位置，未有后端规则前不出现可点击入口。

## 5. 商家界面与接口对照

商家管理只用现有导航中的两个工作区：**订单管理**负责查单、付款事实、取消/售后、发货摘要和异常；**生产管理**负责候选、批次、单件生产和产物。订单详情可跳关联 PU/PB，生产页可回 SO。列表展示订单号、时间、来源、客户（按权限脱敏）、件数、实付、支付、生产、物流、售后与异常；详情按摘要、商品、费用/支付、履约/物流、售后、时间线排布。关键操作记人、时间、原因和前后结果。导出按岗位授权并限制敏感字段。

| 页面行为 | 已有代码基础 | 本轮补齐 |
|---|---|---|
| 结算和付款状态 | /api/cart/checkout、/api/payment/status/:preOrderId、模拟付款 | 待付款入口、过期/失败恢复、可信支付与 SO 跳转、生产关闭模拟入口 |
| 我的订单 | /api/orders/mine 当前只列 SO；/api/orders/:id | PreOrder 与 SO 统一体验，服务端搜索筛选分页及状态摘要 |
| 取消 | /api/orders/:id/cancel | 待付款取消；已付款取消、库存、退款记录与入批互斥 |
| 收货 | /api/orders/:id/confirm-receipt | 发货事实、全件数、重复请求与权限核对 |
| 售后 | /api/orders/:id/aftersale 当前经 PU 关联 | SO 级申请、历史、审核和独立退款记录 |
| 生产批次 | 现有 PB 候选和创建路由 | 候选、最终事务和旁路校验暂缓时间及取消 |
| 发货 | 现有运单及生产字段 | 唯一发货写入口；整单/分件边界明确 |
| 设置与记录 | 现有管理基础 | 暂缓分钟数、岗位权限、变更记录和时间线 |

“已有基础”不表示已满足设计。尤其支付回调、售后关联、订单列表与入批检查要在代码审查后改造。每个新增接口写清身份、输入、幂等、成功/失败和对应中文页面文案。

## 6. 开发与验收顺序

1. 定稿页面和取消/售后规则，Git 存档；备份核对现有 mowo_db、历史订单与迁移账本，不另建业务库绕过旧数据。
2. 完善快照、层级 SKU 校验、库存预留/释放、幂等、支付事实、SO/明细/PU 原子建单；开发环境用模拟支付。
3. 加设置、付款冻结、入批双重校验、取消竞态，回归现有生产流程。
4. 逐页接入购物车、结算、结果页、我的订单、订单详情、商家订单、售后；状态与按钮和服务端结果同步。
5. 上线前单独完成微信支付验签、主动查单、退款、对账、故障补偿和环境隔离。

每步记录修改文件、迁移、接口、旧数据处理、测试和遗留风险。验收包括：重复点击/回调只产生一张 SO；两条明细准确对应三个 PU；并发购买不超卖；取消与入批只成功一方；修改暂缓时间不改变已付款订单；他人不能读取地址或凭证；未退款不显示已退款；旧订单在商品更新或数据迁移后仍可查。详见《03-页面流程与实施建议.md》。
