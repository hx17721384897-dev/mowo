# Web 商品、定制、交易与生产全链路

> 核对日期：2026-09-04。
>
> 本文把用户从“逛联名款或制作私人定制”到“合并购物车、交给微信小程序付款、进入生产并发货”的整条路线放在一张图里。它既记录已经实现的代码事实，也记录首发目标和当前断点。两者不得混为一谈。
>
> 本轮不开发微信小程序，但必须把 Web 交给小程序什么、小程序完成后回传什么、付款成功如何进入生产说明清楚。

## 1. 一句话说明这套业务

用户可以把两类商品放进同一个购物车：

- **联名款**：从已经审核并上架的联名作品中选择标准 SKU。
- **私人定制款**：上传视频、GIF 或图片组，自行筛帧或请工作人员筛帧，再选择适配的标准 SKU。

Web 负责选商品、制作动画、选择款式、合并购物车和生成交易准备记录；微信小程序负责微信身份确认、订单确认和付款；支付结果由服务器可信确认后，系统才建立正式订单，并把订单中的每一个实物拆成可生产、可扫码、可追踪的单件任务。

简单说：**一辆购物车可以同时装联名款和私人定制款，一次付款形成一张订单；但订单里的每一件实物仍有自己的生产编号。**

## 2. 本文范围

### 包含

1. 联名商品浏览、详情、SKU 和加入购物车。
2. 私人定制的两条筛帧路线、动画资产和版本。
3. 使用已有动画再次购买其他款式。
4. 混合购物车、地址、价格确认和 Web 交易准备。
5. Web 扫码进入微信小程序的安全交接协议。
6. 支付成功后的正式订单、订单商品和单件生产任务。
7. 生产批次、打印、领料、配对、装箱、发货和用户订单状态。
8. 下架、价格变化、库存、重复提交、超时、退款和生产失败等异常分支。

### 本轮不包含

- 微信小程序页面和微信支付代码的实际开发。
- 创作者线上分红、牛量、余额、提现和自动结算。
- 社区点赞、关注和内容流。
- 组装完成款产线；当前生产闭环以材料包款为主。
- 售后全部细节和退款渠道实现；本文只规定它们必须接在什么位置。

## 3. 已确认的产品规则

1. Web 不直接收款，以降低首发许可证、主体和支付接入复杂度。
2. 未登录用户可以浏览；点击加入购物车或提交定制时必须登录。
3. 首发只支持微信小程序承接真实付款。
4. 私人定制是用户为自己购买，不因为进入系统就自动成为可销售联名作品。
5. 私人定制首发不做内容上架审核；系统只需保证文件安全、规格适配和可生产性。未来加强监管时另行增加内容治理。
6. “自己筛帧”不需要工作人员确认帧图；“工作人员筛帧”必须由用户播放并确认工作人员返回的结果。
7. 私人定制和联名款都使用后台维护的标准 SKU 和固定价格，不允许用户议价。
8. 创作者身份、企业微信沟通和合作优惠是旁路，不阻断普通私人定制付款。
9. 同一套动画资产可以长期保留，并再次购买不同 SKU；修改动画时建立不可变的新版本，旧订单继续使用旧版本。
10. 一次结算只能填写一个收货地址；需要多个地址时必须分成多张订单。
11. 同一购物车可以同时包含联名款和私人定制款。
12. 普通同款单次购买数量上限暂按 10 件；更大数量转企业微信人工处理。
13. 联名款后台可以优先使用现货；没有现货时进入现做。用户端不必区分“预制”或“现做”，但必须看到真实预计发货时间。
14. 正式订单只有在服务器确认支付成功后建立，不能把前端显示“支付成功”当成付款依据。

## 4. 核心对象和编号

| 对象 | 当前编号/模型 | 什么时候出现 | 用途 |
|---|---|---|---|
| 动画资产 | `ANM` / `AnimationAsset` | 用户或员工确认一套可保存帧图时 | 表示“这套动画是谁的、能做什么”，可长期复购 |
| 动画版本 | `V1/V2...` / `AnimationAssetVersion` | 第一次确认或以后修改动画时 | 保存不可变帧顺序；旧订单永远引用购买时版本 |
| 定制项目 | `DZ` / `CustomizationRequest` | 正式开始一项定制申请时 | 记录一次筛帧和选款式过程，不等于订单 |
| 购物车条目 | `CartItem` | 选择联名 SKU 或定制 SKU 加入购物车时 | 表示用户准备购买的一行商品 |
| 交易准备记录 | 当前 `PreOrder` | Web 点击结算时 | 保存付款前整单快照；未来还需增加安全的小程序领取码 |
| 正式用户订单 | `SO` / `SalesOrder` | 服务器可信确认支付成功后 | 一次付款、一处地址、一张用户可见订单 |
| 订单商品行 | `SalesOrderItem` | 建立 `SO` 时 | 记录一种购买内容、SKU、动画版本、单价和数量 |
| 单件生产任务 | `PU` / `CustomizeOrder` | 建立 `SO` 时按数量展开 | 每一件实物一个任务，防止两份商品只生产一份 |
| 生产批次 | `PB` | 后台选中已付款订单排产时 | 记录一次生产导出和后续扫码范围 |
| 帧素材包 | `FP` | 生产资料生成/打印时 | 唯一对应某个 `PU` 的动画、版本、规格和打印份数 |
| 材料包/箱码 | `KB/BX` | 材料包组装入库或领用时 | 追踪标准材料包来源和领用 |

### 编号关系

```text
ANM 一套动画资产
 └─ V1 / V2 / V3 不可变版本

DZ 一次定制过程
 └─ 选择 ANM 的某个版本 + 一个或多个 SKU

Cart
 ├─ MARKET 联名款 + SKU + 动画版本
 └─ CUSTOM 私人定制 + DZ + SKU + 动画版本

PreOrder 付款前整单
 └─ 支付成功 -> SO
                  ├─ SalesOrderItem A，数量 2
                  │   ├─ PU-01 -> FP-01
                  │   └─ PU-02 -> FP-02
                  └─ SalesOrderItem B，数量 1
                      └─ PU-03 -> FP-03

多个 PU -> PB 生产批次 -> 打印/领料/配对/装箱 -> SO 发货
```

## 5. 目标主流程

### 阶段 A：浏览联名款

1. 用户进入联名作品列表。
2. 服务端只返回同时满足“作品审核通过、允许销售、当前上架、关联 SKU 可用”的作品。
3. 用户进入唯一的联名详情页，查看真实封面、作品信息、可选 SKU、价格、可购买数量和预计发货时间。
4. 用户选择 SKU 和数量。
5. 未登录时点击购买，先跳登录；登录完成后返回原详情页，并保留原来的 SKU 和数量选择。
6. 已登录时加入服务器购物车。

#### 联名款加入购物车前必须再次检查

- 作品仍在售，不能通过旧链接购买已下架或暂停销售的作品。
- SKU 仍启用，并且确实属于该作品允许销售的规格。
- 服务端计算最终价格，前端传入的金额一律不可信。
- 创作者加价、活动价或其他组成必须形成同一套价格快照，详情、购物车、结算和订单不能各算一套。
- 数量在 1 至 10 之间；超过上限引导企业微信。
- 购物车保存动画资产和版本的稳定引用，不能只保存会过期的图片链接。

### 阶段 B：制作私人定制

#### 路线 B1：用户自己筛帧

1. 用户选择机型入口或进入创作中心。
2. 登录后上传视频、GIF 或按顺序命名的图片组。
3. 文件进入私有存储，服务端登记所有者、用途、大小、类型、校验状态和生命周期。
4. 用户在筛帧器中选择片段、抽取核心帧、调整顺序并播放预览。
5. 用户确认筛帧结果后，系统保存 `DZ`，并建立或关联 `ANM + Vn`。
6. 系统根据核心帧数筛选兼容 SKU。例如 4 个核心帧可以适配 12、16、24 等 4 的倍数规格。
7. 用户选择一个或多个标准 SKU，加入购物车。

这条路线不需要工作人员确认帧图。工作人员以后在生产异常或售后环节介入，不应在提交订单前增加无依据的审核门槛。

#### 路线 B2：请工作人员筛帧

1. 用户上传原素材并提交人工筛帧申请，生成 `DZ`。
2. 后台任务进入待处理队列；员工可以领取、筛帧、播放预览和提交结果。
3. 用户在自己的定制页查看工作人员返回的帧图。
4. 用户满意时点击确认，系统建立或更新 `ANM + Vn`，再进入 SKU 选择。
5. 用户不满意时请求重新处理，形成新处理记录，不覆盖已经确认的旧版本。
6. 用户选择一个或多个兼容 SKU，加入购物车。

#### 路线 B3：使用已有动画再次购买

1. 用户从“我的动画”进入某个 `ANM`。
2. 选择现有不可变版本，例如 V1。
3. 系统只展示与该版本核心帧数兼容的 SKU。
4. 用户选择新 SKU 后建立新的 `DZ/CustomProduct` 购买上下文，但不重复上传原素材。
5. 加入购物车时明确锁定 `ANM + V1 + SKU`。

#### 路线 B4：修改已有动画后再购买

1. 用户从已有动画发起修改。
2. 修改完成后建立 V2，不覆盖 V1。
3. 新购物车条目引用 V2；已经在购物车或旧订单中确认使用 V1 的内容仍使用 V1。

### 阶段 C：混合购物车

购物车可以同时出现：

- 联名款 `MARKET` 条目。
- 私人定制 `CUSTOM` 条目。
- 同一动画的不同 SKU。
- 不同动画的不同 SKU。
- 同一商品多份数量。

用户勾选本次要结算的条目，未勾选的仍留在购物车。结算前服务端必须把所有选中条目作为一个整体重新核验；只要其中一行失效，就不能悄悄跳过后继续收费。

#### 结算前统一核验

1. 条目属于当前账号且状态有效。
2. 联名作品仍在售；私人定制已经确认。
3. SKU 启用、规格兼容、数量合法。
4. 动画资产和版本存在，用户有权购买，且版本未被替换。
5. 价格与加入购物车时一致；若变化，明确提示用户重新确认。
6. 地址完整且经过服务端校验。
7. 库存或现做能力满足销售承诺。
8. 同一个点击或网络重试只能产生一个交易准备记录。

### 阶段 D：Web 生成交易准备记录

用户点击的按钮应表达为“生成订单并使用微信支付”或“前往微信小程序确认”，不能写成 Web 已经能够直接付款。

Web 后端生成一份付款前整单快照，至少冻结：

- 当前用户。
- 选中的购物车条目。
- 每行商品类型、标题、封面对象键、SKU、动画资产、动画版本、数量和单价。
- 优惠、运费、应付总额和币种。
- 收货地址快照。
- 用户已确认的定制例外说明。
- 创建时间、有效期和稳定幂等键。

当前代码使用 `PreOrder`，有效期为 10 分钟。这个模型可以继续作为基础，但不应在用户还没打开小程序时就直接开始很短的支付倒计时。

### 阶段 E：Web 与微信小程序交接

推荐把“领取交易”和“微信支付倒计时”分成两个阶段：

1. Web 创建交易准备记录后，生成高强度随机的一次性 `handoffCode`。
2. 数据库只保存领取码摘要；二维码或小程序链接只携带领取码，不暴露可猜测的订单 ID。
3. Web 展示二维码和短码，并轮询该记录状态。
4. 用户在微信小程序登录，绑定并验证手机号。
5. 服务端核对小程序手机号与 Web 账号；不一致时拒绝领取并提供明确说明。
6. 第一次成功领取后绑定到该微信身份，其他账号不能再次领取。
7. 小程序展示完整商品、数量、地址和应付金额，由用户最后确认。
8. 用户确认后才创建微信支付单，并开始较短的支付有效期。
9. 取消或超时后释放临时库存；购物车原内容仍可恢复，不应丢失。

建议状态：

```text
UNCLAIMED -> CLAIMED -> PAYMENT_CREATED -> PAID
      |          |             |
      +----------+-------------+-> EXPIRED / CANCELLED
```

具体的领取有效期、支付有效期和重新生成规则在开发小程序前最终确认。建议领取窗口长于支付窗口，例如领取 30 分钟、创建微信支付单后 10 至 15 分钟。

### 阶段 F：可信支付确认

1. 微信支付服务器通知后端。
2. 后端验证平台签名、商户号、应用号、金额、币种、交易状态和通知唯一号。
3. 后端按支付流水号和交易准备记录做幂等处理。
4. 在同一数据库事务内建立 `SO`、`SalesOrderItem` 和按数量展开的 `PU`，并清理或标记已购买购物车条目。
5. 重复通知只能返回已成功，不能再建第二张订单或重复占库存。
6. Web 和小程序查询到服务器状态 `PAID` 后再显示付款成功。

不得让普通前端直接调用一个“告诉服务器我已付款”的接口。开发环境的模拟支付必须由环境开关隔离，生产永久关闭。

### 阶段 G：付款后进入生产

1. 正式订单初始为“已付款”。
2. 后台选择订单建立 `PB` 生产批次；同一张 `SO` 的所有商品原则上进入同一批次并齐套发货。
3. 系统检查每个 `PU` 是否具备 SKU、动画版本、帧文件、模板和完整地址。
4. 导出地址后，订单进入处理中；录入并绑定快递面单后进入待生产。
5. 导出生产资料时，系统按打印裁切组排序，生成 Word、打印份数、材料包需求和唯一 `FP` 标签。
6. 帧素材线打印、裁切、装袋并扫描 `FP` 完成。
7. 材料线按批次领取标准材料包并扫描领用。
8. 配对岗位扫描 `FP` 和材料包码，系统核对它们是否属于同一 `PU` 和兼容 SKU。
9. 装箱岗位先扫描快递面单，再扫描订单所需全部 `FP`；齐套后才能完成装箱。
10. 发货后更新 `SO` 和全部相关单件任务，用户在订单页查看物流。

#### 混合订单的生产要求

- 联名款也必须携带它对应的 `ANM + Vn`，否则无法生成打印文件。
- 私人定制必须使用用户付款时锁定的版本，不能因为后来产生 V2 就改印 V2。
- 数量为 2 时必须生成两个 `PU` 和两个唯一 `FP`，Word 清单明确打印两份。
- 一张订单有多个商品时，任一件未装箱都不能把整单标成已发货。
- 指定页返工生成新 `FP`，旧码失效；批次总览直观显示返工环节和当前有效版本。

## 6. 目标状态变化

### 交易准备记录

```text
待领取 -> 已领取 -> 待支付 -> 已支付
   |         |         |
   +---------+---------+-> 已过期 / 已取消
```

### 正式订单

```text
已付款 -> 待处理 -> 处理中 -> 待生产 -> 生产中 -> 待发货 -> 已发货 -> 已收货
                                      |
                                      +-> 返工后回到对应生产环节
```

代码内部目前主要使用：

```text
paid -> locked -> processing -> producing -> shipped -> received
```

页面中文与数据库英文必须只有一张映射表，不能由每个页面分别解释。

### 取消与售后

- 未支付：取消交易准备记录，释放临时占用，不生成正式订单。
- 已支付但未进入生产：允许用户申请取消，退款成功后释放库存并关闭 `SO/PU`。
- 已进入生产：不能直接按钮取消，进入客服/售后判断，避免已经制作的私人内容无人承担成本。
- 已发货：按标准商品和私人定制的不同规则处理退换；退回材料先进入隔离检查，不能直接增加可售库存。

## 7. 价格、库存和快照规则

### 价格

同一商品只能有一套服务器价格来源。联名款最终价可由“SKU 基础价 + 已启用的创作者加价/活动规则”组成，但必须在以下位置完全一致：

1. 商品详情。
2. 购物车。
3. Web 结算。
4. 小程序确认。
5. 微信支付金额。
6. `SalesOrderItem` 历史快照。

价格变化时不自动替用户接受；结算必须返回“价格已变化，请重新确认”。

### 库存

需要区分三件事：

- 联名成品库存：有货时优先发现货。
- 标准材料包库存：私人定制和联名现做都可能消耗。
- 现做能力：没有联名成品库存不等于一定停售。

因此不能简单用“联名成品库存为 0”把商品标成不可购买。首发应由 SKU 配置决定它是“仅现货销售”还是“允许现做”，并据此计算可售状态和交期。

### 不可变订单快照

付款后的订单必须保留购买时事实：

- 商品标题和封面对象键。
- SKU 名称、尺寸、材质、帧数、颜色和款式。
- 动画资产 ID 和不可变版本 ID。
- 单价、优惠、数量和总额。
- 收货地址。
- 联名作品、版权/销售授权关系的稳定引用。

图片访问地址可以过期，因此数据库应保存私有对象键或文件 ID，需要显示时再生成短期签名地址，不能只保存临时 URL。

## 8. 重要异常分支

| 情况 | 推荐处理 |
|---|---|
| 未登录点击加入购物车 | 登录后返回原页面并恢复选择，不建立无法读取的游客购物车 |
| 联名作品加入购物车后下架 | 条目标记失效，禁止结算并说明原因 |
| SKU 停用或规格改变 | 禁止结算；已付款订单继续使用历史快照 |
| 价格变化 | 显示旧价和新价，用户主动确认后更新购物车 |
| 定制后来产生 V2 | 已锁定 V1 的购物车/订单不自动换成 V2 |
| 一次结算部分条目失效 | 整次结算暂停，由用户处理失效条目后重试 |
| 用户重复点击结算 | 相同幂等键返回同一交易准备记录 |
| Web 刷新或网络超时 | 能恢复二维码和当前状态，不创建重复记录 |
| 二维码被别人拍到 | 必须登录、核对手机号、一次领取并绑定微信身份 |
| 领取码过期 | 原记录关闭、释放占用；用户可从购物车重新生成 |
| 支付通知重复 | 返回同一 `SO`，不重复建单或扣库存 |
| 支付金额不一致 | 拒绝落单并告警，不能按前端金额放行 |
| 已付款但打印文件缺失 | `SO` 保持已付款，生产批次明确阻断原因并通知员工补模板/文件 |
| 同一订单一件返工 | 只让对应 `PU/FP` 回到返工环节，整单等待重新齐套 |
| 支付失败或超时 | 释放预留库存；当前代码的定时任务会处理超时，但失败回调路径仍需统一核对 |
| 取消订单释放库存失败 | 订单不能静默成功；记录补偿任务和告警，后台可重试 |

## 9. 当前代码已经完成什么

### 已基本形成闭环

- 用户自己筛帧、工作人员筛帧、用户确认结果和选择兼容 SKU。
- `DZ` 定制项目、`ANM` 动画资产和不可变版本。
- 已有动画复购，以及修改后生成 V2、旧购买保留 V1。
- 登录用户的服务器购物车可以容纳 `CUSTOM` 和 `MARKET` 两种条目。
- 结算页可以选择地址并把多条购物车内容提交为一份 `PreOrder`。
- 支付回调建立一张 `SO`、多条 `SalesOrderItem`，并按数量展开多个 `PU`。
- 正常材料包款生产路径：`PB`、地址、面单、Word、领料、四岗位扫码、返工、齐套和发货。
- `PreOrder` 超时定时任务会释放 `MARKET` 预留库存。
- 正式订单取消接口会检查是否已进生产，并尝试释放联名款库存。

### 当前只能算“开发演示”

- Web 结算页仍以“立即支付”表达，并只显示“小程序接入中”，没有二维码、一次性领取码或身份绑定。
- 支付成功主要依赖开发 Mock；真实微信支付尚未接通。
- 小程序已有页面骨架，但与当前主后端的交易契约未闭环。
- 当前自动测试分别覆盖定制、订单结构和生产，尚未覆盖一张真实的 `MARKET + CUSTOM` 混合订单从商品页一直走到发货。

## 10. 当前发现的断点和风险

### P0：不解决就不能接真实付款

1. **支付回调未验证微信签名。** 当前 `/api/payment/callback` 留有签名验证 TODO；知道交易准备记录的人可能伪造支付成功。
2. **没有 Web 到小程序的安全领取链路。** 当前没有一次性领取码、领取状态、微信身份绑定和防多人领取。
3. **联名款付款后缺动画生产资料。** 支付落单时只从私人定制读取动画资产/版本/帧文件；`MARKET` 商品没有把 `CollabWork` 的动画版本写入订单商品和 `PU`，生产批次会因缺帧文件而阻断。
4. **联名价计算不一致。** 详情页展示 SKU 价格加创作者加价，但购物车和订单目前主要使用 SKU 基础价，可能出现“看到一个价、实际按另一个价落单”。
5. **公开联名详情校验不完整。** 列表和详情对审核/上架条件的检查不同，旧直链可能访问已暂停或未正式上架的作品。

### P1：主流程需要补齐

1. 两个联名详情页同时存在并互相导流，功能和 UI 有差异，应合并为唯一页面。
2. 联名详情页建立了本地游客购物车，但正式购物车只读取服务器数据；这与“购买时登录”的规则冲突。
3. 联名推荐读取了错误字段，部分推荐内容可能不显示。
4. 商品页数量上限仍可到 99，未统一为首发 10 件。
5. 购物车中的联名作品没有完整复核在售状态；封面字段名也存在不一致。
6. 当前 10 分钟 `PreOrder` 把领取期和支付期混在一起，用户扫码稍慢就可能过期。
7. 结算前端没有发送稳定幂等键，重复点击或网络重试存在重复交易准备记录风险。
8. 库存预锁和 `PreOrder` 创建没有完全处在同一个事务内，服务异常时依赖手工回滚。
9. 地址主要由前端验证，服务端还需补完整性、长度和格式校验。
10. 联名无成品库存时当前倾向标记缺货，与“允许现做”的业务规则冲突。
11. 购物车读取逐条查询商品、SKU 和库存，条目较多时会形成大量数据库请求。
12. 付款失败、过期查询和定时释放应收口到同一幂等库存补偿函数，避免不同路径结果不一致。

### P2：上线质量和体验

1. 联名详情中的销量、评分、评价数、发货和售后承诺含硬编码演示值，应接真实数据或删除。
2. 前端 API 地址仍有本机 `127.0.0.1` 写法，部署时必须统一环境配置。
3. 订单和购物车应保存稳定文件 ID/对象键，展示时生成短期签名地址。
4. 支付、领取、价格变化、库存补偿和生产阻断需要脱敏审计和告警。
5. 真实用户素材上线前仍缺恶意文件扫描、正式私有 OSS、备份恢复和容量验证。

## 11. 推荐开发批次

### 批次 2A：统一联名商品入口

- 合并两个联名详情页。
- 统一公开上架条件、价格公式、数量上限和登录回跳。
- 删除无效游客购物车和演示承诺。
- 修复推荐、封面和购物车在售复核。
- 让联名购物车明确锁定 `ANM + Vn + SKU`。

完成标准：已上架联名款能加入服务器购物车；下架、暂停、错 SKU、超量和价格变化都会被服务器正确拦截。

### 批次 2B：统一混合购物车和结算快照

- 为 `CUSTOM` 与 `MARKET` 建立同一套服务端快照和复核器。
- 固定动画版本、最终价和文件引用。
- 补稳定幂等键、服务端地址校验和事务化库存预占。
- 明确“仅现货/允许现做”和交期规则。

完成标准：一件联名款和一件私人定制款可以一次结算；重复点击只有一个交易准备记录。

### 批次 2C：修复付款后的订单生产资料

- 支付落单同时为联名款写入动画资产、版本和帧文件来源。
- 用同一构建器建立 `SO/Item/PU`，不再按商品类型分成两套不完整逻辑。
- 补混合订单从 Mock 支付到建立生产批次的自动测试。

完成标准：混合订单付款后，每个 `PU` 都能生成正确的 `FP` 和 Word，不因联名款缺帧而阻断。

### 批次 3A：Web 到小程序交接协议

- 增加领取码摘要、领取状态、领取身份、过期和重发机制。
- Web 展示二维码、短码和实时状态。
- 定义小程序领取、手机号核对和订单确认 API。

完成标准：一份交易只能由匹配账号领取一次；刷新和重试不重复建单。

### 批次 3B：微信支付

- 接入微信商户配置、服务端下单、签名验证、证书轮换和支付查询。
- 服务器金额校验、回调幂等、失败补偿和每日对账。
- 生产永久禁用 Mock。

完成标准：真实沙箱/测试商户付款能可靠建立一张 `SO`，重复回调和伪造回调测试均通过。

### 批次 2D/4A：完整回归与上线准备

- 混合订单、数量、多 SKU、多页打印、返工、取消、超时和发货全链路测试。
- 恶意文件扫描、正式 OSS、备份恢复、监控告警和压测。

## 13. 仍需负责人最终确认的少量产品参数

以下问题不阻止先修 P0/P1 结构，但在开发对应批次时需要确认：

1. Web 领取码的有效时间，以及领取后允许多久才创建微信支付单。
2. 联名 SKU 是“仅现货”还是“允许现做”的后台配置方式和预计交期文案。
3. 联名创作者加价是否直接进入商品固定售价，首发是否完全不展示拆分。
4. 支付前价格变化后，是整单重新确认还是只确认变化条目。
5. 企业微信人工收款的临时兜底是否上线；若上线，必须有人工核销、付款凭证、操作审计和防重复落单规则。
6. 私人定制开始生产后的取消成本和售后口径。

在这些参数确认前，系统仍应坚持四条底线：金额由服务器算、支付由可信渠道确认、动画版本不可变、每件实物都能追踪到唯一生产任务。
