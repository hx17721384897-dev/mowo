## 模块职责

该业务域连接四件事：

1. 认证创作者把自己的动画申请为联名作品，平台审核、上架和管理帧素材。
2. 联名作品成交后记录创作者分红，经历收货、冷却、结算、提现和储备金释放。
3. 牛量系统根据投稿、外部声量和推广转化调整等级，进而影响未来分红率。
4. 大 IP 商务合同独立于标准分红体系，由管理员记录条款和打款。

当前页面和模型覆盖面较完整，但资金闭环、推广归因和部分上下架状态仍未真正接通，不能按“企业级可上线财务系统”理解。

## 已确认的上线阶段与业务边界

1. 首发不启用线上分红率、牛量等级、推广归因、创作者余额、提现和收益仪表盘。相关页面和路由应默认关闭，不能因为代码存在就对外形成可用承诺。
2. 初期联名合同在线下签署，合作方不必注册平台账号。合同主体应能独立表示个人、工作室、公司或其他 IP 权利方，平台账号只是可选关联；未来线上查看收益或提现前再绑定并验证账号。
3. 初期分红由平台与创作者线下约定和处理，并在现有管理后台内增加仅供授权员工使用的简化合作台账。台账用于关联合作主体、联名作品、线下约定、销售/应付依据、实际付款和凭证；不向创作者开放、不提供自主提现，也不等同于未来完整分红系统。具体字段和复核流程在开发该功能时确认。
4. 平台可由员工人工给少量账号标记“合作创作者/优惠资格”，用于开放约定的定制工具能力或标准购买优惠。该标签不代表可靠实名、线上合同或自动分红身份；权限、优惠、审批依据和有效期需要另行确认并留痕。
5. 创作者规模扩大后再建设线上收益体系和用户可见仪表盘。未来必须区分收益预估、收益确认/可提现、提现申请、审核、实际付款、失败/退回等事实；“结算”不能等同于“钱已打出”。
6. 现有分红、储备金、牛量、提现与推广代码保留为代码事实和未来重构参考，但在启用前必须重新确认规则、统一账本与订单快照，并完成安全、财务和对账验收。
7. 未生效且没有关联资金或履约事实的合同草稿可以按权限删除；正式合同、结算、付款和其他财务记录不得物理删除，只能作废、归档或冲正，并保留原因、操作人、时间和原记录。
8. 联名作品下架后立即关闭商城、搜索和公开分享访问。历史买家只能查看成交时商品快照、履约和售后信息，不得读取创作者原帧；创作者本人和授权员工按合同、运营、生产或售后用途受控访问，私有素材访问必须留痕。

## 2026-08-13 首发关闭实现

- 经审核联名作品展示和购买入口继续开放，前台名称由“创意社区”改为“联名作品”；这不是社区重新上线。
- `CREATOR_FINANCE_ENABLED=false` 时，收益/提现、结算和分红配置 API 由服务端拒绝，财务定时任务不启动；支付、用户确认收货、后台确认收货均不创建或推进线上分红记录。
- `BULL_SYSTEM_ENABLED=false` 时，牛量、推广链接 API 关闭，每日牛量任务不启动。
- `CREATOR_COLLAB_SELF_SERVICE_ENABLED=false` 时，创作者在线申请、修改联名和加价等自助接口关闭；普通定制与人工联系合作继续可用。
- 管理后台隐藏结算、牛量和引流入口；合同、联名作品、联名审核与内部台账相关页面继续保留。
- 联名审核仍能批准作品并生成展示素材；财务关闭时 `revenueRate=0`，通知明确合作与结算以线下确认记录为准，不展示自动分红承诺。
- 未来恢复任一开关前，必须重新确认业务规则并完成账本、退款冲正、对账、权限、安全和回归测试；不能只把环境变量改为 `true` 就直接上线。

## 技术实现

- Fastify 路由 + Prisma/PostgreSQL。
- 联名原帧和 ZIP 帧包保存在阿里云 OSS；公开/创作者/管理员接口返回预签名读取 URL。
- 分红率由 `lib/revenue.js` 读取 `PlatformConfig` 后计算。
- 冷却期、储备金释放和牛量计算由 API 进程内 Scheduler 执行。
- 联名金额、储备金、合同金额和结算金额大量使用 JavaScript `Number` 与数据库 `Float`；旧收益和余额使用 `Decimal`。
- 多个复杂字段以 JSON 字符串保存，包括帧列表、支持 SKU、创作者加价、变更记录和合同打款日志。

## API 与权限

### 公开与普通登录用户

- `GET /api/collab/works`、`GET /api/collab/works/:id`：联名作品展示。
- `POST /api/collab/works/:id/view`：匿名有效浏览登记；同一商品、指纹和 UTC 日期只计一次，不保存明文身份或 IP。

### 认证创作者

- `/api/collab/apply`、`/api/collab/my-works`：批量申请和自己的作品。
- `/api/creator/collab/*`：作品详情、修改版、加价、帧包和统计。
- `/api/creator/notifications/*`：通知。
- `/api/creator/settlement/*`：联名分红和储备金查询。
- `/api/creator/bull/*`：牛量状态、变动日志和推广链接。
- `/api/creator/links/social`：外部视频链接。
- `/api/earnings/*`：旧收益余额、提现和提现记录。

创作者身份校验有两种实现：部分接口只看 Token 的 `role >= 1`，部分只看 `certifyStatus === 2`。封禁、限制和认证撤销不会统一实时查询数据库，继承第一批认证模块的状态缓存风险。

### 管理员与超级管理员

- `role >= 2` 可审核和上下架联名、管理活动/帧包、执行内部结算、调整牛量、审核外链、编辑合同和录入合同打款。
- `role = 3` 才能修改分红参数、违约政策和删除合同。
- 金额入账、合同条款编辑和记录付款目前没有经办/复核双人机制。

## 联名申请与展示流程

### 当前申请

1. 认证创作者从 `CustomProduct` 或自己的 `CustomizeOrder` 选择动画来源。
2. 单次最多提交 20 款，勾选授权协议，并选择 SKU 和可选活动。
3. 服务端可能先把 Data URI 原帧逐张上传 OSS，再校验 SKU 并创建 `CollabWork`。
4. 管理员审核时计算分红率；2026-09-04 起审核通过后保持下架，必须完成正式销售配置并由管理员明确上架。
5. 后台异步生成 hover GIF；任务只存在于 API 进程内，不持久化。

已确认的问题：

- 从订单申请时只排除 `pending`，取消、售后等非有效订单也可能成为联名来源。
- 活动只检查启用和未结束，不检查是否已经开始。
- 原帧先上传、SKU 后校验，失败申请会留下孤立 OSS 文件。
- Data URI 的 MIME 和扩展名来自客户端，没有图片白名单、尺寸、解码验证或内容扫描。
- 20 款及大量帧逐张串行上传发生在一个 HTTP 请求里，容易超时并占用 API 内存和连接。
- 新手作品序号由“已通过数 + 待审数”临时计算，并发提交可能超过前 N 款限制。

### 当前公开范围

- 2026-09-04 起，列表、详情和购物车共同要求 `status=approved + isOnShelf=true + shelfStatus=on_sale + isRevision=false`，并要求有效动画资产、版本、封面和至少一个已启用的正式销售 SKU。
- 公开列表和详情使用明确字段白名单，不返回审批人、分成、加价拆分、内部下架原因、修改记录和其他后台字段。
- 公开联名点赞路由及响应中的点赞字段已经移除，首版货架不再依赖社区开关。
- 列表已改为服务端分页，每页最多 24 条；支持商品/创作者搜索、创作者筛选以及推荐、最新、热门三种服务端排序。
- 卡片直接读取轻量预览帧、最低价、规格和交期摘要，不再逐卡请求完整详情。
- 正式详情可见 3 秒后登记有效浏览，同一匿名指纹对同一商品按 UTC 日期只计一次；后台预览排除，热门依据汇总值排序。
- 后台销售配置已强制保证核心帧与 SKU 兼容、最终售价不低于基础价、交期有效；所有恢复销售路径也复用同一完整性检查。
- `CollabWork.supportedSkus/creatorMarkups` 暂时由正式配置自动同步，用于兼容尚未迁移的旧申请代码；公开接口和购物车不再读取它们。

### 修改版

创作者提交修改时会创建一条 `isRevision=true` 的影子记录。审核通过后，代码先把影子记录本身改为 `approved + 上架`，再把部分字段覆盖回原作品。公开查询没有排除修改版，因此原作品和影子记录可能同时公开，形成重复商品。整个审核、原作品覆盖、通知和 GIF 任务也没有统一事务。

### 帧包上传

- 预签名上传没有限制 ZIP 大小、Content-Type、文件结构或解压后大小。
- `confirm-upload` 信任客户端传入的 `ossKey`，不要求它等于服务端刚生成的路径，也不验证对象存在和归属。
- 知道其他私有 key 的创作者可能把自己的帧包记录指向该 key，使后续管理员/生产接口为其生成读取链接。
- 该链路需要对象前缀归属校验、HEAD 校验、病毒/恶意压缩包扫描和异步解包验证。

## 分红率与创作者加价

2026-09-04 后顾客端只读取管理员确认的 `CollabSaleSku.finalPrice`。旧创作者加价接口和页面暂时保留以免删除尚未确认的分红设计，但其 `creatorMarkups` 只作为兼容/待讨论数据，不会直接改变公开售价。后续需确认它应改为“调价申请”还是完全转为线下合作台账；在确认前不得让它成为第二套实时价格来源。

代码公式与 `REVENUE.md` 基本一致：新手期、活动期、正常期三者取最高，正常期可加独家奖励，再受最高分红率限制。

但“快照时点”存在根本冲突：

- 当前在作品审核通过时计算一次 `CollabWork.revenueRate`。
- 新手期 14 天结束后，这个字段不会自动下降；活动结束后也不会重算。
- 创作者牛量以后升降级，也不会改变已审核作品的新订单分红率。
- `CollabOrder` 又设计了订单级分红率快照，说明更合理的时点可能是成交时计算、随后冻结到订单。

创作者加价方面，规划称“加价 100% 归创作者，基础价按分红率计算”。当前 `CollabOrder` 没有 `markupAmount` 或对应入账字段，购物车又没有收取加价，因此这部分收益没有落账路径。

## 分红、冷却、储备金与结算

### 计划状态

`estimated -> cooling -> available -> withdrawn`，售后时还会写入未在主要注释和筛选枚举中的 `cancelled`。

### 当前实际断点

1. 支付回调创建 `CollabOrder` 的字段与 Schema 不匹配，异常被忽略，正常购买不会生成联名分账记录。
2. 管理员单笔把订单改为已收货时有后备创建逻辑，但用户确认收货、自动收货和管理员批量收货都不会创建缺失记录。
3. 如果未来修好支付并提前创建 `CollabOrder`，管理员后备逻辑看到记录已存在就直接返回，不会创建储备金账户变动和流水。
4. 后备逻辑按“收货时当前 SKU 价格”计算，不使用成交价；调价会改变历史订单分红。
5. `CollabOrder.orderId` 和储备金扣入/释放没有数据库唯一约束，并发或重复任务可能重复记账。

### 余额和结算问题

- 冷却到期把金额加到 `Balance.pendingAmount`；管理员结算时只增加 `availableAmount`，没有扣减 `pendingAmount`。
- 结算查询在事务外读取订单；两个管理员并发结算时可能对同一批订单重复增加可提现余额。
- 订单只按 ID 批量更新，事务内没有再次要求 `settlementStatus=pending`。
- 同一创作者一周只有一条结算记录；若本周结算后又有新订单变为 available，只能等下一周。
- “确认打款”实际上只是增加平台内部余额，没有连接银行、支付宝或灵活用工平台，也没有真实付款回执。
- 结算后 `revenueStatus` 仍为 available；提现后也没有把具体订单转为 withdrawn，创作者状态汇总会把历史订单长期算作可提现。
- 金额使用 Float/Number，不适合长期财务累计和精确对账，建议统一整数分或 Decimal。

### 储备金问题

- 第二笔及以后储备金只累加总额，没有更新 `nextReleaseAt/nextReleaseAmount`，创作者看到的最近释放信息会陈旧。
- 释放任务先查询“是否已有 release”，再创建释放流水；多实例同时运行时仍可能重复释放。
- `freeze/unfreeze/confiscate` 只有模型注释，没有实际管理接口和规则。
- 多笔释放流水的 `balanceAfter` 使用同一个最终余额，不是每笔变化后的逐笔余额。

## 提现

- 前端写最低提现 10 元，后端允许最低 1 元。
- 前端目前提交固定的“待绑定”作为姓名和账号，没有真实收款账户绑定与验证。
- 后端在事务外检查余额，再在事务内无条件扣减；并发提现可能导致负余额。
- 没有幂等键，重复点击或网络重试可创建重复申请。
- 项目没有管理员审核、拒绝、打款成功/失败的提现处理接口，也没有失败后返还锁定余额的流程。
- `WithdrawalRequest` 明文保存收款姓名和账号，没有字段级加密或密钥轮换设计。
- 提现记录响应虽然生成 `accountNumberMasked`，但通过 `...w` 同时返回完整 `accountNumber`，与代码注释“只显示后四位”不一致。
- 页面宣称灵活用工平台代扣代缴并预计 1 到 3 个工作日到账，实际仅有占位字段，没有外部平台集成。

## 牛量与推广归因

### 当前计算

- 每天 03:00 对所有 `CreatorProfile` 串行计算。
- 活跃分来自近 30 天审核通过的联名作品数。
- 声量分计划来自播放量、点赞量和人工系数。
- 转化分来自推广点击记录中已绑定订单的数量。
- 达标可直接升级；长期低于当前等级时每次最多降一级。

### 已确认断点

- 外部视频审核只把播放量/点赞量写在 `CreatorSocialLink`，牛量任务却从上一条 `BullScore` 读取；没有聚合代码，也没有爬虫，因此人工录入的声量不会进入积分。
- 推广链接能生成和展示，但没有点击采集接口、前端归因保存、订单绑定或累计计数更新；`ReferralClick` 没有创建者。
- 防异常声量的注释称“无订单或播放/订单比过高则不计分”，代码却在 `monthlyOrders===0` 时允许正常计分。
- 月订单数统计所有 `CollabOrder`，没有排除取消、退款或售后订单。
- 审核通过的修改版也可能计为投稿，重复影子记录会抬高活跃分。
- `bull.js`/Scheduler 展示系数使用 `1.0/1.2/1.5/1.8/2.0`，分红配置默认使用 `1.0/1.1/1.2/1.4/1.6`；页面看到的牛量系数不等于实际分红计算系数。
- 普通管理员可批量写任意牛量配置 key 和任意字符串数值，没有白名单、范围、权重和必须合计为 1 的校验。
- 管理员列表先加载全部创作者再在内存筛选/分页；创作者增多后响应时间和内存会线性增长。
- 每日任务按创作者串行执行多次查询；多 API 实例还会重复运行，规模扩大后需要任务队列、批量聚合和分布式锁。

## 外部视频链接

- 创作者能提交、修改待审链接和删除任意状态链接；管理员能审核并录入播放/点赞。
- URL 只验证为非空字符串，没有限制 HTTPS、平台域名或标准化，重复检测也没有数据库唯一约束。
- 未来若加入服务端抓取，必须先防止 SSRF、内网探测、重定向绕过和超大响应。
- 管理列表在数据库分页后再做关键词过滤，可能漏掉匹配项，返回的 total 也不是关键词过滤后的数量。
- 创作者可以删除已经审核并参与过声量评估的证据，缺少归档和审计状态。

## 商务合同

- 规划和 Schema 注释允许“大 IP 没有平台账号”，但 `creatorId` 在 Schema 和迁移中是必填非空外键；路由传 `null` 会创建失败。
- 合同附件字段存在，但新增、编辑、格式化响应和后台页面都没有附件流程。
- 合同类型没有对应字段组合校验，例如买断合同不强制买断金额，结束时间也不校验晚于开始时间。
- 打款记录保存在一个 JSON 数组中，采用读出、追加、整段覆盖；并发录入会丢数据，数组增长后读写成本持续增加。
- 打款日志没有独立主键约束、外部凭证、币种、付款状态、冲正记录和不可变审计链。
- 超级管理员可以物理删除合同。企业环境更适合归档/作废并保留完整版本与访问审计。
- 合同金额同样使用 Float；正式财务数据应使用 Decimal 或整数分。

## 数据库迁移状态

- 当前 `schema.prisma` 新增了 `shelfStatus`、暂停和下架字段，但现有迁移 SQL 中没有这些列。
- 按仓库迁移从零建库后，当前联名上下架路由会访问不存在的列。
- 违约政策路由使用 `PlatformConfig.key/value`，实际模型字段是 `configKey/configValue`，GET/PUT 都会运行时报错。
- 项目没有真实用户，修复迁移链和重建开发数据库的兼容成本较低；仍应先确定是否保留历史迁移，不能直接把 Schema 当迁移执行记录。

## 文档与代码差异

1. `REVENUE.md` 写订单发货后按周结算；代码是确认收货后冷却 15 天，再由管理员任意时间操作内部余额入账。
2. `REVENUE.md` 写结算后写 `earnings`；当前没有任何 `Earning` 写入，实际更新 `Balance` 和 `SettlementRecord`。
3. 文档规划 CRMEB 支付回调为联名主链路；当前 Web 已有自己的购物车/预订单支付链路，但联名记录创建失败。
4. `REVENUE.md` 仍把展示页、结算、数据面板和牛量列为待开发，当前页面和路由已存在，但不代表闭环可用。
5. `REVENUE.md` 的旧字段是 `bullEnergy/bullEnergyScore`，当前 Schema 使用 `bullLevel/bullScore/bullCoefficient`。
6. 文档的新手期和活动期有结束时间；审核时永久快照使到期逻辑不生效。
7. 文档称加价 100% 归创作者；当前订单、分账和余额没有加价收益字段。
8. `DATABASE.md` 描述每日冷却、90 天储备金和牛量任务；任务存在，但在 API 进程中运行且缺少多实例幂等保障。
9. `FRONTEND.md` 和页面文案把提现描述为真实代扣代缴流程；代码只有占位记录。
10. `USER_SCENARIOS.md` 设计创作者下架申请，当前只有管理员审批接口，没有创作者发起接口。

## 上线前阻断风险

| 风险 | 后果 | 改造复杂度 |
|---|---|---|
| 支付后联名订单无法创建 | 联名销售没有创作者收益记录 | 高，需与第二批统一重做成交快照和幂等支付事务 |
| 分红与储备金触发路径分裂 | 不同收货入口得到不同账务结果 | 高，需单一订单状态机和统一领域事件/事务 |
| 结算并发可重复入账 | 平台余额可能多记，产生实际资金损失 | 高，需行锁/条件更新、稳定批次号、不可变账本和幂等结果 |
| 提现并发可透支且无审核回退 | 余额负数、申请永久卡住或重复提现 | 高，需提现状态机、冻结账、外部支付回执和复核机制 |
| 新手/活动/牛量费率时点错误 | 长期多付或少付创作者，历史无法解释 | 中高，先定产品规则，再做订单成交时快照 |
| 创作者加价无入账路径 | 展示、实付和创作者所得不一致 | 中高，需价格拆分和订单明细 |
| 公开接口绕过真实货架状态 | 下架原帧仍可访问，可能侵犯版权和运营约束 | 低中，统一公开可见性服务和响应白名单 |
| 金额用 Float 且无统一流水账 | 累计误差、无法审计和对账 | 高，需 Decimal/整数分及账本迁移 |
| 私有 ZIP 确认信任任意 key | 越权引用私有对象、恶意压缩包进入生产 | 中，需上传会话、归属校验和扫描流水线 |
| 新货架字段无迁移 | 按现有迁移建库后接口直接报错 | 低，无真实数据时补迁移相对简单 |

## 性能与扩容风险

- 公开/管理联名列表缺少统一分页上限，复杂字段和预签名会放大响应。
- 批量联名申请在请求线程串行上传 OSS，应该改成“先创建任务，再异步处理素材”。
- GIF 生成使用 `setImmediate` 留在 API 进程，重启会丢任务，CPU 峰值也会影响接口延迟。
- 待结算接口一次加载全部可结算订单并在内存分组，订单量大时应改为数据库聚合和游标明细。
- 牛量管理列表先全量查询再内存分页；每日任务逐人多查询，均不适合大规模创作者。
- 合同打款 JSON 数组和作品 JSON 帧列表会不断膨胀，难以索引、并发更新和审计。
- 全部 Scheduler 随每个 API 实例启动，扩容前必须拆成单独 Worker 或加入可靠分布式锁。

## 建议的目标边界

1. `Order/OrderItem` 保存实际成交的基础价、加价、优惠、退款和分红基数。
2. 成交时计算并冻结订单级分红率，作品只保存规则来源或展示参考值。
3. 订单状态变化通过唯一服务触发冷却、储备金和逆向冲正，任何入口都走同一逻辑。
4. 资金使用不可变流水 + 余额快照，所有入账、冻结、提现、退款、储备金都有唯一业务键。
5. 财务操作采用经办/复核、权限分离、操作理由和外部凭证，不允许物理删除。
6. OSS 使用上传会话记录绑定所有者、对象前缀、用途、大小、哈希、扫描状态和有效期。
7. 推广归因先确定 Cookie/小程序场景值、归因窗口、去重和隐私规则，再实现点击与订单绑定。
