# 运维、质量、安全与容量现状

> 调查基准：2026-08-12。当前阿里云未充值、没有真实用户、没有生产环境。本文件评估“代码当前具备什么”和“企业上线还缺什么”，不代表本轮已实施整改。

## 执行摘要

项目已有较广的业务原型：单个 Fastify 服务包含大量业务路由，PostgreSQL Schema 当前有 75 个模型，Web 有数十个 HTML 页面，小程序有 14 个页面骨架。它适合继续产品验证和开发，但**目前不具备企业生产发布基线，也没有证据证明可承载大批量访问**。

最大的限制不是 Fastify 或 PostgreSQL 选型，而是运行体系仍不完整：迁移不可复现、敏感请求体进入审计日志、无统一限流/安全头、无业务自动测试/CI、无监控告警/备份演练，并且 CPU/内存重任务与 265 个 API 共用单进程。2026-08-12 已完成第一批配置、依赖、种子和基础检查整改。

## 当前可验证的正向基础

- Fastify 5、Prisma 5 和 PostgreSQL 是可继续演进的常见服务端组合，无需仅为“企业级”重写技术栈。
- `package-lock.json` 存在，`npm ci --dry-run` 可解析；当前 `npm audit --omit=dev` 报告 0 个已知生产依赖漏洞。
- 全部后端 JavaScript 文件通过 `node --check`，当前 Prisma Schema 通过 `prisma validate`。
- OSS 客户端强制 HTTPS，上传使用预签名思路；密码使用 bcrypt；新认证有短 AccessToken、RefreshToken 哈希、轮换和会话撤销的基础。
- 多个核心写流程已使用 Prisma 事务，部分库存操作使用条件更新或幂等键。
- `.env` 被 `.gitignore` 排除，没有发现环境文件被 Git 跟踪。

这些是良好起点，但不等同于经过生产验证。

`findMany` 与 `take` 不是一一对应，因此不能简单断言 79 个接口都缺分页；但它明确说明有界查询没有成为统一约束。管理、库存、机型、购物车、牛量和结算等模块存在全量读取或内存聚合，数据增长后会首先压迫数据库和 Node 堆内存。

## 环境与配置

### 当前事实

- `content-service/.env` 本地存在但不受 Git 管理；仓库已有脱敏的 `.env.example`。
- 启动前集中校验数据库、JWT、Cookie、CORS、OSS、短信和隐私版本；服务默认监听 3001，也读取 `HOST`、`PORT`。
- JWT 和 Cookie 不再使用源码默认密钥；生产密钥至少 32 位且必须不同。
- 生产拒绝任意 Origin、占位配置、模拟短信和缺失隐私版本；OSS 配置在接收请求前检查。
- 尚未接入正式密钥托管/轮换，也未建立预发和生产环境的供应流程。

### 上线要求

启动前必须使用结构化配置 Schema 校验所有必填值、长度和允许值；生产缺任何密钥或误用占位值都应 fail fast。密钥进入阿里云 KMS/Secrets Manager 或等价服务，数据库/OSS/SMS 使用最小权限子账号并建立轮换流程。

## 部署与扩容

`docs/ARCHITECTURE.md` 规划 Nginx + ECS + PM2 + PostgreSQL，但仓库没有 Nginx 完整配置、Dockerfile、进程管理配置、IaC、部署脚本、CI/CD、回滚步骤或发布检查表。`crmeb/` 实际只有 `.gitkeep`，不能按架构图视为已接入商城。

后端固定监听 `0.0.0.0:3001`，根路径只返回静态成功消息，不检查数据库、OSS 或 Scheduler，因此它只是存活响应，不是 readiness。代码没有 SIGTERM/SIGINT 优雅停机处理；Prisma 的 `onClose` 只有在 Fastify 被正确关闭时才执行。

两个 Scheduler 随每个 API 实例启动。当前单实例可运行，但横向扩容会重复执行任务，API 全停时任务也随之停止。GIF/缩略图、条码、DOCX/ZIP 和批量下载也在 API 进程执行，可能阻塞事件循环或消耗大量堆内存。

### 推荐的渐进拓扑

首发无需一开始拆成大量微服务。更稳妥的顺序是：

1. 静态 Web 交给 CDN/对象存储；HTTPS 网关/Nginx 只转发 API。
2. API 保持一个代码库，但做成无状态进程；上传走 OSS 直传。
3. Scheduler 和图片/文档生产任务迁到独立 Worker，使用持久队列、任务租约、重试和死信。
4. PostgreSQL 使用托管实例、连接池、自动备份和慢查询；Redis 仅在共享限流、缓存、锁或队列确有需要时引入。
5. 压测证明单实例上限后再水平扩容，不按猜测购买机器。

## 安全基线

### 已确认高风险

1. `ARCHITECTURE.md` 保留了明文数据库连接口令示例，`test.http` 保存多枚完整 JWT；Git 跟踪文件中还存在其他疑似凭据模式。即使是开发凭据，也应轮换并清理当前文件，必要时清理 Git 历史。
2. 全局 `onResponse` 审计 Hook 把已登录 POST/PUT/DELETE 的整个请求体截取后写入数据库。密码、新地址、收件电话、提现账号等会进入 `operation_logs.after`。
3. 生产环境缺密钥时会使用固定 JWT/Cookie 默认值；`NODE_ENV` 漏配还会放宽 CORS。
4. 未注册 `@fastify/helmet`、全局/API 分组限流、CSRF 防护或统一安全响应头。短信和联络有局部控制，但登录、上传、互动、搜索和高成本导出没有一致的滥用防护。
5. Web Token 存 localStorage 且有持久化 XSS 面；小程序刷新凭证架构不通。详见对应前端模块。
6. 支付回调仍为 Mock/未验签，财务、提现和结算闭环不满足真实资金安全要求。

### 审计日志建议

审计系统应记录动作、目标 ID、结果、操作者、请求 ID、来源和受控差异，不保存任意请求体。建立字段级 denylist/allowlist，对手机号、地址、账号、Token、密码、验证码、Cookie 和文件签名 URL 脱敏；安全审计日志与业务调试日志分离并设置访问权限和保留期限。

## API 契约与质量

- 265 个端点中静态找到约 51 个 `schema` 配置，未发现 Fastify response schema；输入和输出契约覆盖率较低。
- Web 和小程序都人工复制 DTO/API 路径，已出现多处会直接失败的契约漂移。
- 后端已有 `dev/start/check`；`check` 覆盖环境、JavaScript 语法和 Prisma Schema，但仍无 lint、业务自动测试、覆盖率、迁移部署或页面冒烟测试。
- `test.http` 是人工请求笔记，依赖固定 ID/Token，不是隔离且可重复的测试。
- 仓库没有 `.github/workflows`、CODEOWNERS、SECURITY、贡献规范或发布审批配置。
- `docx`、`adm-zip` 原先只因上层依赖而可解析，现已在服务 `package.json` 和锁定文件中显式声明并完成独立安装核验。
- `README.md` 提及的 `mowo_process.py`、`mowo_word.py` 未在当前仓库找到；生产操作不能依赖未版本化工具。

### 最小质量门禁

1. `npm ci`、`node --check`、Prisma validate/format、静态链接检查。
2. 从空 PostgreSQL 执行迁移和种子，再跑服务健康检查。
3. API 契约测试覆盖登录、权限、上传授权、购物车报价、支付回调、库存、生产状态、结算和注销。
4. Playwright 覆盖 Web 首发闭环；微信开发者工具自动化/真机清单覆盖小程序闭环。
5. 依赖漏洞、Secret 扫描、SAST 和镜像扫描。
6. 发布到预发后执行冒烟、回滚演练，人工批准进入生产。

## 性能与容量

### 当前瓶颈方向

- 列表全量读取、Node 内存聚合和缺少针对查询的复合索引。
- 购物车等接口存在 N+1 查询和在读取路径中逐项写状态。
- 图片下载使用 `fetch(url, { timeout: 15000 })`，Node 原生 fetch 不识别该 timeout 选项；短信 `https.request` 也没有显式超时/Abort。
- API 进程同步承担 Canvas/GIF、条码、ZIP 和 DOCX 生成；大任务可造成内存峰值和请求排队。
- OSS 签名、外部图片、短信、未来支付等外部调用缺统一 timeout、重试、熔断和幂等策略。
- 每个 API 实例都有 Prisma 连接池和 Scheduler；扩容前没有总连接预算与任务单例保证。
- 无 CDN 缓存策略、热点缓存、请求体分业务上限、响应压缩或容量基准结果。

### 压测方法

先由产品确定首发峰值、并发、文件大小和 SLO，再构造匿名浏览、登录、作品列表/详情、加购/结算、后台导出等混合场景。至少记录吞吐、P50/P95/P99、错误率、Node 堆/事件循环延迟、数据库连接/锁/慢查询和 OSS 延迟。支付、库存、结算要额外做重复回调和并发竞争测试。

## 可观测性与应急

当前只有 Fastify/Pino 基础日志，没有统一 request ID、结构化业务错误码、指标、Tracing、错误聚合、日志脱敏、Dashboard 或告警。也没有事故分级、值班联系人、状态页或运行手册。

最低应监控：请求量/错误率/延迟、进程 CPU/内存/事件循环、数据库连接/慢查询/锁、队列积压、Scheduler 成败、短信/OSS/支付外部依赖、支付金额对账、库存负数和结算异常。告警必须指向具体处理人和 Runbook，不能只收集日志。

## 备份、恢复与数据治理

仓库未见数据库备份、OSS 版本/生命周期、恢复演练、RPO/RTO、跨区域副本或灾难恢复文档。上线前至少需要：

- PostgreSQL 自动全量备份 + PITR，备份加密并与运行账号隔离。
- 每季度或重要变更前做恢复演练，记录恢复时间和校验结果。
- OSS 私有桶开启版本控制/防误删策略，上传临时对象与正式归档使用不同生命周期。
- 财务/订单/合同/审计与可删除用户内容分别定义保留和删除规则。
- 为误删、错误发布、密钥泄露、支付回调积压和库存错账建立 Runbook。

## 工程就绪等级

> 以下 R0-R4 是工程准备等级，不是 `RELEASE_SCOPE.md` 中的产品阶段 B/C/D。二者的对应关系见 `docs/LAUNCH_READINESS.md`。

| 等级 | 目标 | 主要事项 | 复杂度 |
|---|---|---|---|
| R0 可重复开发 | 每台机器可重复启动 | 当前 Schema 基线迁移、`.env.example`+校验、声明完整依赖、移除凭据、统一 API Origin | 中 |
| R1 可安全邀请 | 能接收受邀用户真实资料 | 审计脱敏、密钥轮换、权限统一、限流/安全头、XSS、上传授权、会话和数据删除 | 高 |
| R2 可真实交易 | 钱、库存、订单可对账 | 统一报价/订单状态/库存/支付/退款/售后，幂等与不可变流水 | 高 |
| R3 可稳定发布 | 每次改动可验证和回滚 | 自动测试、契约生成、CI、预发、空库部署、回滚、监控和安全扫描 | 中高 |
| R4 可规模扩展 | 有证据满足目标流量 | Worker/队列、查询与索引优化、告警、压测、备份恢复、多实例验证 | 高 |

由于没有真实用户，R0 和数据模型调整现在做最省成本；R2/R4 应在首发业务范围和容量目标确认后设计，避免为了“企业级”过早堆基础设施。

## 发布阻断清单

以下任一未解决，都不应接受真实支付或正式用户数据：

- 数据库不能从空库迁移并恢复。
- 代码/历史中凭据未轮换，生产允许默认密钥启动。
- 审计日志仍保存敏感请求体。
- Web API 地址仍指 localhost，核心 XSS/设置页故障未修。
- 小程序登录续期、首页和购物车契约未修，核心页面仍占位。
- 支付回调未验签/金额核验/幂等对账。
- 库存、订单、退款、结算的并发一致性未通过测试。
- 无备份恢复、监控告警、CI 测试和回滚演练。
