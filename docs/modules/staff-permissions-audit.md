# 员工权限与安全记录

> 实施日期：2026-08-13。本文记录当前代码事实、岗位边界、接口保护和测试方式。生产、库存、分红等业务规则不由本模块定义。

## 简单说明

员工账号不再只依赖“数字越大权限越高”。数据库保留旧 `role` 兼容现有页面和路由，同时新增固定 `staffRole`，服务器根据岗位和请求区域决定是否允许访问。隐藏菜单只是减少误点，服务器拒绝才是真正的权限保护。

## 固定岗位

| staffRole | 中文名称 | 当前允许区域 | 当前禁止区域 |
|---|---|---|---|
| `OWNER` | 负责人 | 全部后台、员工岗位、安全记录 | 不能修改自己的岗位；最后一位负责人不能被降级 |
| `CUSTOMER_SERVICE` | 运营客服 | 定制订单、售后、联络留言、商品维护、普通用户查询和封禁 | 员工岗位、安全记录、合同/结算/牛量、生产库存 |
| `PRODUCTION` | 生产人员 | 库存、材料、帧包、批次、扫码、生产导入 | 用户总表、员工岗位、安全记录、合同与合作财务 |
| `COLLAB_OPS` | 合作运营 | 创作者认证、联名、合同、结算、牛量、引流和分红配置读取 | 用户总表、员工岗位、安全记录、生产资料；高风险平台配置仍由负责人修改 |

分红、结算、牛量和提现相关代码、页面与数据未隐藏或删除。本批只限制员工访问范围，产品是否首发上线仍按 `RELEASE_SCOPE.md` 和后续业务决定执行。

## 负责人初始化状态

- 2026-08-13 已在本地开发数据库通过受控初始化建立一位真实负责人账号，账号使用短信验证码登录，不预设密码。
- 文档、通用操作日志和代码均不保存负责人明文手机号；明文只存在于受访问控制的用户账号数据中。
- 当前保留原有负责人作为备用，因此本地共有两位可用负责人。是否停用旧测试负责人，需在新负责人完成登录与后台权限验证后另行确认。
- 该初始化动作同时写入 `audit_logs` 和 `operation_logs`，记录岗位、结果和目标账号 ID，不记录明文手机号。

## 服务端实现

- `src/lib/permissions.js`：岗位、权限点、岗位模板和 URL 到权限点的映射。
- `src/plugins/jwt.js`：每次认证回查数据库当前 `role`、`staffRole`、账号状态和设备会话。
- `src/index.js`：后台请求统一经过岗位权限 Hook，单个路由遗漏 `preHandler` 时仍有入口保护。
- `routes/admin.js`：员工岗位调整、账号保护、安全记录查询和售后鉴权。
- 岗位变更会撤销目标员工全部设备会话，旧 Access Token 立即失效。

员工保护规则：

1. 只有负责人能设置或移除员工岗位。
2. 任何人不能修改自己的岗位或封禁自己。
3. 运营客服只能封禁普通用户，不能停用员工。
4. 负责人账号不能通过普通封禁操作停用。
5. 系统必须至少保留一位负责人。

## 安全记录

`operation_logs` 现在记录：员工、旧兼容角色、请求方法、路径、目标、IP、结果、HTTP 状态、设备会话、浏览器信息和时间。

结果值：

- `SUCCESS`：操作成功。
- `FAILED`：请求已处理但失败。
- `DENIED`：未登录或岗位越权，被服务器拒绝。

统一脱敏规则位于 `src/lib/audit.js`。密码、验证码、Token、Cookie、密钥、完整手机号、地址、收件信息、快递单号及文件内容不会写入通用操作详情。历史高风险详情在迁移中统一替换为 `HISTORICAL_SENSITIVE_DETAIL_REMOVED`。

`admin-logs.html` 仅负责人可访问。页面对日志内容做 HTML 转义，数据库中的特殊字符不会作为网页代码执行；页面可按方法和结果筛选，并显示员工姓名、脱敏手机号和岗位。

网络安全相关日志正式保留期限上线前需由公司结合适用法律和律师意见确认。当前产品决策基线为不少于六个月，同时遵循个人信息最短必要原则；不得把安全日志当成长期保存用户隐私正文的理由。

## 已修复缺口

- 前台“进入后台”入口只在实时用户信息含固定员工岗位时显示；普通用户退出或切换账号后会清除残留的员工显示状态。
- 后台首页不再只读取浏览器旧令牌中的数字角色，而是向服务器查询当前岗位；数据库岗位调整后刷新页面即可按最新岗位判断。
- `GET /api/admin/aftersales` 和 `PUT /api/admin/aftersales/:id` 已补登录和员工权限保护。
- 用户列表默认只返回脱敏手机号。
- 用户列表同时显示 `ACTIVE / PENDING_DELETE / DELETED` 等账号状态，避免把“注销处理中”误判为普通或封禁账号。
- `admin-account-deletions.html` 对运营客服开放脱敏只读状态；只有负责人拥有重试、填写原因暂停和恢复权限。系统不提供人工批准、拒绝或强制删除。
- 注销任务失败 15 分钟后自动重试；连续失败 3 次或持续 1 小时转人工关注，24 小时为紧急提示，48 小时为内部异常处理目标。
- 运营客服不能封禁生产人员、合作运营或负责人。
- 岗位和封禁判断以后端数据库实时值为准。
- 安全记录不再复制完整请求体。
- 未登录和越权后台访问会留下 `DENIED` 记录。

## 按功能临时授权的后续方向（尚未实施）

当前代码已经把“岗位”和“权限点”分开：页面仍按固定岗位展示，服务器则通过 `PERMISSION` 常量判断具体后台区域。这为以后增加按功能授权留出了位置，但当前数据库还没有员工申请、负责人审批、到期时间和撤销记录。

首发建议继续使用四个固定岗位作为基础权限，不立即建设大型公司的完整权限申请平台。原因是首发人员少，完整平台会同时增加审批流、到期任务、离职回收、权限冲突和管理员页面，复杂度明显高于当前收益。

当出现跨岗位协作或临时员工后，建议采用“固定岗位 + 少量例外授权”，而不是推翻现有岗位：

1. 岗位继续决定员工日常基础权限。
2. 新增单个功能授权记录，至少包含员工、权限点、只读/可操作范围、申请原因、批准人、开始时间、到期时间和撤销时间。
3. 负责人在后台批准、提前撤销或续期；系统到期自动失效，不能依赖人工记忆。
4. 所有申请、批准、使用、拒绝和撤销继续写入操作与审计日志。
5. 普通用户/游客身份不要混入员工权限体系。需要只看不能改时，应命名为“员工只读权限”，避免把网站游客误当内部员工。

员工达到约 5 至 10 人、同一功能频繁出现跨岗位借用，或开始接触合同、结算、付款等高风险操作时，再实施这一层最合适。更大规模后再增加多级审批、资源范围、定期复核、单点登录和强制多因素认证。
